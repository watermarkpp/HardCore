## 1. 最初要解决的事情

用户要的是手机稳定运行，以及以后添加词缀、技能点燃、新怪物、装备、宝石、符文、镶嵌等内容时，避免四处修改核心大脚本。总体路线一直是模块化单体、编译式数据扩展、少而明确的领域端口和有界执行。不是增加Manager数量，也不是把游戏改为本地服务器、整套ECS或每个模块一个线程。

保留现有ContentLayers、唯一canonical planner、HP/actor状态权威、空间索引、PlayerState、有序持久化writer、资源缓存/lease以及旧火墙合同。新端口委托原权威，不增加第二份HP、技能规划或存档写入真相。

装配变化时编译属性/技能修饰/触发订阅/依赖；运行时只访问实际匹配订阅及到期效果。未装备、未激活内容目录变大，不应使每击或每帧扫描增加。编译不扣MP、不抽战斗RNG、不构建另一份release计划。有效定义必须贯穿资源报价、准入、冷却、伤害、几何与表现依赖。

## 2. 三种扩展层级

| 层级 | 正确扩展方式 | 交付边界 |
|---|---|---|
| L1 已有原语组合 | 定义、参数、资源清单、组合测试 | 常规内容不散落修改核心；数值和来源有稳定ID |
| L2 新行为原语 | 小型可信handler、明确能力与版本端口 | 有界计算、只读事件和受约束命令；不直接写HP/Node或同步读文件 |
| L3 系统模块 | 模块自身UI/规则，领域端口和事务合同 | 镶嵌/符文等业务独立，但物品、金币、保存仍由唯一权威提交 |

首期是可信内置模块，权限属于工程约束，没有承诺任意脚本沙箱。也没有承诺未来所有未知玩法永远零核心修改。确需新原语时，通过清晰版本边界和连带回归扩展。

## 3. 必须保持的执行合同

- 已接受动作锁定当时合法定义、来源、数值、资源与容量。实时几何/目标life在原释放边界采样，不能为了容量把目标都提前冻结。
- 在真实HP提交后、observer/回血改变现场前冻结本次损失/死亡事实。基础同步目标批次完成后才处理新增反应，保持旧AOE遍历与death-pending边界。handler产生命令，不递归调用其他handler。
- 所有physics/process/deferred入口共用同一主循环剩余预算，嵌套计费不重复。必要攻击、碰撞、伤害、死亡不能因预算不足丢失。可延后工作有游标、小原子量子和最老服务年龄。
- 内存容量、累计执行量、截止时效是三种不同证明。活状态数、有限当前同屏怪数或帧率单项，不能代替整链及长期服务保证。
- 旧RNG、碰撞、触控、移动、时间域和旧火墙真实寿命保持合同。新触发独立固定算法随机域；非法请求在抽签前拒绝。空扩展差分必须覆盖旧行为。
- 生命周期按实际owner/阶段退休，不用任意TTL/LRU清掉必要票据。旧actor life、旧root、资源lease、credit、已接受child分别交接，节点死亡不自动抹掉归属。队列明确取消资格与单消费者；已提交持久化回执换图后仍要消费。
- 经济事务只预留相关输入；复核稳定身份与版本，确定结果和operation_id一次生成。不能拿保存中的旧整份profile覆盖期间新战斗/药剂状态。
- 未知模块版本先保护所有权和完整原载荷，再处理当前schema。未知并不等于合法默认值；不得清空后自动保存。当前版本损坏的合法backup恢复与未来未知版本保护是不同路径。
- 关键资源依赖含所有可能子效果、声音、图标与表现；准入前准备，沿现有request/get/lease/cache权威。加载完成不证明首次GPU绘制无卡顿。必要可读性不能与装饰一起被丢弃。

## 4. 用户最新裁决覆盖旧示例

原RFC保留原文用于追溯，新的合同和测试另记录版本；不可只凭Pro较早回复恢复已被用户覆盖的规则。

| 主题 | 旧历史 | 当前有效规则与含义 |
|---|---|---|
| 同种DOT | 更强强度、延长到期、保持旧next_tick/归属 | 完整替换：新伤害、新周期、完整期限、新来源/credit。新合法施加成功后才替换；较弱也替换；从实际施加时刻计算新due/expiry |
| 多来源 | 部分夹具三来源同ignite形成90状态 | 不同种共存；同种只有显式叠加天赋才有独立层。三来源不等于三种或三层许可 |
| 未提交旧tick | 旧实例继续刷新 | 旧未提交tick失效；已提交HP/死亡事实/合法接受child不回滚、不改credit。旧返回栈不得推进或stop新实例 |
| 应用顺序 | 可能误按cast编号淘汰旧释放 | 合法实际应用顺序决定替换；A早接受晚释放，仍可能合法替换已应用B |
| 世界出生配置 | 活世界任意增加计划外slot会破坏容量闭包 | 新配置在地图重新发布/切换后生效；当前战斗只消费完整已发布刷怪计划和登记召唤。正常刷新和原已接受工作保留 |

频繁以短于周期的间隔刷新同种DOT，会把next_due不断后移。没有tick可能是本次新产品规则的合法结果，不能为了测绿偷偷恢复旧相位。90状态测试若继续保留相同负载，必须来自合法三种DOT或明确登记、默认关闭的独立层验证权限；仅改名字不能伪造种类。无合法配置时标NOT_RUN/MISSING，不能弱化正式场景或默开全角色叠加。

通读后没有发现总体架构路线需要推翻，但局部审查曾多次被后续纠正，云端应避免恢复旧结论：

| 历史偏差 | 后续纠正后的做法 |
|---|---|
| 只读commit/tree/搜索结果便形成源码判断 | 固定SHA后读实际文件/blob；机械附件范围与源码语义复核分开 |
| 用较早P5未实现段落覆盖后续进度；把旧遗物未迁journal当阻断 | 继承实际Gem/Rune端口、身份/所有权及已有专项；未承诺把所有旧经济迁完，也未授权上线正式费用/概率 |
| 附件物理行号当源码行号；一次WORLD invocation关联错误 | 回到真实文件及原receipt核对；错误引用不能用于验收 |
| 曾建议清空真实profile | 后续明确撤回；只用runner隔离临时用户数据，保留真实存档 |
| 将death/life清理等同所有receipt可退休；随意固定64条journal裁剪 | 按producer/consumer与持久化watermark/恢复合同退休，不能TTL/LRU或凭魔法数丢记录 |
| 仅根动作fanout预留当成所有未来目标承诺；出生后track_child当准入 | 接受前完成逐目标/整链资格与容量；完整计划及真实SummonQueue资格必须在factory副作用前验证 |
| 周期取消只观察queued，忽略producing的实际owner | 未消费取消与已经被批次消费的责任分开，单消费者与终态关联 |
| 把旧“child未接入、Root未实现、Scene API未消费”等缺口反复续作 | 5c34/fff/e72等后续增量已关闭的项目继承，相关改动再跑回归，不再造第二实现 |
| 帧间隔当CPU；ABBA尾部小样本泛化成全部性能胜利 | CPU、帧间隔、完成量、实际服务延迟、队列、内存分列；阶段及重复运行不是当前同SHA全部通过 |

当前应收口现有工程，不能从P0再造一遍，也不能只剩“出包”口径。云端按原RFC §20、§21、§22、§23形成逐条矩阵，并把后来Task编号映射P0—P6。只使用PASS、FAIL、BLOCKED、NOT_RUN、MISSING；产品变更另写原因，不创造验收状态。

最终候选同一固定源码/内容要覆盖空扩展旧行为差分、合法及非法组合、关键高阶/生成式组合、真实生产适配器和持久化恢复、必要性能与正式runner防假PASS。Windows、Linux headless、Android导出、GPU和设备分别记录；阶段回执不能相加宣称全量验收。
