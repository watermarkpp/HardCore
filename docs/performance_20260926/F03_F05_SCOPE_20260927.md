## 已核实生产路径

### F03

- `PlayerState.record_kills_and_experience_batch` 在一次死亡批次内修改任务、经验和等级；非测试模式经 `_commit_death_event` 同步写盘；失败恢复任务、经验和等级，GameRoot 恢复世界刷新状态。成功才允许掉落抽取。
- `_commit_death_event` 每次包含完整 `quest_states` 和完整压缩后的 `world_state`，而不是本次修改的槽位。`_write_json_atomic` 在主线程完成编码、校验、写入、flush、回读、轮换与再次回读。
- `mark_monster_respawn_dead` 单次调用依次经过 compact/normalize、with_deadline/normalize 和 entry_for/normalize；读取一个槽位也会重建整个表。不能仅缩短 JSON 后仍保留每件死亡的多次全表重建。
- `prepare_loot_save` 调用 `_prepare_character_save_payload`，后者先同步 `_checkpoint_world_clock`。现有 `loot_prepared_file.gd` 只在后台准备私有 TMP；`finish_prepared_loot_save` 仍在主线程验证和执行 `_promote_verified_json` 的文件事务。
- `finish_prepared_loot_save` 更新日志水位时使用当前 `_death_event_sequence`，后台重构必须改为已冻结、实际持久化的请求序号，不能从完成时的活动角色推导身份或水位。
- profile 验证链调用 GameData 的掉落实例验证；它不是可直接交给线程调用的纯函数。工作线程不得持有 PlayerState / GameData 节点回调。

### F05

- `_pump_enemy_death_work_queue` 只从 `_pending_enemy_deaths[0]` 选择结算和显示任务。该任务处于 MATERIALIZING 时，后续 QUEUED 怪物不能结算。
- 批次成功后 `_settle_pending_enemy_death_batch` 在同一个调用内对每只怪执行完整 `_plan_enemy_death_item`；外部 1.2ms 预算无法中断这段调用内部的存档和完整规划。
- 表现节奏为生产模式一件 / 至少两帧；此节奏继续保留。它应限制显示工作，不应延迟后续死亡的经验、任务和已确认的刷新计划。
- 碰撞落点已有可暂停的 `_advance_loot_ground_position`，保持候选顺序、有效地形判定和最终位置规则。固定名称 F04 不再进行全图避让重排。
