## 最多三个值得补的具体缺口

1. **G1（已知 V3 待合并验收项）：Loading 旧 epoch 与失败时序。** 合入既有 `combat_epoch_delivery_test` 后，在最终 HEAD 复跑其旧代次断言，并与一次 arrival failure/retry 下的待拾取、待死亡结算对账；断言旧 epoch 不伤害、不复活、不发奖励，失败后锁可恢复。将同帧致死→传送顺序一起记录，避免把已有的 stale token 检查当成旧 epoch 回调证据；不另建同覆盖测试。
2. **G2：生产死亡掉落到跨角色实例的一条链。** 用正式敌人死亡/掉落计划产生带 `drop_affix` 的实例，经真实 `LootPickup` 收取后执行保存失败重试、p→shared→q→equip→reload；每一站对账相同 `instance_id`、modifier 和实际属性，另在 shared/equip 站点各注入一次失败并确认源记录仍在。
3. **G3：金币上限入口矩阵。** 在 `PLAYER_GOLD_CAP-1` 和恰好上限分别走 GameRoot 金币拾取、单件出售、批量出售、任务奖励及 `receive_loot_batch_partial`；失败必须保留地面拾取、背包物品或未领取任务状态，并断言 UI/回调不会先确认销毁。保留现有负值、overflow migration 和 `add_gold` rollback 断言。

除上述三项外，本复核没有把设备未连接、V3 待 merge、WAL 进程崩溃重启或视觉验收重新包装成新发现；它们仍是既有记录的验收边界。
