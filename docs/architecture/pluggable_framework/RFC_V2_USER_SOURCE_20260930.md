## 0. 决策摘要

选择“**模块化单体 + 数据驱动的机制组合 + 有界的运行时执行核心**”。所有模块仍在同一个游戏进程内，战斗、移动、物品、存档各自保留唯一权威；扩展通过受约束的接口接入，不另建本地服务器，不全面改写成 ECS，也不把每个词缀做成独立节点或线程。

上一版运行时方案解决“工作怎样安排”；本版补齐“内容怎样增加、机制怎样组合、组合如何安全运行”。两者是一套架构的两个方面，不是两个平行框架。

核心约束：

1. **常规新增内容改数据；真正新增行为原语才增加小型机制处理器；核心接口的改变单独版本化。** 不能承诺所有未来玩法都无需改代码。
2. **词缀、装备、符文、镶嵌、套装、天赋、怪物被动，统一提供属性贡献、技能修饰与触发规则。** 它们不是各自一套战斗系统。
3. **装配期编译，战斗期直接消费。** 配置解析、依赖排序、词条组合和静态校验不进入每次命中循环。
4. **战斗效果与画面效果分开。** 点燃属于持续伤害机制；火焰画面只是表现。动画是否加载完成不决定已经接受的伤害。
5. **模块不能直接写别人的状态。** 扩展只产出允许的修饰或命令；当前领域权威负责验证、提交、记录结果。
6. **共享预算不等于丢伤害。** 调度限制可延后工作；必要玩法计算靠有界内容、合适算法和实测成本保证，不靠无限排队或偷偷降频。
7. **每个扩展携带身份、依赖、成本、资源和迁移契约。** 没有这些材料的功能包不得发布。
8. **历史合同原样保留。** 坐标、Snapshot、来源受击规则、已有 RNG 顺序、原装备生成与存档验证，不因重构被悄悄改写。
9. **插接不等于随时热拔。** 安装新包在启动或受控重载边界；换装备在原子事务边界；战斗中不卸载任意脚本和正在使用的规则。
10. **框架成熟以证据定义。** 空扩展差分、组合效果、取消/恢复、存档故障、复杂战斗及多设备长时间测试共同通过，才算达到交付门槛。

**最需要改变的不是目录数量，而是新增功能的接入方式。** 现在增加一个新功能，容易同时碰到数据解析、属性汇总、技能分类、伤害、UI、存档白名单和资源加载。新架构要把这些变成少数稳定端口，而不是每次靠全仓搜索逐处补条件。

这并不证明全部长帧都由架构造成。GPU、首次资源使用、具体算法与设备热状态仍需要分别测量。

## 3. 架构选择与结构

### 3.1 三种路线

| 路线 | 好处 | 核心问题 | 决定 |
|---|---|---|---|
| 任意脚本插件 + 全局广播事件 | 初期接入快 | 重入、执行顺序、每击全表扫描、递归触发与成本不可控 | 不采用 |
| 全面 ECS/独立服务器式重写 | 可以全面重做数据布局 | 迁移面过大，重复状态/同步风险高，不能证明比现有增量优化划算 | 不作为本轮路线 |
| 现有领域权威 + 编译式扩展 + 受约束端口 | 能渐进保留玩法，并控制组合成本 | 要认真设计注册、版本、状态和验证边界 | **采用** |

### 3.2 目标依赖方向

```text
已有内容源、地图编辑、规则覆盖、新增功能包
                    │
             校验 / 编译 / 发布
                    ↓
      不可变有效内容目录 + 功能清单 + 资源依赖
                    │
 装备/符文/镶嵌/状态/怪物特性 → Actor 装配编译器
                    │
        属性贡献 / 技能修饰 / 已匹配触发表
                    ↓
         当前唯一技能计划与战斗执行链
                    │
          明确的扩展执行检查点
                    ↓
        机制处理器 → 受约束效果命令
                    │
    当前领域权威提交：HP / 状态 / 位移 / 物品
                    ↓
      结果记录 + 视图脏标记 + 表现提示
                    │
        HUD / 动画 / 音效 / 特效适配器

旁侧基础能力：
  世界执行协调、时间域、共享帧预算、既有空间查询、
  资源预取与应用、持久化事务、身份/生命周期、诊断。
```

规则层不得反向依赖 HUD/场景节点；表现层不得反向决定伤害；新增功能包不得相互直接读写内部状态。交互通过公开定义、标签、查询或明确命令完成。

**这不是一条全局大 FIFO。** 战斗、寻路、资源、物品事务与表现有各自的顺序和时效，不能混在同一队列相互阻塞。

## 4. 可插接分成三层

### L1：内容配置型

使用既有机制原语组合的新词缀、新装备、数值型符文、普通怪物变体、配方、表现映射。交付以数据、资源声明和测试用例为主；不修改 `enemy.gd`、`player.gd` 或 `game_root.gd` 的专属分支。

例：生命+50、指定技能等级+1、烈火命中后施加已存在的燃烧效果、把现有投射物配置给一个新怪物。仅当相应原语已存在且适用时，这些才是纯配置工作。

### L2：机制原语型

现有能力无法表达的行为，新增一个小型、审查过的处理器，例如“在满足条件时按某种新规则转换伤害”。它声明读哪些字段、输出哪些命令、在哪个检查点运行、最大工作量和生命周期；不能接管整个游戏循环。

不能为了声称“零代码扩展”而做可执行任意表达式、反射任意方法的 JSON 语言。普通组合用数据，确实复杂的新行为用明确类型的代码。

### L3：业务模块型

符文、镶嵌、锻造、合成等模块，拥有自己的规则、界面和可持久化状态，但通过共同的物品事务、装配贡献、能力授予和展示端口接入。业务模块不拥有独立 HP、存档文件竞争写入或第二套技能执行器。

**本轮优先支持项目内可信模块。** 不承诺第三方任意 MOD 脚本的安全沙箱。接口限制与静态检查是工程约束，不是同进程 GDScript 的安全隔离保证。

## 5. 功能包协议

### 5.1 清单必须声明的内容

每个功能包至少声明：

| 类别 | 必需信息 |
|---|---|
| 身份与兼容 | `module_id`、模块版本、契约版本、所需核心 API 范围、内容 hash |
| 依赖 | 必需/可选依赖、冲突包、显式覆盖目标、互斥组 |
| 注册内容 | 属性、标签、效果、技能修饰、触发规则、配方、怪物 profile、表现提示、扩展 schema |
| 能力权限 | 允许查询的端口与允许输出的命令类型 |
| 生命周期 | 全局/角色/世界/装备来源的作用域；生效、撤销、取消、收尾策略 |
| 成本 | 最大扇出、最大状态数、目标数量策略、更新方式、资源内存与表现等级 |
| 持久化 | schema、迁移器、未知版本处理、依赖缺失策略 |
| 验收 | 功能、失败、组合与性能场景；预期实际检查数 |

以下是**清单形状示例**，不是已经可导入现有游戏的 JSON，也不是正式开放点燃玩法：

```json
{
  "module_id": "hc.features.ignite",
  "module_version": "1.0.0",
  "contract_version": 1,
  "requires_core_api": {"major": 1, "minimum_minor": 0},
  "required_capabilities": ["combat.post_hit.v1", "effects.periodic.v1"],
  "registers": {
    "effects": ["hc.effect.ignite.v1"],
    "triggers": ["hc.trigger.fire_sword_ignite.v1"],
    "cues": ["hc.cue.ignite.v1"]
  },
  "scope": "world",
  "activation_boundary": "world_ready",
  "requested_commands": ["apply_status"],
  "continuous_callbacks": [],
  "persisted_module_state": false
}
```

### 5.2 注册与发布

顺序：读取现有内容与功能清单 → 解析依赖 → 验证 ID 与 schema → 验证冲突和命令权限 → 编译规则及触发表 → 验证容量与资源闭包 → 暂存候选目录 → 原子发布新有效目录。

循环依赖、未知操作、同一 ID 的隐式覆盖或两个互斥的投递替换，同时存在时必须拒绝候选。不能“后加载覆盖前加载”。显式优先级也不能用来掩盖原本不允许组合的修改。

现有 `ContentLayers` 是数据进入系统的入口。新编译器消费它及正式 canonical 数据，不创建第二个可编辑怪物/装备/技能数据库。代码处理器采用构建时固定的可信映射，不根据外部配置任意 `load()` 一个脚本。

### 5.3 启用和停用

新包只在启动或受控的世界重载边界启用。单纯换装备是来源绑定变化，不是卸载功能包代码。

停用流程是：停止新准入 → 处理活动实例的明确去向 → 等待必须消费的事务回执 → 移除订阅与来源绑定 → 释放资源租约。活动燃烧能否持续到期由效果策略决定；已进入落盘提交的物品事务不能随世界销毁而丢弃。

## 6. 统一的定义模型：少数基本积木

建立以下逻辑定义，按有实际消费者的顺序实现，而不是先创建大量空类。

| 定义 | 表达的概念 |
|---|---|
| `StatDefinition` | 属性类型、单位、有效范围、叠加阶段、取整/溢出规则 |
| `TagDefinition` | 明确的机制类别、状态或资格，不依赖中文名猜测 |
| `ModifierDefinition` | 某个来源对属性或技能某个允许字段的贡献 |
| `TriggerDefinition` | 哪种事件、什么条件、以什么频率、产生哪些效果 |
| `EffectDefinition` | 即时/持续/周期效果、数值基准、叠加、驱散和取消策略 |
| `AbilityDefinition` | 现有技能定义的有效视图；不是第二套技能库 |
| `MonsterBehaviorProfile` | 现有行为能力的组合、参数和动作冲突规则 |
| `PresentationCueDefinition` | 表现提示到资源与锚点的映射，不含战斗判定 |
| `ItemExtensionSchema` | 符文、镶嵌等持久化扩展区的版本化结构 |
| `RecipeDefinition` | 原料、前置条件、结果、费用、报价与随机策略 |

保留现有 `monster_id`、`item_id`、技能稳定 ID；不把原有数字 ID 全仓改成字符串。新增机制 ID 使用命名空间。中文名只用于显示与明确的历史迁移，不能成为新正式身份。

开发数据继续沿用当前 JSON/authoring 流程。可以使用 Godot Resource 做编辑器视图或构建产物，但每种定义只能有一个可编辑权威。Godot 资源会共享，不能把单个怪物的 HP、点燃剩余时间、层数写到共享 EffectDefinition 里。[W01]

标签采用来源贡献或引用计数；移除一个来源不能把其他来源仍然授予的免疫/状态一并移除。层级标签匹配在编译期生成索引，不在每次命中时拆分字符串；标签数量也不绑定到单个固定 32/64 位集合。

运行时把定义编译为只读类型化记录；活动状态放入独立实例。仅把 Dictionary 外壳设为只读，不足以证明所有嵌套对象不可变或可跨线程共享。

## 7. 身份、作用域和撤销

### 7.1 不同身份不能混为一个 ID

`ActorRef` 至少区分世界代次、actor 运行 ID 与该 actor 的生命代次，防止死亡后同 ID 复用。物品使用持久化实例 ID；装备来源再包含 slot/扩展实例和机制 ID。

事件与效果至少能够关联：

```text
world_epoch / actor_life_epoch
root_action_id / parent_event_id / event_id
release_id / hit_ordinal
source_actor / credit_owner
source_instance_id / mechanic_id / effect_instance_id
content_revision / loadout_revision
```

这些是逻辑字段，不要求每个事件都创建一个包含所有字段的大 Dictionary。热点采用固定结构、紧凑 ID 或复用缓冲；详细字符串仅在定义和诊断层保留。

### 7.2 一个状态一个写入者

| 状态 | 写入者 |
|---|---|
| HP、资源扣除、受击与死亡资格 | 当前战斗/actor 权威，逐步封装端口但不增加第二份 HP |
| 实际位移、接触恢复、空间索引更新 | 当前运动与空间权威 |
| 属性贡献和已编译装配 | PlayerState/actor 属性权威在事务边界发布 |
| 新持续效果实例 | 活动效果运行时；旧毒/旧 buff 迁移前仍由原实现唯一推进 |
| 背包、镶嵌、符文、金币 | 当前物品状态权威，通过事务入口修改 |
| 文件事务与回执 | 当前有序持久化服务 |
| 画面和 HUD | 表现适配器读取提交结果，不能改战斗状态 |

### 7.3 卸下装备不等于抹掉已经释放的伤害

装备移除必须撤销其后续属性贡献和新触发资格。已经接受的攻击、投射物和持续伤害默认消费接受时锁定的定义与数值快照；不能因后来卸装把半空中的攻击变成另一套数据。

持续光环等确实依赖装备仍存在的机制，明确声明 `while_source_bound`；自主持续到期的燃烧声明 `until_expired`。击杀归属与施法者节点存活分开，不靠强引用把死亡/换图 actor 永久留在内存。

内部冷却的生命周期单独声明。新装备触发默认不能通过卸装再装备刷新冷却；保存或保留其来源级截止记录，按该机制的时间域到期。不要把冷却状态随临时表现节点一起销毁。

## 8. 装配编译：可扩展但不让词缀进入每帧大循环

### 8.1 共同贡献入口

装备固有属性、随机词缀、锻造、宝石、符文、套装、角色增益和怪物特性，都提供标准化的三类贡献：属性修饰、技能修饰、触发订阅。相同机制在宝石和装备上复用定义，但各自有独立来源句柄。

装配编译器完成解析、合法性验证、叠加、依赖排序和订阅索引。它不构建一次攻击的 release snapshot，不消耗战斗 RNG，不扣 MP，因此不是第二个技能 planner。

### 8.2 编译时机

只在影响机制的版本变化时编译：装备更换、宝石/符文变化、技能等级变化、相关状态变化、内容目录切换。纯耐久数字变化不应无条件重建全部机制；如果耐久到零会改变装备生效资格，则在跨越该边界时失效相应缓存。

编译产物必须原子发布，不能先更新伤害、下一帧才更新触发规则。需要异步准备的装配，在完成之前旧的有效装配继续有效，或者对应物品操作保持明确的 pending；绝不把半份新配置暴露给战斗。

### 8.3 运行期快路

一次烈火命中直接读取已经筛选的“该 actor、该技能、该事件”的订阅切片，再检查活的目标条件、内部冷却和概率。它不扫描背包、全词缀表或全部模块。

形式上应接近：

```text
本次事件处理成本 ≈ 本次实际匹配的订阅数 + 实际产生命令数
```

而不是“全项目词缀数 × 每次命中数”。这是一项待测试证明的设计目标，不是本次测出的性能结果。新增未装备、未激活内容仍会影响构建和加载容量，但不应为每击增加扫描。

### 8.4 属性叠加规则

每种属性声明自己的聚合方式。等级、攻击区间、移动速度、攻速档位、命中、抗性不能统一套一个乘法。

对于允许的新增连续属性，可以提供“基础值 + 固定贡献 → 同组百分比相加 → 独立乘区 → 限幅与取整”的通用算子。现有属性先调用旧计算器保留精确规则，不在迁移时自动改变旧顺序、负数或取整语义。

属性依赖关系要检查循环；不允许“最终攻击依赖最终攻击”这类无定义递归。最大 HP/MP 变化对当前资源的影响由独立策略声明，不能自动获得免费回血；旧资源调整规则由适配器原样保留，新策略通过单独测试。

贡献按来源记录，移除来源后重新求该属性的有效值，不能通过“减回旧加值、除回旧倍率”来处理交叠 buff。常态只保留计算所需数据；完整来源解释按需生成，用于解释面板和调试。

## 9. 技能扩展仍经过唯一计划

现有入口保留为 `SkillRuntimeRouter.build_canonical_plan()`。[E06] 需要增加的是该入口内部的“有效定义”接入：基础技能定义加上当前装配允许的修饰，形成一次动作所使用的版本。

有效定义必须被前置目标验证、资源报价、冷却计算、效果计算、几何构建和表现依赖共同消费。不能只有最终伤害采用新配置，而 MP 仍按旧配置扣除；也不能在 `_plan()` 与 contract 包装阶段重新读取不同版本的裸定义。

装配/数值在既定动作接受边界锁定；位置、方向、目标快照在现有规则规定的释放边界锁定。不能为方便把所有技能都提前锁死目标，改变已有追踪语义。

允许的技能修饰端口包括等级贡献、明确标注的数值字段、范围修饰、状态附加、投射物修饰与能力授予。改变投递模型，例如“单体射弹变成地面范围”，必须声明互斥替换能力，经过几何、资源、伤害与表现全链验证；不是随意覆盖一个字符串。

通用定义新增合法字段以后，由它生成现有分类消费者的只读视图。不要继续由多个文件手工维护同一技能的分类名单。但每个名单表达的维度必须区分：几何类别、伤害通道、来源反应家族不是同一个分类。

来源 1.76 的基础技能分类保持其冻结基线校验；新增技能/子效果通过带版本的扩展描述注册。有效分类可以组合生成，但不能为了容纳新 ID 而让未知来源默认变成 DIRECT，也不能让所有周期子事件冒充一个玩家主技能。

扩展包不得自己扣蓝后再调用现有技能流程；不得绕过唯一入口直接实例化“有伤害的视觉特效”。

## 10. 战斗事件与命令：可组合而不形成回调风暴

### 10.1 分清“接触”“造成伤害”“击杀”

至少区分动作接受、命中判定完成、伤害提交、状态施加和击杀归属确认。触发条件必须说明使用哪个事件。

伤害结果记录按需要提供原始值、减免后值、被护盾/MP 吸收值、实际 HP 损失、过量伤害和本次是否首次造成死亡。吸血通常消费实际有效损失还是其他基准，由机制声明，不能默认拿原始伤害发奖。

0 伤害、被闪避、被免疫与非法请求必须可区分。新持续伤害不得误入把所有输入提升为至少 1 点伤害的通用兼容函数。

### 10.2 两种扩展检查点

**前置修饰检查点**：纯计算，修改被允许的字段；不能写 HP、发 UI 信号或递归启动技能。多个修饰按固定阶段和稳定次序组合。

**提交后反应检查点**：读取已确认结果，产出命令，例如施加状态、治疗、请求合法子攻击。命令交给领域权威执行；不能让一个 handler 直接调用另一个 handler。

初次接入保持原攻击与多目标遍历顺序不变。新增的反应命令放在明确的“本次基础释放完成后”检查点处理，避免燃烧/爆炸插入一半时改变该次基础 AOE 后续目标。不能为了新框架提前执行旧死亡清理；原先保护多目标释放的 death-pending 边界必须保留。

这里“基础释放完成”指一次同步基础目标批次结束；单个投射物命中拥有自己的命中批次，不等待整个技能所有投射物、动画或磁盘事务结束。新检查点保持与当前命中同一合法模拟步，不额外制造任意一帧或一段动画的延迟。

基础伤害已经提交后，新增状态应用失败不回滚已发生的基础命中，也不能把失败伪装成成功。测试与内容校验应消除合法内容下的容量/配置失败；运行时意外拒绝必须有独立原因与诊断。

### 10.3 允许的命令族

`ApplyStatus`、`RemoveStatus`、`ModifyResource`、`RequestChildAction`、`RequestDisplacement`、`RequestSummon`、`EmitPresentationCue`。每族只调用已有或明确新增的领域端口。位移仍通过碰撞和索引更新；召唤仍通过正式生成配额；子攻击仍经过合法准入，不是任意再扣一次血。

权威机制不能把持久化、日志写文件或纹理加载藏在命令处理器里。需要经济结果的事件提交给经济事务域，而不是在伤害调用栈里保存整个角色。

### 10.4 重入和执行顺序

同一处理器执行中新增命令进入本次受控缓冲，不通过同步信号再次进入 combat 根入口。缓冲以广度优先的明确层级处理，保留 root/parent 身份和稳定次序；旧玩法的随机流和顺序不因无扩展接入而改变。

权威事件与表现通知分开：前者不能合并丢失，后者只有声明可合并的种类才能合并。合法同步命令是否必须本步完成，由事件契约规定，不以“队列都是下一帧”一刀切。

## 11. 触发链、概率与容量

### 11.1 防止点燃—爆炸—点燃无限递归

每个触发声明允许的来源类别：直接命中、持续伤害、反射、触发产生的子攻击等。默认的“烈火命中点燃”仅接受直接的烈火基础命中，不接收自身燃烧 tick，也不接收其子事件。

触发声明 `per_hit`、`per_target_per_release`、`per_release`、`per_status_tick` 等去重粒度。一次范围攻击击中十只怪能触发几次，不由代码作者临时决定。

编译时检测依赖环和可生成事件的上界。时间型循环必须包含明确、受约束的周期与终止条件；零时间的自激循环不能通过。深度、扇出及状态上限属于机制契约，不能在运行时悄悄截断本来承诺无限的效果。

运行时仍保留 root 内去重、每层命令上界和重复事件检测，防止实现错误。越界是故障，不是可以长期接受的“为了帧率少算几个怪”。

### 11.2 随机流

旧攻击、掉落、锻造的 RNG 规则先原样保留。新触发使用独立、算法版本固定的随机域，以稳定动作/来源/目标/命中序号标识抽签位置；不能从旧技能 RNG 随手多取一次数。

同样的输入、种子、内容和装配应产生相同的新触发结果。未装备词缀不抽签；非法请求在 RNG 之前拒绝。重试事务不能重抽已经确定的结果。

AOE 系数、内部冷却与触发概率是公开的玩法参数，只对声明采用它们的新内容生效；不能借框架迁移暗中降低旧技能收益。

### 11.3 容量不是随意的隐藏上限

每个根动作在准入时验证新机制所需容量；需要预留的命令缓冲、状态槽和生成配额应在可拒绝的边界明确预留。已接受的必要结果不能因为装饰特效挤占了内存就消失。

不能承诺任意多条合法机制、任意多怪、任意大的连锁都保持固定性能。发布时需要验证最大允许组合；超过容量应在内容构建、装备组合或动作准入边界被显式处理，而不是伤害算到一半停止。

## 12. 持续效果运行时

新增燃烧、流血、减速、诅咒等共用活动效果容器和到期调度。它们不各自创建 `_process()` 节点，也不各自扫描怪物。

每个 `EffectDefinition` 必须明确：作用目标、施加条件、伤害/治疗算子、时间域、周期、到期顺序、叠层键、层数策略、刷新策略、强弱替换、驱散类别、免疫类别、来源撤销策略、击杀归属和持久化规则。

推荐先使用到期堆或其他有界到期结构，只访问当前到期项。具体结构以测量决定。相同数值但不同来源、到期时间或归属的效果不能为了减少条数任意合并。

默认给新燃烧采用模拟时间，暂停冻结；现有火墙的真实寿命保持不变。[E15] 不把“统一管理”误解为“统一修改全部时间语义”。

周期过载不能用大 delta 瞬间补算所有历史 tick，也不能无声跳掉。新效果通过固定模拟推进与最大合法并发进行容量验证；暂停不计模拟欠账。异常卡顿后的补步行为先沿用引擎/当前模拟策略，记录模拟时间与墙钟差异；任何改变补算规则的方案单独立项。

旧毒与旧 buff 初期只经适配器提供只读状态与标准结果，不让新 manager 和旧计时器同时推进。每类迁移必须一次移交状态所有权，不能“双跑再比对”造成双重伤害。差分比较使用影子纯计算，不提交第二次结果。

## 13. 垂直验收样例：烈火命中后点燃

这是框架验收样例，不是已经获批的正式数值和平衡改动。正式开关默认关闭；测试使用明确 fixture。

### 13.1 路径

```text
装备/符文给出“烈火命中附加燃烧”贡献
→ 装配编译为 warrior.fire_sword 的直接命中订阅
→ 现有烈火基础攻击按原规则准入、计算与提交
→ 基础释放完成，收到已确认的伤害结果
→ 检查目标仍活着、HP 损失条件、免疫和去重
→ 在新触发随机域判断概率
→ ApplyStatus(hc.effect.ignite.v1)
→ 活动效果容器登记实例和到期计划
→ 到期通过共同伤害端口处理燃烧
→ 发布燃烧表现提示与状态图标
```

### 13.2 必须钉住的语义

烈火基础投递保留 PHYSICAL；燃烧子事件声明自己的周期伤害语义，不能冒充 DIRECT 或 MINE。元素标签、减伤通道、来源消息家族、是否造成受击停顿是四个维度。初版新增燃烧建议不制造普通命中硬直、不触发直接魔法的下一步移动延迟；这只适用于新机制，不改变旧毒/火墙规则。[E08]

攻击方数值来源在被接受的触发事件中锁定，不能每跳回头读取已经换掉的武器。目标免疫与减伤在每跳执行时重新检查，前提是该效果明确选择这种规则。基础数值取“减伤前技能力量”还是“实际 HP 损失”是定义字段，不能在实现时混用。

已经死亡的目标不新增燃烧；燃烧致死通过原死亡/奖励权威结算一次；旧节点释放不能丢失击杀归属。战斗事件不由特效节点的播放结束触发。

同一来源反复点燃的测试策略：不加层，保留较强的锁定强度，刷新到期时间，不把 next_tick 提前成立即 tick。不同来源是否独立叠加由正式效果定义明确声明，不能只用 effect_id 覆盖别人。

### 13.3 确定性测试夹具

无防御、无免疫，触发概率固定 100%；已确认基础命中 HP 损失 100；示例规则选择该损失的 5% 为每跳原始伤害、周期 1000ms、持续 4000ms。应在施加后第 1/2/3/4 秒各产生 5 点燃烧伤害，最后一跳先执行再到期，总计 20 点。这里的“100%、5%、4秒”只为测试接口，不是正式平衡决定。

有防御/吸收/免疫的独立夹具应验证各字段的真实变化，不能仍固定期望 20。刷新时沿用原有 next_tick 相位，以新到期时间决定以后哪些 tick 有效；暂停 2 秒不能替模拟燃烧走掉 2 秒。

至少测试：未命中不触发、0 HP 损失策略、目标免疫、同帧重复投递、AOE 多目标、卸装、来源死亡、换图、强弱刷新、最后一跳到期、燃烧致死、防递归与特效缺失。

## 14. 装备、符文、镶嵌与套装

### 14.1 一套贡献协议

宝石不直接修改玩家攻击力；它把贡献提供给装配编译器。符文不直接改 `enemy.gd`；它提供技能修饰或触发定义。套装聚合满足条件的来源后，同样产出贡献。

镶嵌和符文仍是独立业务模块：开孔规则、可镶嵌类别、顺序规则、拆卸消耗、配方与界面不塞进属性系统。是否做符文之语、多少孔、失败率和费用，本设计不替用户作平衡决策。

### 14.2 共同事务端口

所有涉及金币、材料、目标装备和嵌入物的操作，遵循：

```text
只读报价
→ 核对角色、物品 ID、相关版本与规则版本
→ 预留相关物品/槽位/数量
→ 生成一次性的确定结果与 operation_id
→ 通过既有有序持久化执行器处理
→ 在安全提交边界原子应用相关状态
→ 发布结果与装配失效标记
```

不能把报价使用的背包索引当成永久身份；提交必须核对实例 ID 与版本。预留只锁相关输入，不冻结整个战斗世界。相同 operation_id 的重试返回原结果，不重抽概率、不重复消耗。

新贵重物品交易建议在持久化回执确认后开放结果物品继续交易。界面可显示 pending，不能阻塞主线程等磁盘。当前已经存在的药剂即时生效与锻造后台保存语义不因这个建议被一律替换；迁移时各自声明 `applied_in_memory` 与 `durable` 的区别。[E05、E13]

如果其他状态在后台写入期间变化，不能用旧的整份角色快照覆盖新变化。沿用唯一写入顺序、身份/版本检查和明确的重建/冲突处理；不要让模块自己用“失败回滚旧副本”覆盖期间产生的新战斗收益。

### 14.3 插槽内物品的唯一归属

宝石从背包进入装备后，只能有一个合法归属。存档里的嵌入记录必须携带其稳定身份与必要数据；它不能同时作为一件可用背包物品存在。

取出、装备出售、仓库转移、分解、角色删除与导入恢复必须调用同一归属规则。堆叠材料记录消耗数量和事务结果；不可堆叠的宝石/符文记录实例身份。禁止用 UI 隐藏重复物品来掩盖数据重复。

### 14.4 物品扩展 schema

已确认旧实例拒绝未登记顶层字段。[E04] 因此：旧 v1 数据仍走原严格验证器；需要扩展的物品进入明确的新容器/schema，保留原身份、原掉落规则版本与已生成词缀，扩展挂入有命名空间的 `extensions`。

扩展区形状示例（不是完整物品记录）：

```json
{
  "extensions": {
    "hc.socketing": {"schema_version": 1, "sockets": []},
    "hc.runes": {"schema_version": 1, "bindings": []}
  }
}
```

每个扩展区有注册校验器、迁移器与容量约束。新容器由正式 codec 路由，不让旧 v1 校验器突然接受任意未知字段。历史掉落的确定性验证仍使用其原始规则；新规则发布不重新洗掉玩家已经获得的词缀。

必须同时处理保存、加载、备份恢复、仓库、掉落、复制、出售、物品提示和锻造消费者，不是只改一个保存函数。

## 15. 新怪物与 Boss 的扩展端口

新增怪物分成身份与属性、行为组合、攻击能力、表现资源、刷新与掉落五部分。每部分用现有权威数据连接，不能在地图上塞一份独立怪物属性。

行为插件产出“动作意图”：追击、返程、普通攻击、施法、召唤、特殊动作。动作仲裁仍由当前 actor 行动门控制，保持同 tick 的准入、身体动作占用、硬直和死亡边界；不能让近战 AI、施法插件和 Boss 插件各自都认为自己能起手。

普通变体复用行为 profile；真正新行为增加一个受约束的行为能力。新 Boss 的子技能仍进入共同的攻击/效果/资源端口，不自己扫描全组或直接扣玩家血。

大体型怪物声明真实碰撞与导航规格。缺少匹配导航数据应在内容验证时拒绝，不能为了加载成功借用小怪半径。正式地图发布不因新增怪物而默认全量重建；只处理受影响目标和合法 profile。

怪物与玩家可以共享伤害、状态、标签和表现协议，但不强迫共用同一 AI 或同一套动作节奏。第一批只迁移一类普通怪和一个明确的小型特性，验证后扩展；不一次重写全部特殊 Boss。

## 16. 表现、资源和 UI 也要可插接

### 16.1 表现提示协议

机制发布例如 `ignite.applied`、`ignite.refreshed`、`ignite.removed` 的提示，并携带当前有效目标身份、锚点和表现参数。资源映射决定具体火焰、音效与图标。

持续表现以 effect_instance_id 管理 start/update/stop，刷新不重复叠出多个节点；目标死亡/换图/池对象复用必须让旧提示失效。逻辑多个来源可保留多个伤害实例，视觉在明示聚合策略下只显示一个燃烧外观。

### 16.2 可读性等级

危险范围预警、投射物可见性、攻击起手属于必要战斗可读性，不能当作普通装饰丢掉。重复火星、非必要尾迹等才可在授权策略下合并或降低密度。任何视觉降级不得改变命中几何、伤害与危险范围的可辨识性。

不授权本轮顺手降低现有贴图精度、改变已确认的图标/黄圈/视角或换渲染器。

### 16.3 资源依赖闭包

装配或新地图发布前，计算可能触发到的效果、子效果、声音、图标和关键表现资源的依赖闭包。不是只预热按钮上的主技能，漏掉“第一次触发点燃/爆炸”资源。

复用现有 streaming、pin/lease、异步请求与缓存。共享预算覆盖准备、加载就绪后的验证/应用和释放；内存统计包括被实例持有、加载中与就绪待应用资源。

新能力的关键表现尚未准备好时，在能力/装配的准入阶段处理准备状态；不能先接受攻击，再为了纹理加载改变已锁定的伤害时间。旧能力的冷/热一致性合同保持不动。

工程当前配置为 `gl_compatibility`。[E17] 资源加载完不等于首次绘制成本为零；预热必须按实际渲染器验证，不能照搬仅适用于其他后端的方案。[W04]

### 16.4 UI 模块

镶嵌/符文界面通过视图模型读取状态，通过命令入口提交操作。面板隐藏时停止无需求更新；profile/inventory 等变化聚合为具体视图脏标记，不让每个新面板同步挂在每次战斗提交后刷新。[E14]

词条说明来自同一注册定义与格式化规则，不在面板再复制一套伤害公式。详细“数值从哪来”按需生成，不在每帧构建整份说明。

## 17. 稳定运行核心：扩展不得绕过预算

继续采用上一版的世界执行协调、帧内预算账本、明确时间域和表现提交边界，而不是给每个模块各分一份独立的 1ms。

### 17.1 三种成本约束

**玩法规模约束**：一个动作最多产生多少子事件、目标按哪种规则确定、状态如何叠加、能召唤多少实体。它们是公开机制合同，必须在组合验证中成立。

**执行量子约束**：路径推进、资源应用、索引/缓存维护、事务准备等可分步工作必须有游标或足够小的原子步骤。预算检查必须进入内部的大步骤；外面有 deadline 不代表内部重建可抢占。[E10–E13]

**全局竞争约束**：多个模块共用主线程、后台并发与资源内存能力。不能每个模块单独满足上限，合起来却持续超载。

### 17.2 帧内账本

同一主循环帧内，物理回调、process、deferred 入口只能领取剩余额度；一次主循环内多个物理步也不能让可延后任务反复获得完整新额度。具体引擎帧号与回调顺序由微型测试锁定，不能假设。

嵌套调用只计费一次，同时保留 inclusive/self 诊断。后台任务准备、完成验证、应用与同步回调全部列入账本。预算时钟独立于可关闭的详细诊断开关。

预算是软约束，不能抢占已经执行的 GDScript 长函数。处理器必须限制内部循环并接受实测；仅声明自己是“轻量插件”没有意义。

### 17.3 不牺牲及时性

已接受的必要攻击、实际碰撞、伤害与死亡资格不因维护预算耗尽而丢失。允许延后的路径重算、资源应用和维护任务必须记录最老年龄；不能用“每次只算一点”把 60 FPS 换成怪物迟钝。

持续效果只检查到期实例，不是每帧调用所有词缀。未激活模块只有必要的已加载定义占用，不应新增逐帧工作。静态标签匹配、订阅排序、资源依赖解析和校验尽量在装配/构建期完成。

重型必要计算超过设备承载时，必须优化算法、数据布局或内容组合，不得悄悄少伤害、缩减命中目标或把可躲避投射物变成必中特效。

### 17.4 后台计算边界

保留当前 JSON worker；新并行仅用于测量证明足够重且可隔离的纯计算。活动场景树不允许任意跨线程操作；官方也提醒轻任务线程化可能变慢。[W02、W03]

worker 输入为必要的独立数据，不是完整 live 世界、Node、PlayerState 或 UI；地图只读外壳里的可变共享缓存同样不允许并发乱写。结果携带领域身份，主线程应用时复核。

日常帧先确认任务已完成，再执行必要的 join/清理，不能每帧阻塞等所有 worker；但也不能永不回收任务。退出与真正的安全屏障有单独收尾策略。[W03]

## 18. 存档、版本和卸载兼容

### 18.1 保存什么

保存角色/物品的长期状态、物品实例身份、扩展数据、已经抽出的词缀与随机结果、必要的冷却/状态信息、规则与 schema 版本。已编译属性、命中候选、寻路任务和表现节点不作为新持久化权威。

能重建的缓存不存。历史掉落必须保留其生成版本与验证依据，不把当前最新版随机生成器拿来验证所有老物品。[E04]

### 18.2 三类时间分别序列化

模拟时长保存剩余量或明确的模拟状态；真实到期保存符合该机制合同的截止信息；离线刷新采用当前持久化时间规则。不能保存进程相对 ticks 并假装它在应用重启后仍有效。

是否允许某种燃烧跨退出继续结算，是独立的机制选择。本版默认的新战斗燃烧随世界会话结束清理，不在离线期间偷偷追加伤害。已有世界刷新和火墙规则不由此改写。

### 18.3 未知或缺失模块

纯表现映射缺失可以使用预先验证的兼容表现，但不能让危险攻击完全不可见。影响物品经济与战斗的扩展版本未知时，不能将未知字段清空后自动保存，也不能随便给默认值继续使用。

默认策略：保留原文件和未知载荷，阻止会破坏数据的写入，显示具体不兼容原因；需要继续游戏的降级/隔离模式必须单独定义并测试。不能把“保留字节”说成“能够安全执行未知机制”。

### 18.4 老 APK 与新扩展

旧 APK 通常不知道新物品 schema；本设计不能承诺未经测试的新→旧→新往返。发布新持久化格式前，必须提供备份、明确迁移入口与兼容测试。功能代码可回滚不等于存档可逆；需要新版本持久化状态的阶段不能仅靠一个 feature flag 无损回退。

### 18.5 事务状态必须如实

接口区分拒绝、pending、已在内存应用、已持久化及失败/恢复中。不能因为任务成功入队就宣称“保存成功”。已进入不可取消提交的回执必须消费；map epoch 变化不是丢弃角色或仓库回执的理由。[E13]

## 19. 最小端口集合与文件映射

以下是**拟议接口职责**，不是当前仓库已定义的 API。采用类型化值和只读视图；具体实现语言可为 GDScript 的明确类/组合，不依赖尚未验证的引擎新语法。

| 端口 | 输入 → 输出 | 不允许的副作用 |
|---|---|---|
| `ContributionProvider.collect(source, catalog)` | 来源快照 → 属性/技能/触发贡献 | 不改玩家数值、不写文件 |
| `LoadoutCompiler.compile(contributions, base_revision)` | 已验证贡献 → 不可变装配 | 不扣资源、不构建 release |
| `MechanicHandler.evaluate(event_view, binding, command_writer)` | 只读事件与绑定 → 有界命令 | 不直接改 Node/HP，不加载资源 |
| `SpatialQueryPort.query_envelope/query_sweep` | 明确 map/epoch、Ground GU 几何 → 当前合法候选/快照 | 不全组扫描，不建立第二份战斗空间索引 |
| `EffectRuntime.apply(request)` | 已验证效果请求 → 实例句柄/拒绝原因 | 不重复建立旧状态计时器 |
| `CombatPort.submit(command)` | 合法战斗命令 → 权威结果 | 不复制一份战斗真相 |
| `ItemTransactionPort.quote/commit` | 明确输入身份和版本 → 报价/事务回执 | 不允许模块自己并行改背包和文件 |
| `PresentationPort.publish(cue)` | 已提交结果 → 有界表现更新 | 不决定命中、伤害或资源扣除 |
| `ResourcePort.request/lease/release` | 资源需求与有效身份 → 资源状态/租约 | 不绕开已有缓存新建同义缓存 |
| `SchemaPort.validate/migrate` | 指定版本载荷 → 已验证载荷或失败 | 不修改原文件、不丢未知字段 |
| `WorkBudgetPort.try_begin/finish` | 任务类别与量子 → 本帧许可/计量 | 不推进玩法时间、不截断必要伤害 |

### 19.1 建议目录

保留上一版 `scripts/layers/runtime/execution/` 五项职责：世界协调、帧预算、世界上下文、时间域与表现提交。

新增少数实际使用的文件族：

```text
scripts/features/contracts/       定义、事件、命令、来源与 schema 契约
scripts/features/compilation/     依赖解析、内容编译、装配编译、触发表
scripts/features/runtime/        受约束分发与新活动效果运行时
scripts/features/adapters/       现有战斗/属性/事务/表现的单向适配
scripts/features/ignite/         第一个纵向验收模块（默认关闭）
assets/data/features/            受版本管理的新增定义与模块清单
```

符文、镶嵌目录在对应模块立项时创建，不先写一堆空管理器。允许按职责拆文件，但不为追求“每个文件很短”把一个原子事务拆成多层跨调用状态。

### 19.2 与现有文件的对接

| 现有位置 | 拟议变化 | 保留内容 |
|---|---|---|
| `content_layer_registry.gd` | 增加候选编译与依赖/冲突验证入口 | 五层、现有基础数据权威 |
| `equipment_rules.gd`、PlayerState 的装配汇总 | 提供标准贡献并发布装配版本 | 现有属性语义与技能等级权限 |
| `skill_runtime_router.gd` | 内部统一消费有效定义 | 唯一正式 planner 入口 |
| `skill_execution_plan_contract.gd` | 由有效定义导出分类与能力需求 | 原资源、快照及坐标合同 |
| `combat_runtime_service.gd` | 明确扩展检查点与新命令适配 | 当前伤害、受击与 RNG 规则 |
| `enemy.gd`、`player.gd` | 渐进暴露领域端口，减少新增硬编码 | 状态唯一归属、实际移动及动作顺序 |
| `item_drop_instance_rules.gd` | 增加版本路由/新容器适配 | 旧规则严格校验、实例 ID、已抽词缀 |
| `equipment_enhancement_service.gd` | 逐步通过共同事务端口 | 已确认报价、概率及用户流程 |
| `json_persistence_service/job.gd` | 增补阶段计量与回执适配 | 有序写入、备份、验证、恢复 |
| 现有 streaming / UI texture / HUD | 资源需求与表现端口接入 | 唯一缓存、租约、用户确认美术 |
| 地图发布与空间查询 | 只提供正式上下文和能力 | 人工地图、精确碰撞、发布 hash |

分发器复用事件/命令缓冲时，处理器不能把短生命周期视图保留到下一帧；异步请求只捕获必要的独立字段与身份。对象池复用必须更新代次，不能让旧命令作用到复用后的新实例。

迁移适配器不是永久允许两套执行器同时运行。每个功能在同一时刻只有旧路径或新路径拥有副作用权；影子验证仅输出比较结果。

## 20. 测试体系：成熟框架必须证明组合没有失控

### 20.1 四层测试

**定义与纯规则**：依赖环、未知标签/属性/算子、ID 冲突、字段类型、非法数值、取整、作用域、资源缺失、非终止触发图。

**生产适配器与状态边界**：必须走真实动作、命中、物品、持久化和生命周期入口；不能只测试纯函数或同步测试 helper。

**组合与生成式测试**：合法的装备/状态/技能组合进行可重复随机测试、关键两两组合与重点高阶组合；这不能证明所有组合绝对正确，但能补单模块测试的盲区。

**设备性能与长时间测试**：固定源码、内容与输入，对比冷/热资源、群怪、连锁、掉落、存档及 UI；无 GPU 指标时明确未知。

### 20.2 必须加入的验收场景

| 场景 | 必须证明 |
|---|---|
| 关闭所有新功能包 | 旧伤害、RNG、动作顺序、掉落和存档不变；空扩展快路不扫描注册表 |
| 增加大量未装备词缀定义 | 每击订阅检查数量不随全库词缀数增长 |
| 词缀 + 宝石 + 符文都提供同一机制 | 按声明聚合或分别触发；来源不混淆，移除任一来源不误删其余贡献 |
| 烈火 + 点燃 + 吸血 | 基准字段、伤害归属与吸血触发粒度正确；DOT 不误触发直接命中链 |
| 点燃 + 死亡爆炸 + 再点燃 | 不递归自激；子事件有来源、深度与容量验证 |
| AOE 同时击杀多个目标 | 每个死亡与奖励只提交一次；不因插件执行提前清掉后续基础目标 |
| 卸装、重装、快速切换 | 已接受攻击快照不变；新触发资格及时改变；不能刷内部冷却 |
| 暂停、变速、后台恢复 | 各时间域保持原语义；新燃烧不凭墙钟补一堆伤害 |
| 角色死亡与同 ID 重生 | 旧效果、旧路径和旧表现不能命中新生命 |
| 镶嵌时双击/切页/仓库并发操作 | 不重复消耗、复制宝石或覆盖无关状态 |
| 保存失败、回执晚到、进程重启 | 结果不重抽、物品只有一份、备份可恢复、不吞未知扩展 |
| 启用/停用包与缺失依赖 | 只在安全边界切换；当前有效目录不被半加载候选破坏 |
| 冷资源首次触发 | 不在命中回调里同步读纹理；必要表现可读，冷/热伤害时间一致 |
| 大量路径/资源/存档同帧完成 | 共用剩余预算；单个大步骤不能绕过量子控制 |
| 0 个实际检查的测试、故意坏断言 | runner 必须拒绝假 PASS；不是只看打印文本 |

### 20.3 规模与指标

建议把“30 怪 + 持续 AOE + 同时三类持续状态”作为新增组合压力夹具，意味着最多 90 个活动状态用于验证；这只是测试规模，不是当前性能实测，也不是新的玩法上限。另测“30 怪同 tick 状态到期与死亡、掉落、存档结果及资源完成一起发生”。

指标：真实帧间隔 P50/P95/P99；超过 33.33/50/100ms 的帧；最长连续慢帧；必要动作延迟；路径/结算/资源最老等待；匹配订阅数；子事件数；最大量子；活动状态/资源占用；持续热机表现。

静态/计数门槛先固定为：新增热路径同步 I/O 为 0；纯机制直接写非本域状态为 0；未激活扩展逐帧回调为 0；同一逻辑双驱动为 0；重复经济提交和重复死亡归属为 0；非法来源/未知 schema 不得隐式通过。

毫秒、内存、任务等待的设备档位门槛在 P0 用真实基线冻结，然后再开始性能变更。这里不能虚构“每次插件只花 0.02ms”或承诺全部手机 60 FPS。高 FPS 但奖励/怪物/输入明显迟缓，同样失败。

新增测试必须接现有正式 runner，保留隔离用户数据和失败分类。把已知失败列成债务不等于允许它遮住新的失败。

## 21. 分阶段实施：总设计完整，迁移不一次推倒

下表是实施路线与验收边界，不是已经执行的施工记录，也不是可以跳过详细任务计划直接全量改写的授权。

| 阶段 | 交付 | 通过门槛 |
|---|---|---|
| P0 证据与接口基线 | 固定版本/内容/引擎，重跑相关基线，捕获原调用顺序与随机结果，确定设备预算 | 假 PASS 检测有效；旧失败逐项对照；生产路径被覆盖 |
| P1 稳定执行底座 | 接入共享帧预算、量子计量、生命周期/时间域类型；先改现有可延后工作 | 旧行为不变；同帧多入口不重领预算；等待没有变成新问题 |
| P2 定义与装配编译 | 现有内容入口增加编译；标准贡献、稳定 ID、冲突检测；先接一个纯数值词缀 | 关闭扩展零行为差异；属性来源/卸装/技能等级全部正确 |
| P3 触发与效果纵向切片 | 命中结果检查点、受约束命令、新状态运行时、烈火点燃测试包 | 直接命中/周期分类正确，冷/热/暂停/换装/致死/连锁/资源全过程通过 |
| P4 旧能力渐进接入 | 逐类迁移相关被动/状态及选定怪物能力；一次只移交一个副作用所有者 | 无双计时、双扣血、顺序/RNG 变化；每类有差分与组合验收 |
| P5 经济扩展接入 | 新物品扩展 schema、迁移与事务端口；用一个测试宝石验证镶嵌取出 | 身份、所有权、备份、失败恢复和未知版本安全；不自动上线正式符文/概率 |
| P6 发布能力与耐久验证 | 包依赖/资源闭包/组合成本门禁，真机压力与持续运行，编写新增功能模板 | 功能正确与时效/帧时间同时达标，才按独立开关发布 |

P1 和 P2 不是竞争方案：P1 治理当下成本，P2 提供以后内容接入边界。P3 必须做真实纵向样例，不能只有一堆接口没有生产消费者。

每阶段保留独立提交、证据和可回退开关。只要涉及持久化格式变化，回滚必须依据迁移策略，不能假设关闭插件就能回到旧 APK。主树、人工地图和用户存档在当前设计阶段不修改。

## 22. 以后新增一个功能的标准交付包

以后无论增加词缀、装备、符文或新怪物，交付都应回答这些问题：

1. 它使用哪个稳定 ID、哪些已有能力，是否真的需要新增原语？
2. 读取什么状态，谁拥有写入，在哪个检查点执行？
3. 数值如何组合，概率/RNG 如何独立，来源如何撤销？
4. 是否可递归触发，最大目标、命令、状态和资源成本是什么？
5. 暂停、死亡、卸装、换图、重复投递和失败时分别怎样处理？
6. 资源如何提前准备，必要战斗表现怎样保证？
7. 新状态如何保存/迁移，旧存档与未知模块如何保护？
8. 哪些生产组合和性能测试证明它不会拖累已有系统？

其中已有原语能够表达的常规新增，目标是：增加定义、资源清单和测试，而不修改核心大脚本。无法表达的能力扩展一个明确端口或原语，不用临时绕过框架。

## 23. 完成定义与本次结论

这次交付的是覆盖“内容生产—组合编译—战斗执行—经济事务—表现资源—持久化—性能—验证”的完整总体设计，不是一个已经跑过真机的成熟成品。

框架完成的判断不是 Manager 数量、设计模式名称或代码行数。必须能够实际完成以下纵向验证：同一燃烧机制既能由词缀也能由符文授予；卸掉一个来源不误删其他来源；点燃与既有攻击/毒/火墙不会混淆时序；镶嵌可保存恢复且不复制物品；新增怪物能复用能力又保持独立行动规则；复杂场景的帧时间与业务延迟同时受控。

**推荐正式路线：保留现有业务权威，建立少而明确的扩展端口；把常规扩展编译为数据，把复杂行为约束为小处理器，把系统级扩展约束为事务模块；所有新增能力共同遵守执行预算、生命周期和组合验收。**

不承诺以后没有 bug，也不承诺所有未知玩法永远不改核心。目标是让大部分新增不再散落修改多个核心文件；确实要改核心时，有明确版本边界和能识别连带影响的证据。

## 附录 B：公开技术参考

本次查阅仅用引擎/平台的一手文档。外部参考解释设计取舍，不证明本项目实际帧耗时，也不表示要引入另一引擎。

- **W01 — Godot Resources**：资源与节点的区别、自定义资源、共享加载与序列化。支持把定义与实例状态分开，不要求替换现有 JSON 权威。
- **W02 — Godot Thread-safe APIs**：活动场景树、共享资源与线程访问限制。支持主线程领域提交和独立 worker 输入边界。
- **W03 — Godot WorkerThreadPool**：小任务可能负收益；wait 会暂停调用线程；任务需要完成收尾。支持按实测选择并行，而非全部插件线程化。
- **W04 — Godot Reducing stutter from shader (pipeline) compilations**：预热与渲染后端有关。用于限制预热建议适用范围，不据此直接诊断当前火墙问题。
- **W05 — Epic Understanding the Gameplay Ability System**：可参考“能力、属性、效果、标签、表现”分工；不复制网络预测/复制层，不把 Unreal GAS 嵌入 Godot。

## 附录 C：边界核对表

| 问题 | 本设计的答案 |
|---|---|
| 以后加一个词缀是否都不用改核心？ | 已有原语覆盖的常规词缀应只改数据；全新原语通过版本化端口扩展，不能保证所有未知玩法零核心修改。 |
| 新框架是否多保存一份玩家血量？ | 否。只建立端口、编译产物与新效果状态；领域状态仍唯一。 |
| 所有插件是否每帧回调？ | 否。贡献按变化编译，事件按匹配分发，持续状态按到期处理。 |
| 预算不足能否少结算几个 AOE 目标？ | 否。必须验证合法组合容量和优化必要计算；不能用丢玩法换帧率。 |
| 火墙和点燃是否共用同一套时间规则？ | 不强制。旧火墙保持合同，新点燃显式选模拟时间。 |
| 怪物是否一定与玩家用同一个 AI？ | 否。共享端口不等于共享决策与动作节奏。 |
| 换图能否取消全部后台结果？ | 否。路径/表现按世界失效，已经提交的角色/仓库回执仍须消费。 |
| 增加 slots/sockets 能否直接修改旧保存字段？ | 否。当前旧实例白名单会拒绝；必须新 schema/codec/迁移并全链验证。 |
| 任意模块脚本是否真的被隔离沙箱保护？ | 否。首期为可信内置模块，权限是工程约束；未承诺不可信脚本沙箱。 |
| 该框架现在是否已经可运行并通过手机验收？ | 否。本次是设计交付；实施、构建与真机结果均 NOT_RUN。 |
