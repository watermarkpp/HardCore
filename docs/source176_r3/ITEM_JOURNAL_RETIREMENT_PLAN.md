# 持久化操作序列与 journal64 恢复

2026-10-02，状态 PASS（下述受测协议范围）。只处理既有 default-off 镶嵌事务，不新增正式玩法。

旧 v1 journal 的任意字符串操作 ID 无法从年龄或长度推断不可再入。
保留其最多64条原始结果，重复提交仍返回原结果；满额的新旧式操作继续拒绝。
绝不按TTL/LRU删除它们。

新增明确的 v2 序列协议：现有事务端口在 quote 时签发随机epoch和连续序号，
quote不写盘；第一次成功事务把epoch、序号、物品所有权结果通过同一角色writer
原子提交。后续仅接受同epoch的下一序号。至多保留最近64条完整结果，连续的
`retired_through`水位永久拒绝更早身份，包括改变请求内容后重发旧ID。退休的
v2请求返回明确拒绝，不冒称仍保有旧完整结果；v1结果保持原协议。

v2文档同时保留原v1结果数组，迁移不丢历史；这是两套身份协议的有界共存，
不是简单把旧64限制调大。未来版本/未知动作仍terminal，不能回退到旧备份。
序号限制在JSON可精确表示的正整数范围内，到达耗尽边界明确拒绝。

生产者是事务端口的下一序号quote；同一accepted plan只拥有一个现有writer job。
消费者是该job完成回调；旧plan回调只有仍为当前活动job才能发布内存状态。
下一事务仅在旧job和其回调结束后接收，并将历史水位和新的所有权变更原子提交。
重启恢复从同一角色文档恢复水位；不存在第二文件、第二writer或内存定时清理。

证明顺序：缺失继续执行能力RED → 单元序列/容量/未知版本矩阵 → 真实端口
连续跨越64边界 → 重复点击、延迟旧回调、错误epoch/序号/请求、取消和重启 →
原v1镶嵌/保存/未来版本回归。独立cold必须绑定本轮native成功producer。
未在最终源码运行的边界明确保留NOT_RUN。

## 2026-10-02 旧 v2 回退增量（施工中，尚未最终验收）

Pro/dot 指出低水位从旧备份恢复会重开同 epoch 的已完成命令。原生同进程及独立
cold 均复现 2→1 与130→65，旧命令再次获得非 replay 资格，进入新 writer并改变
恢复后的物品状态。证据不等同于用户真实存档已发生资产增殖。

恢复协议采用显式 hc.item.transactions.v3/schema3，只在既有角色备份恢复路径
生成新随机 epoch，并把它与恢复的整个物品文档经过同一临时校验及原子提升保存。
健康v2原样保留；v2/schema3仍是未来版本而terminal。恢复v3不删旧结果：原有
64个legacy结果及最近64个序列结果原样保留，连续序号与水位不重置。v3最近窗口
允许不同epoch，但每个结果的序号必须等于窗口位置；只有当前durable epoch的
下一序号有新提交资格。完整保留的旧结果只读重放；其余旧epoch一律拒绝，包含
改变请求内容的旧ID。再次恢复v3必须再次更换epoch；不会复用旧发行权。

生产者仍为同一事务端口，消费者仍为当前job完成回调；load_save既有生命周期
门禁先处理pending writer。无额外文件、第二writer、TTL、LRU或历史结果简单清空。
恢复写入/校验/提升失败保持fail-closed；新epoch不能只存在内存。随机身份沿用
既有16字节Crypto生成方式，生成失败或撞上可见旧epoch明确拒绝，不静默重试。

待最终同源码回归：同进程/独立cold/再次重启、迟到回调、v3再次回退、临时写入
失败、混合epoch窗口超过64、未来版本与默认root/旧备份兼容。不能将本节施工
设计等同为已通过。有效旧primary被外部整体替换且从不触发备份恢复的防回滚
属于另一威胁模型；本增量不声称有外部单调存储或检测任意人工降档的能力。
