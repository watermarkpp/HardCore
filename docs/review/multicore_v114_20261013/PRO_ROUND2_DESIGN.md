# HardCore 当前群怪多核架构：第二轮最终设计

## 决策与证据边界

**推荐目标：画面/输入主线程 + 一个长期运行的唯一权威模拟线程 + Godot 批量工作线程池。**

原顺序提交应保留，但它不必留在画面线程。真实移动、立即攻击、HP、技能时序、死亡及其同步玩法回调，由同一个模拟所有者按原顺序执行；worker 提供计算结果，不自行提交游戏事实。

本方案采用 DRG: Survivor 移动版已披露的“连续原生数据贯穿批量任务链、战斗计算与表现处理分开、无需全量 ECS 改写”模式。独立模拟时钟、HardCore 顺序提交及局部修复是本项目的专用设计，不是 DRG 已公开的实现。[S1]

当前来源身份按主控本轮提供：114 交付提交 `10daa4d20e3be0dac1161f45b6be94e44a0bfc50`；维护场地 `codex/integration` HEAD `45170d0eaf4d2c642d4a03de392f64fa2b1e25bf`；当前 `enemy.gd` SHA256 `d8f73dc3c9dcc17f81a4031d19154544ce3f89b5a3e945c51f9caa10b01653f3`。本轮未读取这些完整源码字节，也未做新原生、APK 或手机测试。300 ms 仅是当前部分决策计划的参数，不是模拟频率或线程架构前提。

## 1. 推荐线程与所有权

```text
Android 输入入口 / Godot 输入、UI路由
             │ 带时间戳、顺序号和视图身份的命令
             ▼
画面主线程 M ─── ClockPolicy / 呈现需求 ───► 模拟所有者 S
   │                                          │
   │ 输入、UI、资源/场景生命周期               │ 唯一世界状态、时钟推进
   │ 读取只读表现包、渲染提交                   │ 原顺序移动/攻击/HP/技能/死亡
   │                                          │ 固定阶段批量派发、局部修复
   │                                          ▼
   │                                  Godot WorkerThreadPool
   │                                  W0  W1  W2 ... Wp-1
   │                                  原生数值块、独占输出
   │                                          │
   └──────────── 已提交表现包 / 有序表现事件 ◄──┘ 经S提交后发布

Godot渲染/物理服务线程、Android驱动/GPU：仍是引擎/系统服务，
不计作项目可任意占用的空闲worker，不成为第二份HP权威。
```

| 职责 | 所有者 | 工作线程能做什么 |
|---|---|---|
| 输入路由、UI、场景和渲染资源生命周期 | M；必要的平台输入桥只传纯命令 | 不操作活动 UI/SceneTree |
| 时钟推进、任务release、effective tick和提交次序 | S | 不自行扣时间、延迟生效或推进下一tick |
| 位置、原空间索引、目标、HP、技能、当前状态与同步玩法回调 | S | 只读独立数值输入，不写权威 |
| 路径/候选、动态几何、静态地图查询 | S负责输入与选择；worker批算 | 沿原算法、原索引语义、原精度计算 |
| 命中与伤害数值 | worker仅算输入已合法确定的纯部分；S采样live条件并提交 | 不以完成顺序扣血，不提前消耗共享RNG |
| 动画帧、方向、UV、排序键、飘字批量参数 | worker可准备；M提交绘制 | 不把动画完成当作攻击或死亡时点 |
| 存档 | S在原事务边界产生一致快照；原存储服务写入并确认 | I/O可以异步，不能提前伪造持久化成功 |

S 使用独立长期 Thread/C++线程，不放进 WorkerThreadPool 长期占槽。工作池只接有限、无内部等待的计算块。[S2][S3]

### 1.1 唯一权威如何迁移

把原 Node 中的战斗位置、目标、速度、半径、冷却、HP、当前状态、技能进度和相应方法，抽到 S 独占的状态与服务中。它们不是每帧从节点复制出来的第二套可写世界，而是切换后唯一允许推进的世界。

画面节点保留显示 transform、Sprite/动画资源、血条和UI，只投影已提交状态。旧逻辑读取位置或HP必须转到模拟接口，禁止继续把显示节点位置作为战斗输入。攻击触发、伤害回调、吸血、死亡、掉落事实等能反过来影响本次战斗的回调也必须迁入 S；音画/UI通知才送到 M。

同一个运行会话只能启用一个所有者。切换在安全世界/加载边界进行，旧 `_physics_process`、计时器和伤害写入口停止；不能新旧双方同时推进，再用覆盖字段“同步”。只读表现副本、存档快照、worker输入不构成第二权威。

### 1.2 Godot三种机制不能混为一谈

| 机制 | 能力 | 不能据此承诺的能力 |
|---|---|---|
| Node `process_thread_group=SUB_THREAD` | 引擎在子线程处理一组节点；可用group order安排依赖 | 仍由引擎的process/physics回调调度，不等于独立于画面循环的时钟 |
| 独立 Thread + WorkerThreadPool | 专用所有者持续运行，有限批次由工作池执行 | 不自动使所有Node、资源或服务器查询合法 |
| RenderingServer/PhysicsServer线程能力 | 在对应配置和API合同下使用服务器；RID不要求每项都有Node | 不意味着DirectSpaceState可随时查询，也不意味着任意线程可手动推进主物理世界 |

场景线程组可作为过渡工具，不作为最终独立模拟所有者。跨线程 `call_deferred()` 适合表现通知，不能替代本次应立即发生的真实HP回调。[S4][S5]

### 1.3 正式PhysicsServer能力如何保留

当前自定义的群怪运动/几何规则应原样抽成数值模块，不为线程换成流场、新空间索引或另一套碰撞器。服务器仍可管理原RID、形状及确实依赖它的物理对象；但所有权、命令顺序和取结果阶段必须明确。[S5][S6]

对必须查询活动PhysicsSpace的路径，设置一个带tick身份的 `PhysicsPort`：在引擎合法同步阶段执行查询/更新，结果只交回S。**线程安全的调用，不等于当前写入已立即反映在查询结果。**这个端口的同步和等待计入模拟关键路径。

如果当前即时攻击/移动强依赖“只有画面主循环才会启动的物理step”，保留该依赖就仍有主循环耦合。普通GDExtension和“separate thread”开关不能被假定能独立驱动默认物理世界。目标版本必须消除这项关键路径依赖，或另做保持原求解器、唯一step所有者的引擎驱动适配；未完成前，不签收“完全独立模拟”。本轮未取得114全文，不能声称当前已经不存在这类依赖。

## 2. 统一时钟、输入与截止

### 2.1 主线程制定需求，不逐帧发放模拟许可

M设置一次有版本的 `ClockPolicy`：单调时钟基准、当前逻辑步长/倍率、暂停规则、目标呈现节奏、状态新鲜度和截止预算。S按这个合同独立等待绝对release时刻并推进；M只在暂停、恢复、刷新率策略等变动时发布有序更新，不需要每帧发送“现在可以算了”。

避免 `M._process -> 请求S算一步`：这会把画面掉帧重新传递给模拟。也不采用“做完再sleep固定时长”的漂移循环，而按绝对时刻等待。

| 概念 | 定义与决定者 |
|---|---|
| logic tick k | S唯一推进的游戏逻辑步；步长沿当前规则，不默认改成60Hz |
| display frame r | M/引擎/系统呈现帧；与逻辑tick分别编号 |
| input sampled time | 平台事件到达与S在原采样位置接受输入的时间，分别记录 |
| release time Rj | 输入和前置结果已确定后，任务j最早可开工时间 |
| deadline Dj | 为不耽误其原消费者所分配的完成期限 |
| effective tick/phase/ordinal | S赋予的游戏生效位置；worker不可更改 |
| presentation time Fr | 实際交给显示系统的时间；不反向重定义已提交逻辑时间 |

统一调度不等于把旧simulation时间、wall-time到期和暂停补偿偷偷统一为同一种语义。旧合同在S中通过时钟适配保留，但每个状态只有一个推进者。

### 2.2 频率分层

规划按当前已定义的 rich observation/retarget/planning 门触发；连续移动、碰撞和立即攻击沿原每physics-step合同；事件在原事件位置处理；显示按呈现帧消费。当前300ms不门控移动碰撞/攻击，也不决定worker什么时候有资格提交。

S可以让worker提前准备已经具备输入的部分，但只能在原事件位置使其结果生效。过早算完不提前移动；迟到也不能偷偷改到下一tick再生效。

### 2.3 输入链也必须解耦，不能只移动模拟循环

Godot默认输入积累可把相似事件合并到渲染帧结束时发出。关闭积累可改善反应，但不能保证一个已经被驱动阻塞的主循环仍及时处理输入。[S7]

最终输入合同是：时间戳、到达顺序、按下/抬起边沿、当前UI路由身份和必要的视图/相机身份进入有界命令邮箱；S在原采样相位消费。不能让S轮询活动节点或用未来相机解释用户点击已显示画面的位置。

正常Godot输入入口达标时复用它；若要求渲染阻塞时输入依然及时送达，则需在Android已有输入转发链增加小型原生邮箱桥，仍保持原UI消费、坐标变换与唯一输入路由。该桥属于适配工作，不声称已有一个启用即完成的通用插件钩子。收到过晚的事件不能回写已提交tick；它应记录迟交，并进入下一合法采样位置。

### 2.4 呈现期限不是“有结果就算按时”

设原逻辑步长为h，tick k在Rk释放，选择本次应服务的目标呈现时刻Fr。保守安排：

`Dsim,k <= min(Rk+h, Fr - M_late - GPU_tail - margin)`

`M_late`为取得新状态后无法提前做的画面工作。每个数据任务还要为后续顺序提交和局部修复留下尾部预算。GPU可流水重叠时可以收紧模型，但不能不计GPU。

呈现合同预先确定每帧要求的最低已提交tick；M不能把“当前碰巧完成的tick”重新定义为要求。读取到旧tick时记录新鲜度失败。三个有所有权标记的表现缓冲槽可防止生产者覆盖消费者，但**缓冲槽数量不代表故意延迟三帧**。只发布完整提交状态，不发布半个世界。

中间纯表现快照可以被更新的完整快照取代，逻辑tick、真实伤害和离散事件不能丢。M不忙等模拟。偶发迟到可能导致真实重复旧帧，这是失败记录，不用插值把它包装成达标。显示系统在迟交帧时本身就可能重复旧图；画面帧节奏控制不能代替模拟期限。[S8]

## 3. 有界任务池与过载

### 3.1 采用成熟执行器，只写固定游戏流水线

优先复用 Godot `WorkerThreadPool.add_group_task`；每个element对应原生数据块，不对应“第几只怪”。`tasks_needed`明确限制参与线程，原生块保留到完成回收。S不放进池、不让worker等待其他worker。[S2]

专用调度只包含固定阶段：准备输入/查询、批量数值、原序消费修复、表现准备/发布。不建设可执行任意脚本的任务图框架，不实现自己的通用抢占、工作窃取或线程调度器。

S维护有限的ready窗口，按“最早消费者截止—关键路径—工作量”选择派发。Godot公开优先级是high/low，不是EDF；最早截止优先在本项目提交队列中落实，不伪称引擎提供硬实时EDF。已运行的无关长任务仍可能阻塞，须计入干扰。

### 3.2 能控制的约束

| 约束 | 设计 |
|---|---|
| 在途范围 | 默认当前tick一个工作窗口，可加一个同tick前瞻窗口；不滚动积累多个未完成模拟tick |
| 任务容量 | 固定slots、预分配输入/输出；满时停止投机派发，不截断合法实体或事件 |
| 分块指标 | 候选—peer判定数、地图边测试数、原索引遍历工作量等；不是十怪一块 |
| 不可抢占块 | 给块设工作量上界，超大循环按原顺序保存游标分块；不得丢迭代或重排运算 |
| 均衡 | 块数多于可用worker，较快worker自然完成更多块；不绑定一模块永占一核 |
| 共享内存 | 只读输入、独占输出、短发布同步；不持世界锁执行kernel |
| 优先级 | 当前将消费的移动/攻击依赖先于远处投机准备；低优先工作不得用长块占满池 |
| 回收 | 每任务有限结束；完成后正式回收；退休world的输入仍保留到在途任务不再读取 |

块的时间目标由保守的慢核能力换算，并保留OS调度和温控余量。平均耗时不是最坏界；预估再精确也不是Android的硬实时保证。系统线程调度和核心利用必须与应用任务数分开看。[S9]

### 3.3 最迟启动与必要条件

任务j的最迟启动：

`LSj = Dj - Cj_bound - Jj - margin_j`

其中Cj_bound包括在设计运行包络下本块执行的保守成本，Jj包含已知不可抢占干扰。ready不等于可及时完成；到LS仍未启动即记录预计miss。不能为提高ready率把Dj向后改。

一个逻辑步的必要成本边界：

`C_S_serial + P + D + V + R_conflict + T_pool + C_publish <= Dsim - Rk`

`T_pool >= max(W / p_effective, L_dependency)`

第二式只是下界，不是充分条件；仍有调度、内存和服务器同步开销。p_effective表示扣除主线程、S、渲染/引擎工作后可持续获得的等效能力，不是线程个数。

对一个独立阶段，若所有块都能在最慢参与核上以Cj_bound界定，且确有m条可用执行通道，则无额外干扰时的列表调度保守界可写为：

`T_stage <= sum(Cj_bound)/m + (1 - 1/m)*max(Cj_bound)`

实际再加可验证的调度干扰界。没有可用干扰界，就只能报告设计包络内的软实时达标，不能承诺任意系统负载下硬实时。

### 3.4 截止失败如何处理

- 临近期限时取消尚未领取、不会被当前消费者需要的投机块；合法游戏义务不取消。
- S可领取未执行的关键块，或用原生串行路径完成剩余原序后缀；不回退到画面主线程，不每轮重做已提交前缀。
- 已运行块不强杀、不覆盖其内存；它必须按有限块结束。不能把同一任务不断复制派发制造恢复队列。
- 已提交事实不回滚、不重扣，未完成tick不冒充完成。不得跨tick无限积压；迟到量与未服务义务必须显式统计。

临界失败恢复只保障正确性，不保障该帧期限。持续输入负载超过可持续处理能力时，“不减工作、不降频、无滞后、有限资源”不可能靠队列策略同时满足。此时该实现/配置不合格：应继续压缩真实关键路径或增加有效计算能力，而不是默认放慢游戏、插值遮盖或静默暂停。暂停/降载属于另需授权的产品选择。

## 4. 原序结果与局部修复

### 4.1 等价目标

原执行为 `W_(i+1) = F_i(W_i, I_k)`。F_i包括原候选顺序、短路、位置发布、立即攻击及同步回调。新版本仍由S按同一序列执行F_i；worker只替换其中输入可证明相同的数值子表达式。顺序化的是状态变更，不要求所有数值计算都串行。

S不能把所有怪的最终位移并行算完后直接批量写入。后一个actor必须观察前一个actor的真实提交。

### 4.2 计划需带的紧凑依赖

| 数据 | 目的 |
|---|---|
| world/life身份、tick/phase/actor及候选ordinal | 防止错生命期、错世界、错消费位置 |
| self/target的pose、半径、动作参数依赖 | 识别会改变整段候选准备的变化 |
| 按原slot保存的peer身份、数值读版本与几何结果 | 只修复受影响的peer—候选判断 |
| 查询覆盖范围及其变更见证 | 捕捉原候选之外的新进入者 |
| 地图/投影/环境的实际依赖版本 | 不把旧地图结果当新世界有效 |
| 原侧向/阶段/谓词顺序 | 修复后仍从原首选方向开始，不按worker完成顺序选择 |

这些数据使用连续数组、范围索引、位图等紧凑结构，不为每个pair建立Dictionary。版本由唯一S在正式写入口更新，是派生有效性信息，不是第二位置/HP系统。

### 4.3 避免每次全候选重算

S维护当前窗口的变更集合；计划维护自己的读取集合。集合不相交，沿原消费顺序复用已计算数值；相交时，只修复受影响的几何元素。原消费者仍执行必要的live资格和回调，不能因有数值结果就整包预批准。

例如后续actor有20个peer候选，只有前一actor A改变位置；self、target和查询身份顺序不变时，只重新计算A与该actor各实际需要候选轨迹的关系，不重算其他19个peer，也不重算未改变的静态地图部分。该例是结构示意，不是实际候选计数或收益数据。若一个窗口里前面的多个actor都已移动，第i个actor可能面对i-1项甚至更多同步变更；局部修复没有固定“一只peer”的上界，最坏仍可能接近全量。

同bucket移动必须写pose变更；membership revision未变没有豁免权。移动后又移回也应保留变化序列，不能靠最终位置相等抹掉期间同步行为。

**新进入者：**记录移动、出生、死亡、传送、半径/地图/资格变化的旧新覆盖。若可能影响查询范围，且该身份原本不在候选池，重新执行该范围的原Index查询，恢复其原顺序；不得简单把新ID附到末尾。若原Index自身还做位置相关筛选，范围内容变化也须触发该层查询重验。这是原索引的变更旁路记录，不是替换空间索引算法。

**短路：**第一方向旧时被挡、现在可能放行，必须从原首选方向重走原逻辑；原本短路未算的部分按需要补算。worker提前算出的纯数据可以未被消费，但不能提前执行副作用、RNG或HP；三个不同几何predicate也不能共用一个bool。

### 4.4 严格顺序确实限制并行量时

密集堵口可能使几乎每次提交都影响后续读取。此时缩短前瞻窗口、停止低采用率投机，保留静态与未变数据的并行，并让顺序后缀在S的紧凑原生实现中运行；不否决整个多线程架构。

真正可能改变语义、必须由用户另选的是：全体actor从同一旧状态同时决策、统一群体求解替代原逐序规则、移动/攻击默认晚一tick、按完成次序提交、降频或少更新。最终方案不采用它们。

## 5. 成熟模式、最小模块与迁移

### 5.1 直接借鉴与专用新增

| 来源/机制 | 借鉴 | 不冒充现成能力 |
|---|---|---|
| DRG: Survivor移动版 | 原生连续数据贯穿批量运动任务；批量表现；不必全量ECS | 未公开完整线程/时钟/HP提交图，不能说其采用本设计的唯一S；本轮也不更换流场/KD-tree |
| Godot Thread与WorkerThreadPool | 专用线程、批量分发、完成回收 | 不是硬实时EDF，不自动知道原顺序语义 |
| Godot场景线程组与Servers | 有管理的线程组、服务器/RID边界 | 不是任意worker可访问活动世界，也不自动独立step |
| Android帧节奏机制 | 呈现时刻、队列/背压与实际帧间隔边界 | 不代替模拟服务期限，不授权自动降低游戏频率 |
| HardCore专用 | 原执行相位/ordinal、读集合与范围变更、原序修复、权威迁移、save/input桥 | 这些是需要实现和验证的本项目适配，不是DRG源码结论 |

DRG访谈明确存在1000敌人追击及500敌人带武器持续战斗测试，并披露10–15级移动任务依赖、连续native containers和无需整体ECS改写；实际worker数、固定逻辑Hz、完整源码仍未公开。[S1] 本轮没有取得更贴近且已经核对完整Android战斗源码的替代，不用demo替换这个主参照，也不重复扩搜候选游戏。

### 5.2 五个最小模块

| 模块 | 接口示意 | 实现建议 |
|---|---|---|
| SimulationHost/WorldState | `start_world`、`set_clock_policy`、`submit_command`、内部`step_tick` | C++拥有线程、状态、时钟与原序提交 |
| CombatKernels | `prepare_range`、`evaluate_range`、`repair_changed` | 原算法C++；连续数值数组，不换物理/索引规则 |
| BatchExecutor | `dispatch_ready`、`poll_published`、`retire_completed` | 薄封装Godot池；固定阶段和容量，不造通用调度器 |
| PresentationBridge | `acquire_frame(min_tick)`、`release_frame`、`drain_events` | 原生缓冲；GD保留场景、UI、资源与显示适配 |
| Platform/TransactionPorts | input、physics、save及load/retire | 最少原生/平台桥；玩法变化仍交S，磁盘成功沿原确认合同 |

纯GD规则可在确保单线程独占、无活动Node/共享资源依赖时留在S一侧；高频循环转原生。UI、编辑器、内容配置不要求全改C++。相机、材质、纹理、Node创建释放仍由M/合法引擎路径负责。[S5][S10]

### 5.3 迁移顺序：阶段1就有实质工作转移

**阶段1：交付当前群怪战斗的闭合纵向切片。**在一个真实地图战斗会话中，把玩家、参与怪物、宠物/投射物及会同步改变该链结果的现有效果，所需的原算法、索引数值和HP提交链接到S；worker真实执行整批候选和几何。必须包含“追击—绕路/碰撞—移动—立即攻击—HP/死亡回调”的闭环，M只呈现。不能只搬怪物、把玩家HP和回调留在M再同步等待；也不能只做空Host或假数据演示。未闭合的会话保持整个旧模式，不在同一局里启用两份权威。

阶段1内部当然先形成可比较的串行原生通路再接多线程，但交付条件包含真实重工作已经离开M，而不是将worker无限后置。

**阶段2：接全当前玩法及事务边界。**扩到当前已实装职业/技能、投射物、召唤、换图、复活、装备变化、旧状态和存档；每条路径指定S所有权、原采样位置、原回调顺序。对依赖主线程帧号/线程ID的计时或预算账本建立显式适配，不能把“每渲染帧”机械改成“每逻辑tick”并声称完全等价。若旧玩法本身以显示帧数决定结果，应列为需裁决的合同矛盾。

**阶段3：批量表现与期限收尾。**迁移动画帧/方向/绘制参数准备，保持等距遮挡和相等键顺序；完善输出缓冲、Android输入桥及物理端口的独立性。最后才按完整调用链和期限条件定生产并行度，不再做旧小核反复对照。

### 5.4 Android构建边界

沿现有Godot引擎版本固定godot-cpp/API、NDK、导出模板和浮点精度；Android提供arm64-v8a，原包若还支持其他ABI则继续匹配；桌面测试库不是手机通过证明。C++标量与Vector2精度、EPS、分支和运算顺序照原合同，不能为SIMD擅开fast-math或重排归约。

使用正式GDExtension和需要时的Android v2插件/AAR路径；官方提供模板，无需换引擎或建设ECS。[S10] .so及依赖须满足目标平台的ELF/APK页对齐要求，包括16KB页兼容。[S11]

保持 `com.personal.mafaoffline`、原签名/安装身份、存档目录和schema；架构迁移不允许用新包名或清档掩盖兼容问题。

## 6. 期限算例与最终承诺

### 6.1 不能只看画面主线程变轻

目标同时要求：S合法tick按期完成、输入及时服务、M和GPU及时呈现、状态新鲜度不持续恶化。S从M移出后允许两者重叠，但S内部的顺序下界仍存在。

定义：

- `M_early`：与当前模拟结果无关的画面/输入工作；
- `M_late`：必须取得本次新状态后才可做的提交；
- `S_serial`：S的准备、顺序提交和发布；
- `W`：独立数值工作的参考单核成本；
- `L`：数值任务依赖链下界；
- `R`：局部修复/失效额外成本；
- `G`：该次新状态对应的GPU尾部；
- `J`：调度、同步及安全余量。

在这些阶段可按描述重叠、且没有额外服务器等待的条件下，乐观成本模型为：

`T_frame_model = max(M_early, S_serial + max(W/p_effective, L) + R) + M_late + G + J`

这不是对异构手机的充分保证，也不能拿平均CPU占用推出p_effective。

### 6.2 纯假设算例，非REA实测

以下只演示一次逻辑步与一个呈现期限对齐的情形。实际逻辑Hz与显示Hz不同，应纳入该区间所有到期逻辑步，不能把原逻辑步长默认为16.67ms。

取 `M_early=2ms, S_serial=4ms, W=32ms, L=3ms, M_late=1.5ms, G=3ms, J=1ms`。

| 条件 | 模型结果 | 与16.67ms比较 |
|---|---:|---|
| 4条等速有效通道，R=0 | 17.5ms | 未达标 |
| 8条等速有效通道，R=0 | 13.5ms | 模型内有余量 |
| 8条等速有效通道，R=4ms | 17.5ms | 再次未达标 |

手机8个逻辑核不意味着可以同时给8个worker、M、S、渲染和系统线程各一颗等速核心。实际并行度和最长任务必须按可持续能力结算；只增加线程可能没有增加有效算力。

### 6.3 施工验收与承诺边界

| 层次 | 必须达到 |
|---|---|
| 结构 | S独立推进且唯一写状态；M不承担当帧战斗结算；worker真实执行整段重计算 |
| 规则 | 同一合法输入与时钟事件序列下，原方向首选、短路、碰撞、立即攻击、HP/技能/RNG/死亡及save事实一致 |
| 期限 | 分列tick完成、输入服务、任务期限、呈现期限、状态年龄；不以ready或低M耗时代替 |
| 资源 | 有界在途、无无限队列、无丢合法事件、无迟到重复提交、无双重权威 |
| 适配 | 不依赖活动Node非法访问；强PhysicsServer依赖和Android输入积累有明确闭合方案 |
| 性能 | 完整场景的主线程、S、全部worker、GPU/driver等待、修复成本及持续热状态一并结算 |

**目标架构可行，推荐按上述路线施工设计；它比“画面线程继续承担全部提交”更符合当前目标。**其成熟基础是原生数据批处理、唯一写者、引擎工作池与明确缓冲所有权；HardCore专用新增限于旧语义映射和适配。

能确定的是目标结构、责任边界、正确性条件和失败判据。不能在尚未实现时承诺4/8线程一定达到60fps。若严格原序链或未迁移的渲染/物理等待超出期限，必须继续改真实关键路径，不用插值、业务降频、少怪或晚一tick作为暗中补救。

本轮状态：设计完成；生产代码修改、新native、APK和设备验证均未执行。
