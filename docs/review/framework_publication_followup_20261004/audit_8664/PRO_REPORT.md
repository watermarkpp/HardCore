## 一、确定的当前缺口：默认启用集合没有经过手动启用的依赖校验

### 两条发布路径现在不一致

| 路径 | 固定源码中的实际行为 |
|---|---|
| `ContentLayers.set_feature_module_enabled()` | `scripts/layers/runtime/content_layer_registry.gd` **L223–228**：逐个检查已选模块的 `requires`，依赖必须同时在候选启用集合中，否则拒绝。 |
| `ContentLayers.reload_feature_catalog()` | 同文件 **L156–160**：只收集 `default_enabled=true` 的模块，然后直接进入统一发布函数。 |
| `_publish_feature_configuration()` | 同文件 **L163–185**：验证实际人物候选，但没有补上启用集合的依赖检查。 |
| 目录编译／人物编译 | `feature_compiler.gd` **L87–109、L111–197**：目录只确认依赖模块已注册及无环；人物编译输入是贡献来源，没有完整启用集合，不能补出上述约束。 |

这不是仅凭“没有找到测试”提出的怀疑，而是两条实际调用链执行了不同规则。 

**最小反例**可使用两个合法、项目内可信JSON包：

```text
A：default_enabled=true，requires=[B]，提供一个合法小额属性贡献
B：default_enabled=false，已注册，无循环或冲突
```

当前目录编译能找到B，因此通过；默认启用集合却只有A。人物来源收集只根据启用集合筛选绑定，也没有检查依赖是否启用，所以A可以随目录发布生效。**同样的A若改由手动启用，在B关闭时反而会被拒绝。** 

我也读取了父版对应代码：这个不一致已经存在，**不能说是本轮原子发布新引入的回归**；但新增可信包入口后，它仍属于当前发布协议需要补齐的缺口。本会话没有运行这个新反例，不将其表述为新取得的原生RED。

### 最小修正与验收边界

将现有“候选启用集合必须包含全部依赖”的判断复用于**所有发布入口**，在目录、人物结果实际替换之前完成即可。**不要自动替用户启用B，也不要增加另一套依赖解析权威。**

最小测试应要求：上述默认集合被拒绝，旧目录、启用集合、人物bundle、stats、compile_count及通知次数保持不变；随后合法包含A/B的候选能够正常发布。现有三份新测试没有覆盖这个组合，不能用它们的PASS关闭这项规则一致性。

## 二、原子人物候选：本轮实现和已有反例相符

### pre-feature快照确实来自唯一原属性汇总

`PlayerState.recalculate_stats()` 仍执行原职业、等级、装备、旧词缀、套装、临时药品和圣物汇总；在应用新feature贡献之前，**`scripts/player_state.gd` L3720–3724** 保存 `result.duplicate(true)`。

随后 **L3743–3756** 用当前实际装备、技能和profile来源生成独立loadout候选；`feature_loadout.gd` **L10–34** 让候选沿用旧不可变bundle和编译代次，只有候选编译及数值验证成功才提升。**失败没有先改变现有loadout，也没有把候选错误写入旧人物的 `feature_errors`。**  

这里新增的是原汇总结果的派生快照，不是第二套属性公式。其正确使用前提仍是：人物基础变化经原 `recalculate_stats()` 更新，不能将任意直接修改公开字段后未汇总的状态，自动视为已更新的发布基础。

### 目录与人物权威结果在通知前一起提交

`content_layer_registry.gd` **L177–183** 先替换目录、authority、bindings和启用集合，再调用 `PlayerState._commit_feature_configuration()`；后者 **L3759–3763** 只有loadout、computed_stats和错误状态赋值。此区间没有yield或发布通知，最后才发出 `feature_catalog_changed`。 

发布锁一直保持到通知返回，因此观察者重入 `enable/disable/reload` 会被拒绝。**这里支持的是“目录与PlayerState权威聚合结果一致地发布”，不是所有UI及每个Player节点的显示缓存同时无回调地完成刷新。**

最终 `feature_publication_atomic_test.result.json` 的 **19检查PASS**明确覆盖实际属性上下限倒置、负MP候选、默认启用无效人物目录、旧编译代次保持以及通知中重入启停／reload。它们应保留，不因上一节的新依赖反例而一并否定。

## 三、生命周期门禁：已测单动作路径成立，但“所有未结束动作”还不能直接推出

### 当前已经落实的范围

`PlayerState.feature_publication_context()` **L9311–9330** 使用原世界登记表，逐个检查owner；空profile不再跳过登记，queued-free仍算活世界且不允许新启用。多owner中任意一个不具备READY合同，都会令候选不就绪。Root仍在 **L1495–1498** 登记，在退出清理段 **L1763–1788** 注销。  

目录重载只检查“无活世界”；启用已注册包时再区分startup与world_ready。停用不套用同一READY门禁，是本轮明确保留的撤销后续资格语义，**不能因为停用允许发生于windup就反判为漏洞**。

最终生命周期回执 **30检查PASS**确实包含空profile世界、输入锁、暂停、额外owner、真实动作active、非空票据、停用后一次真实HP提交及派生事实保留、queued-free与退出后恢复。

### 需要补证的窄时序：当前动作槽位结束，不必然表示全部旧释放都结束

当前发布门禁读取的是：

```gdscript
actor.combat_action_snapshot().active
```

而 `player.gd` **L1444–1451** 的这个快照只描述当前 `_pending_combat_action_id`。同文件的两条延迟释放函数又明确保留旧合同：**新动作覆盖当前动作槽位，不取消较早已经接受的延迟释放。** 

这不是之前已经修好的“单个动作physics先结束、process Timer尚未释放”问题：**L271–275** 仍要求当前动作已committed才结束，那个保护存在。疑问只针对**两个已接受动作的槽位覆盖**。

最小生产入口反例应是：

> 用受允许的测试JSON timing贡献构造较晚释放的A；确认A真实接受。原动作锁允许后再正式接受较短动作B，等待真实physics结束B，而A仍未释放；此时尝试启用另一个已注册world_ready包。

需要同时记录A/B接受结果、旧lease生产者状态、当前action snapshot、Root READY及实际释放次数，**不直接改active字段，不压住回调，不增加正式玩法时长**。当前authority允许独立修改release timing，Player也分别计算动作锁与释放延迟，因此这个组合值得验证；但本轮没有原生执行它，仍列为**生命周期门禁的待复验风险**，不是正常UI已复现的新故障。 

若该路径能通过全部正式接纳，就需要用原Player／lease所有权证明没有未结束生产者，而不能仅凭最新动作槽位。若正式规则拒绝A/B重叠，则保留那个拒绝结果即可，不应为测试强造绕过。
