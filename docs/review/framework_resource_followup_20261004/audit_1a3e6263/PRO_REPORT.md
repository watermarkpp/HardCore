## 一、优先修正：发布通知中取消，会使“已发布”向等待者返回失败

### 确定的源码条件链

**我没有在本会话取得这条新路径的原生RED，也不称其为自然UI复现；以上是由明确调用顺序得出的条件性源码结论。**

### 最小原生反例

复用 `feature_resource_preparation_test.gd`，在其实际 `feature_catalog_changed` 观察者中，一次性调用 `cancel_feature_resource_preparation()`。记录：

- 外部异步调用的最终返回值；
- 实际目录、enabled、stats及资源lease是否已经更新；
- 等待者恢复时 `Budget.snapshot().open_scopes`；
- 通知栈内再次启停是否被原发布锁拒绝。

原14项就绪测试只记录观察者中的scope数；原取消测试在准备阶段取消，均没有执行这个交错。它们原有通过结果不受否定。 

**最小修正边界：**可取消准备与已进入同步原子提升必须分阶段。进入提升后，取消不能再把当前应用请求改判为“准备失败”，也不能释放外层发布锁；该请求应在scope关闭后交付真实结果。可以拒绝或延后处理此时的取消，但**不要回滚已经发布的配置，也不要将所有取消一律延迟到引擎线程结束**——准备期间立即通知原等待者失败的现有语义应保留。

## 二、需补原生反例：持续共享请求可以饿死就绪应用和资源退休

### 问题发生在服务内部，不是FrameBudget公平规则失效

`feature_resource_preparation.gd` **L95–112** 的选择顺序是严格的：

```text
_work 有条目 → 只处理资源请求／轮询／逐caller交付
否则 _applications 有条目 → 执行就绪应用
否则 _retirements 有条目 → 回收一个资源引用
```

而 **L183–210** 只要同一任务仍有其他caller，就继续把该路径排入 `_work`。因此，即使引擎加载早已完成、该服务每帧都得到正常预算，后两条队列也可能一直没有机会。 

这与“32个请求全部完成后排空”不同。当前共享专项每轮都是**有限请求全部停止加入后再回收**，25项PASS与四轮对象数稳定不能证明持续输入时的内部公平性。 

### 不需要无限目标或大量并发的反例

只使用当前已声明的同一张纹理：

1. 发起正式异步启用，同时让两个合法直接准备调用者参与共享任务。
2. 每个直接调用者完成后释放自己的lease，并补发下一次准备，使在途caller数量保持有限。
3. 观察首个已就绪的发布应用，是否只能在停止补发后执行；同时观察退休队列是否持续增加而得不到服务。

这使用的是本轮已经测试支持的 `service.prepare()`，不是绕过资源信任或制造假任务。**源码能够推出严格优先造成的饥饿条件；但本轮没有运行该持续输入反例，不能称现有自然游戏已实测卡死。**

修正应在**这个准备器内部**为已就绪应用、必要的任务终态领取、资源退休提供有界服务机会。不要靠增大1200μs、强制pump、减少caller、伪造frame ID，或放弃尚欠引擎的get权解决。只提升FrameBudget层的公平性也无效，因为这三条队列共用同一个 `feature_resources` 类别。

## 四、共享请求、取消和预算：哪些已证实，哪些仍未证实

### 引擎共享任务的请求／领取权：保留8项专项成果

准备器在cache miss时，无论是否观察到外部已有任务，都会先发起自己的 `load_threaded_request()`；仅在自己的成功请求之后领取对应终态。`feature_resource_foreign_request_test.gd`使用真实外部 `CACHE_MODE_IGNORE` 请求，验证功能准备结束后外部仍可取得同一资源，再检查两方权利全部完成。**最终8检查PASS直接覆盖了此前“偷领外部get权”的反例。**  

共享32调用者的25项专项还确认了一次物理request／get、独立lease、逐caller交付与有限四轮排空。但每lease的 `requested`／`threaded_completed` 是**参与情况**，不能跨32个lease相加后当作32次物理加载；service级 `request_calls/get_calls`才是该项计数。源码和测试对此区分正确。 

### 取消已启动任务：保留13项，但不能覆盖第一节的发布中取消

当前13项测试在自己已request、尚未get时取消，原等待者立即失败，任务继续被持有，最后恰好领取一次并排空。这支持“取消等待不等于取消引擎线程”。 

准确的测试门禁接受 `IN_PROGRESS` 或 `LOADED`，因为worker速度可变；README另述某次实际观察为IN_PROGRESS。**本轮我没有读取那条原始状态打印来独立确认具体状态值，故只采用回执实际保证的‘request之后、get之前取消’。**它也没有测试 `feature_catalog_changed` 内部取消。

### 1200μs与旧计费规则没有被改写

已读取本SHA的FrameBudget：真实process epoch、墙钟计费、在途耗时、necessary超额、嵌套外层一次计费、首次服务优先／余量机会规则均保留。资源准备器没有调用重置额度接口；正常路径在结束scope后才发出completion。**第一节的问题是取消旁路破坏了后一点，不是FrameBudget自身新增了第二份预算。**
