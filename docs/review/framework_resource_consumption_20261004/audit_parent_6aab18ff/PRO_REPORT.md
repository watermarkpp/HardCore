## 一、优先补修：其他已取消等待者恢复后，再次取消仍能改判已提交应用

### 原反例确实已经修复

|---|---|

原应用在L141期间仍位于 `_requests`，但已不受 `_applying_request` 保护。与此同时，ContentLayers的同步提交标记和发布锁已经随应用回调返回而解除。 

因此存在这条完整条件链：

```text
应用A已原子发布新配置
→ 通知中取消另一个准备请求B，B的失败交付被延后
→ A的应用回调返回，提交标记解除，预算scope关闭
→ 先交付B的失败结果
→ B的等待续体再次调用正式取消接口
→ A仍在可取消请求表，被交付false并删除
→ 原定交付A的true被忽略
```

**结果仍是“配置已成功发布，原调用者却收到false”。**这一次不再伴随scope内恢复；它是终态交付顺序的问题，而不是旧缺陷原样未修。

`negative_supervisor/run_terminal_failure.py` **L46–74** 不接受“任意错误都算成功”：它核对唯一场景、完整receipt、run／invocation／source、正常退出及非timeout，并严格匹配bad-header、指定ctex和指定PNG三条错误；额外脚本／解析错误会使监督判定失败。

两点不能外推：

**其一，**脚本的 `finally` 只证明所归档的监督执行完成了恢复，不是物理掉电、监督器自身被强杀或任意文件系统异常下的恢复保证。

**其二，**监督JSON的PASS不是脚本普通退出0。脚本末尾仍返回原validation子进程退出码；归档中外层wrapper为1。这与保留原runnerFAIL一致，不需要为了“全绿”修改退出或错误allowlist。
