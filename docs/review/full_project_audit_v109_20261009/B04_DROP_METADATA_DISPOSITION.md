## Status ownership and runtime meaning

The status is emitted unconditionally by `compile_authority.ps1` at line 535 as `PENDING_ACTIVATION`. The compiler does not use it as an acceptance gate: its real gates are the whitelist/new-row/residue/overlay checks at lines 572-587, origin and live-total checks at lines 511-530, and optional stable-UID comparison at lines 590-625. The preview generator uses a separate `PENDING_ACTIVATION_PREVIEW` value and is not the production authority.

`user_loot_sheet_provider.gd` validates schema at lines 63-65, source and sheet hash at lines 66-73, every monster/slot and UID at lines 74-133, and the computed summary at lines 137-146. It never reads `parsed["status"]`. It publishes `valid=true` only after the complete document and per-slot tallies pass. Therefore `PENDING_ACTIVATION` is currently a metadata/release-state label, not a runtime availability gate.

`loot_runtime_service.gd` constructs the provider at line 30, rejects only `_sheet_authority.valid` at lines 91-94, then consumes the provider profile/probability at lines 100-115 and 242-263. Its result identifies the sheet authority and digest at lines 56-64, but does not inspect status. The runtime contract is therefore “valid compiled sheet plus direct-baseline identity/overflow authority”, not “status must equal ACTIVE”. `GameData` separately loads the direct V2 baseline (lines 287-299 of `scripts/game_data.gd`); its `compiled_slots=7611` is not evidence that the 6083-sheet summary is corrupt.

## What is safe to fix

The smallest truthful disposition is to keep the user sheet and all slot values unchanged, and reconcile only release metadata through the compiler output. A future activation step may change `status` only after the owner records the release decision and verifies the exact generated bytes; it must not be done by hand-editing the JSON or by making the provider infer activation from an unconsumed header field. If the product is intentionally still pre-activation, retaining `PENDING_ACTIVATION` is truthful but should be documented as non-operational until a real activation owner consumes it.

The compiler is suitable for a verification-only rebuild. Its `ProjectRoot`, `WorkbookPath`, `OutputDir`, and `VerifyAgainstAuthority` parameters are declared at lines 1-11. With no live workbook it reconstructs the sealed archived parser inputs at lines 25-32 and validates the archived workbook hash at lines 34-48. `VerifyAgainstAuthority` compares stable slot UIDs and the item/gold, numerator/denominator, overflow, and protected fields for the sheet-compiled portion at lines 590-625. It does not compare overlay or boss-material rows, nor does it make up probabilities. Consequently, exact 6083-slot verification requires both this stable-UID/value comparison and the provider/compiler origin-count, summary, and live-total gates; a successful header-only check is insufficient.

A formal metadata repair/activation review should preserve these invariants:

1. Preserve the archived workbook binding `bc234fca54286547b07f64731c9d0e3674aa19a703863c393c356caf97005251` and the source paths/hashes embedded in the authority JSON.
2. Preserve every `slot_uid`, canonical identity, final numerator/denominator, gold amount, overflow priority, protected flag, origin, and the 6083 profile total. Do not derive or “normalize” probabilities.
3. Rebuild to a fresh output directory, run `-VerifyAgainstAuthority` against the frozen target authority, and retain the compiler receipt and exact output SHA. Do not overwrite the frozen target until the receipt is reviewed.
4. Re-run the strict provider-equivalent checks over all 126 profiles: unique UID ownership, exact per-slot tally, origin buckets, summary fields, empty-sheet/residue accounting, and live total. The provider’s line-139 summary check is the runtime-side guard; the compiler’s lines 511-530 are the source-side guard.
5. Treat `PENDING_ACTIVATION` as a release metadata transition, with a named activation owner and a separate receipt. Do not add a runtime status gate unless product explicitly wants the status to become operational; doing so would change the current runtime contract and needs a focused regression.

## Disposition

**Static disposition: BLOCKED for claiming activation, NOT a confirmed probability-data defect.** The 6083-slot authority is structurally self-consistent in the current JSON and is consumed by runtime through `valid`, not through `status`. The remaining decision is release ownership: either retain `PENDING_ACTIVATION` and label the sheet pre-release, or produce a compiler-generated activation artifact with unchanged slot bytes and a complete 6083-slot receipt. No gameplay change is justified by this audit. Native validation and any activation run are **NOT_RUN** in this task.
