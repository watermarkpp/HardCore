## 二、串行驻留模型成立的前提，尚缺同步重入反证

### 普通非重入调用下，容量转换逻辑能够对应

本轮 `compile_serial_residency()` **L59–81** 明确以“当前事实全部消费后才开始下一个child”为前提，把累计成本与驻留成本分开。runtime在正常pump循环中也确实先处理due／pending，只有没有这些工作时才执行child。 

但是，`effect_runtime.gd` **L324–343** 没有pump执行中标记；**L537** 又同步调用Root，Root随后进入真实HP端口及其同步观察者。**单主线程不等于不可重入。**若观察者在当前子batch尚未封口时再次调用同一个 `pump()`，内部可以再次选取其他已排队child。

相关区别很关键：

- `_children`中的其他分支原本就是合法预留的，不需要伪造ticket。
- 子分支 `_claim_reservation()` **L174–187** 检查完整累计余量和分支资格，但没有在此扣减“仍在构造、尚未提交”的驻留fact份额。
- 驻留fact扣减发生在 `submit_batch()` **L308–316**，即目标HP处理之后。
- 普通串行路径足以控制这个窗口；同步重入则可能打破该前提。 

### 这是待原生验证的证明边界，不是已观测容量事故

本轮现有代码中的生产pump调用者仍是Root的process／physics路径；我没有找到它们自然递归调用自身的证据。因此，**不把这一项定性为现有自然玩法已经发生的容量超额**。

最小测试可以保持两个以上合法兄弟分支待执行，在第一个子batch的实际HP后观察回调中尝试重入同一个runtime，记录：

```text
尚未封口的producing分支数
当前已拥有但未提交的fact数
pending事实数与剩余驻留预留
每次claim、submit与branch退休的顺序
```

首先要证明或反证“未结束的子生产过程中能否进入下一子生产”。只有继续得到驻留超过预留、提交拒绝或事实丢失，才能报告具体容量失败；**不能只看到重入发生，就直接宣称170槽已经溢出。**

如果这个路径被允许，串行证明必须由明确的调度／所有权约束保证，而不是增加1200μs、扩大容量、强行pump或削减目标。第一节的返回值传播也必须独立修正，不能让潜在提交失败继续表现为成功。

### 已测分支退休不依赖TTL／LRU

正常Root路径中的交接为：

```text

→ available
→ producing
→ batch封口并转移为queued
```
