## Source call chain and gate semantics

1. `EnemyActor._launch_physical_projectile` (`scripts/enemy.gd:5259-5337`) creates a release descriptor freezing source/target instance IDs, life/generation, combat epoch, map, damage and target world position. The ID62 receipt contains `damage=7`, `runtime_map_id=1`, source life `1`, target life `0`, target generation `-1`, and target instance `193894287140`.
2. `MonsterRangedProjectileEffect._advance_flight` (`scripts/monster_ranged_projectile_effect.gd:183-221`) ray-tests `WORLD_LAYER | PLAYER_LAYER` and accepts a physical target only when `(collider is PlayerCharacter or SummonActor)` **and** `collider.instance_id == release_descriptor.target_instance_id` (`:199-207`). It calls `_finish(...)` before calling the source actor (`:208-215`).
3. `EnemyActor._on_physical_projectile_contact` (`scripts/enemy.gd:5358-5369`) returns on source combat disabled, target ID mismatch, or `_physical_projectile_release_target_is_valid` false. Only after those gates does it call `_apply_attack_damage`.
4. `_physical_projectile_release_target_is_valid` (`scripts/enemy.gd:5413-5435`) checks body validity/life/generation, source and target map, safe zone, combat epoch, dying/dead state, and positive HP. The diagnostic's direct call against the intended player was true; it does not prove validity for the collider that the ray actually hit.
5. `_apply_attack_damage_impl` (`scripts/enemy.gd:~5810-5900`) writes `last_physical_hit_resolution` before target damage resolution. Therefore an empty `last_physical_hit_resolution` proves this run did not reach the physical-hit admission branch for the intended target; it is not an incoming-damage/evasion result.

## Classification

**Confirmed fixture/scene contamination, production behavior not yet implicated.** The ray found a body, but the body ID is not the frozen target ID. Since `target_contact` is false on this exact identity comparison, the effect finishes as a miss and never calls `_on_physical_projectile_contact`; this explains both unchanged HP and the empty hit dictionary. The ID62 failure is therefore an actor-delivery identity failure, not evidence that ID62's physical damage formula or the seven production-script diff broke.

The test creates a fresh `PlayerCharacter` at `(4,0)` on every iteration (`tests/monster_physical_projectile_attack_test.gd:39-45`) and queues it only at the end (`:189-194`). The scene itself contains only the test node, so the most likely source of the old `CharacterBody2D#...` is a queued prior player whose physics-server body remains query-visible until a physics synchronization step. `process_frame` alone is not evidence that the previous body has retired from direct-space queries. The repeated old collider ID across different target instance IDs supports this, but the current receipt does not yet include collider class/instance ancestry or a physics-sync receipt, so label this as **FAIL / root cause highly supported, not source fix proven**.

This is not currently attributable to a “missing B01 body/source lease”: the intended player has a real `PlayerCharacter` body, the release record is populated, and the direct release-validity check is true. The missing contract is target-body isolation/retirement between per-ID iterations. Do not force `target_contact`, change the target ID, bypass the admission predicate, or weaken the HP assertion.

## Root-cause ordering from the completed diagnostic run

The run's first failure is actually ID42 at `tests/monster_physical_projectile_attack_test.gd:132`: `_descriptors.size()` was `3` when the fixture expected the third release (`5` is the later wall case; the third-release checkpoint is `3`). The process then continued after assertion failure, leaving the ID42 player queued for cleanup. ID50 and ID62 subsequently ray-hit the same old collider ID `178643797471`, while their live release targets were different. Thus the ID62 error is a **secondary cascade**, not an independent ID62 production failure.

The first failure occurs after the test manually sets `_attack_timer = 0.0` and calls `_physics_process(0.01)` (`:128-131`, with the same pattern at `:112-114`, `:142-144`, `:154-157`). `_advance_release` only loops until `_pending_attack_release_record` becomes empty (`:197-203`); it does not prove that the actor accepted a new action/release under the complete attack-state contract. The fixture is directly manipulating a private timer while reusing the same actor and while prior projectile/effect/physics state is still being retired. The correct fixture repair is to advance the real actor through its ordinary release cadence (or wait on the formal release signal with a bounded 30-second timeout), then synchronize physics before the next target is created. Do not force `_attack_timer`, invoke the callback directly, or alter the descriptor count assertion.

A valid regression receipt must first show ID42's third release admitted, then after target cleanup/physics synchronization show each later ray collider's ID equal to its own frozen `target_instance_id`. Until that ordering is restored, ID62 remains `FAIL (downstream fixture contamination)` and cannot be used to justify a production projectile change.
