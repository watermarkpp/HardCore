## 一、F：首次测得583333μs，不能保证第二次也恰好跨越相同的模拟时间

### 当前夹具已经做了什么

现在的测试不是简单拿600000μs倒推第二次输入。它已经从第一批真实状态中求出：

```text
first_effect_started = expires − 原状态 duration
observed_latency = first_effect_started − first_input
second_input_threshold = first_expiry − observed_latency
```

因此，**“改成使用第一次实测起手延迟”不是下一步修复建议——当前代码已经这样做了。**

F 的失败可以写成一个非常直接的等式：

```text
第一次观测延迟 L1 = 583333μs
第二次实际延迟 L2 = 4600000 − 4000000 = 600000μs

死亡相对预计到期的偏差
= L2 − L1
= 16667μs
```

这解释了为什么预测值正确代入了公式，最终仍然晚一个 physics tick。归档同时保留了 live FAIL 和 cold 拒绝失败 producer，处理方向是正确的。

### 原因不是“600ms参数被改坏了”

Player 的正式延迟释放仍经过 `SceneTreeTimer`。而默认 `create_timer()` 使用 process 帧更新，且在节点处理之后更新；Root 的效果模拟钟在 `_physics_process()` 中推进。**两者的更新阶段和量化边界不同。**一次施法映射到 Root 模拟钟上的偏移，不是下一次施法的固定契约。  :chatgpt-content-reference{index="8"}

我的判断是：

**这次16667μs偏差首先证明“当前实时夹具不能稳定保证严格同 tick”，没有单独证明玩家起手时长或正常技能释放存在生产故障。**不应为此把生产 Timer 改成 physics Timer，也不应把原600ms改成583.333ms，更不能把严格相等改成允许一帧误差后宣布原边界通过。

## 二、G：fixed-fps不是实时60帧，但迟到存在更具体的解释

### 时钟环境的判断成立

官方文档明确说明 `--fixed-fps` 会关闭实时同步。因此，“process delta都是1/60、physics为60、`max_fps=60`”只能证明相关配置和观测值，不能直接证明每个实际循环耗时约16.67ms。:chatgpt-content-reference{index="9"}

我对固定提交中的原始 trace 做了只读解析。`paced60` 两个场景的 `wall_usec` 中位数分别约为 **1149.5μs、1316μs**，确实不是墙钟60帧运行。它们不能拿来判断 Android帧率、GPU性能或自然战斗中的实际卡顿。

**但这不意味着2966667μs、1966667μs可以作为“测试跑得太快”的噪声直接忽略。**

实际消费点的迟到计算是：

```text
当前 simulation_usec − 该状态原定 next_due
```

而且是在进入实际周期伤害端口前记录，不是只观察消费后剩余的堆积。因而它测到的是**效果在自己的模拟时间线上迟到了多久**；不能用墙钟跑得快把该值换算缩小。

### 我独立重算到了一个很有辨识度的结果

对 `paced60` 的相邻 `samples.ticks` 做差：

- burst：一次增加2，其余358次各增加1，总共360次；
- overlap：一次增加2，其余180次各增加1，总共182次。

无 `--max-fps` 的固定步进探针也呈现相同的这组投递增量。实时 F 同样主要是每个观察间隔增加一次，并不是进入 fixed-fps 后才出现这种服务形态。这里的样本由测试 `_process()` 逐帧采集；差分不是完整的预算准入日志，但足以暴露吞吐特征。

我随后单独做了一个**数值模型，不是原生测试**：

> 第一批 due 开始时投递2次，此后每个1/60秒的模拟帧投递1次；90个状态每隔原1秒各产生一次投递需求。

结果如下：

| 指标 | 该模型计算结果 | G 的归档结果 |
|---|---:|---:|
| 完整360次投递中的最大迟到 | 2966667μs | 2966667μs |
| 到原定最终到期时已完成的投递数 | 182次 | 182次 |
| 这182次中的最大迟到 | 1966667μs | 1966667μs |

归档中的三个对应量及两个 live 的迟到失败均可在快照说明中核对。

例如，完整场景最后一次投递的模型迟到为：

\[
\frac{360-2}{60}-3
=2.966666\ldots\text{秒}
\]

**三个量同时精确吻合，远比“可能是异步资源慢了”更有解释力。**它强烈指向一个与 process 帧数绑定的服务瓶颈。最后还需要补的证据是：这些未获准继续执行的时刻，究竟被哪个类别、哪条条件拒绝。

## 三、源码中与这个模型吻合的调度链

### 1. Root没有漏掉前置 physics pump

当前 `_physics_process()` 的相关逻辑确实已经在前部执行：

```text
runtime.has_work()
→ advance_simulation(delta)
→ runtime.pump()
```

`_process()` 中则先执行包括死亡、资源在内的服务，资源 `poll_once()` 后还会补一次同一 runtime 的 pump。这次补 pump不推进模拟钟，也不创建新预算。**“把 physics pump移到前面”不是本次有效建议。**

### 2. EffectRuntime本身允许一次pump连续处理多个任务

`pump()` 以 `_pending > 0 or has_due()` 判断是否有当前可处理工作，在循环里逐次申请预算；每个成功准入的量子处理一个事实或一个周期 tick，结束计费后继续申请。

因此，**“每帧近似只投递一次”不是这里写死了每帧一个任务。**另外，当前代码已经区分了“有未来状态”和“现在有due工作”，不应再把“未来状态也一直占公平轮次”当作这份源码的既成缺陷。

### 3. 公平排序会等待“更久没有服务”的类别

`FrameBudget.begin()` 对普通工作同时检查剩余额度与 `_fair_turn()`。后者比较：

```text
last_service_epoch
→ last_service_sequence
→ 初始登记 sequence
```

`end()` 在外层量子完成后更新服务顺序。**所以额度尚未耗尽，并不代表下一个效果量子一定能获准。**当前 `denied` 将额度拒绝与公平拒绝合在一个计数中，单看它不能归因。

### 4. 资源侧存在“本帧不能再轮询，但仍参与公平排序”的组合

资源类别在有 `_threaded_profile_requests` **或** `_visual_subscriptions` 时保持 pending，并传入 `runnable=true`。正式 `poll_once(frame_id)` 成功后，会再次按同样条件登记；而同帧再次调用，会因 `_last_streaming_poll_frame` 相同直接返回。

这会形成如下服务序列：

```text
资源本帧成功轮询
→ 效果获准处理一个量子
→ 效果的最近服务顺序更新得比资源更晚
→ 效果再申请时，公平排序要求先让资源获得下一轮
→ 但资源本帧已轮询过，不能再次执行
→ 后续效果工作只能等待下一process帧
```

这里的根本问题是：

> **“这个生产者还存在待管理对象”不等于“这个生产者现在还能执行下一次服务”。**

当前 `_eligible()` 检查了 runnable、暂停、owner存活、是否在树和处理开关，但这些检查并不能识别资源服务内部的“本帧已完成一次轮询”状态。

**这是可以从源码确认的调度风险，也是本轮数据最支持的根因候选。**不过，在补到“实际拒绝原因＋阻挡类别＋当时剩余额度”之前，我不把每一次迟到都归结为这一条，更不声称已经排除了真实量子耗尽预算的共同作用。

## 四、主控下一步：补一次能裁决因果的观测，而不是继续盲改

建议只在**效果有due工作但 `begin()` 返回0**时，采集一个有上限的小型诊断记录：

```text
process epoch、physics frame、simulation_usec
remaining/spent/inflight budget
拒绝原因：额度不足 / 公平等待 / 当前不可运行
公平等待的具体category及双方最近服务epoch、sequence
该资源服务的last_streaming_poll_frame
资源请求数、视觉订阅数
当前due数量和最早next_due
```

重点是把现有合并的 `denied` 拆出原因，避免每帧全量打印造成新的扰动。这是基于当前准入代码提出的观测方案。

**可证伪预测如下：**

| 观察结果 | 对本轮判断的意义 |
|---|---|
| 效果仍有due、额度有余，但被本帧已轮询的资源类别挡住 | 直接支持“不可再次服务的生产者占住公平轮次” |
| 拒绝主要发生在额度已耗尽，且没有上述阻挡链 | 不能按资源公平问题定案，应找实际耗时最大的量子 |
| 阻挡者主要是另一个类别 | 沿该类别核对“登记为runnable”和“实际能执行”的一致性 |
| 修正生产者当前可执行性后，多次效果投递恢复，原额度与其他服务年龄仍受控 | 才构成修复方向的闭环证据 |

### 修复方向应是“准入资格准确”，不是“取消公平”

如果第一项得到确认，最小方向应当是：

**本帧已完成唯一轮询机会的服务，不再阻挡同帧其他可执行服务；到下一个实际epoch恢复其应有轮次。**

这不能简化成永久取消资源 pending，也不能因为它暂时没有完成的纹理就停止必要轮询。应继续保证资源完成、死亡结算、持久化都能获得服务；既有1200μs墙钟额度、在途计费和 owner生命周期判断也应保留。

尤其需要覆盖“资源在同帧新到达”“本帧资源准入被拒绝、随后获得轮次”“持续效果压力下资源/死亡/保存不能饿死”。**不要通过伪造frame id、重复重置预算，或让一次成功轮询后的空调用反复刷新公平顺序来制造吞吐。**

## 五、严格同tick的稳定构造：固定输入阶段，而非继续校准一次延迟

### 保留两条不同的验证线

**固定步进线**用于严格时间边界构造；**实时线**用于实际服务能力与时延。G 的失败仍必须保留，但 fixed-fps场景不应兼任实时帧率证明。官方对固定步进的说明和当前归档也都支持这种区分。:chatgpt-content-reference{index="19"}

### 建议的生产输入构造法

在静态边界夹具中，把两次 `_try_release_skill()` 都从**同一个明确的process回调阶段**发出，而不是只保证它们各自在某次协程恢复后发出。

保持官方固定步进、正式Player Timer、原600ms起手、原period/duration、原planner及30个接收者不变。第一次输入后取得原状态持续时间；第二次输入与第一次输入相隔该持续时间，并在相同回调阶段执行。当前原持续时间为4秒，对应60Hz下240个固定步进，但应从原状态定义推导并核验整除关系，不另设一个业务时长。当前测试已经读取真实状态duration，具备这个构造基础。

构造的依据是：

\[
E=I_1+L_1+D,\qquad R_2=I_2+L_2
\]

若两次输入处在相同固定步进阶段，获得相同的Timer量化偏移 \(L_1=L_2\)，再令 \(I_2-I_1=D\)，便有 \(R_2=E\)。

**改进点是“相同输入阶段＋固定步进下可重复的量化关系”，不是再把600ms换成第一次测得的583333μs。**后者已经存在，而且F已经反证它在实时环境中不足以保证严格相等。

实际结果仍必须检查：两次接受与释放时刻、process/physics帧号、原始expires、死亡快照严格相等。不能只因预定了240帧就算构造成功，也不能筛选偶然命中的运行。

### 必须独立保留“同tick”和“还有due积压”两个断言

这里有一个重要的后续风险：

**调度吞吐修好以后，原来靠服务受阻留下的due积压可能减少甚至被提前排空。**

因此，死亡发生在原最终到期tick，与该刻仍有未消费due，是两个不同条件。当前源码正好分别检查二者，应继续保留。

如果吞吐修复后第二个条件不再成立，应诚实报告“严格时间相等成立，但指定积压并存未构造出来”，再研究合法的生产工作到达顺序；**不能为了保住旧快照形态，人为阻塞pump、缩预算或插入等待。**

实时线则不应再用第一次Timer偏移预测第二次必然相同。它负责检验真实时钟下原投递迟到约束、结算一致性和服务公平性；要做实时60帧对照，应关闭fixed-fps，并用实际墙钟采样证明节奏，而非仅记录一个配置值。
