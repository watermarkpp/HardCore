# NO_PLAN_FAILURE_AUDIT hook review

Review basis: fixed107 stock `enemy.gd` at Git `edae6fdef6a6551a951fab1ea8c6ade43359d603`, plus Pro10 guidance in `docs/review/crowd_grid_research_20261008/PRO_RESPONSE_ROUND10_20261009.md`. This note defines a bounded passive diagnostic surface. It does not authorize a negative-result cache, a provider/query, a scan, a branch short-circuit, or a return-value change.

## What the audit must call a complete failure

`_hc_neighbor_internal` has an entry wait return at `scripts/enemy.gd:9940-9950`, context/observation failure at `:9952-9956`, direct-path returns at `:10000-10052`, budget/deadline returns at `:10055-10080`, route/pending returns at `:10090-10172`, and the blocked chooser at `:10202-10290`. These are different outcomes. A diagnostic must preserve them as separate branch facts.

The only bounded `NO_PLAN` candidate is: the actor entered `_hc_choose_blocked_neighbor`, the original far/near branch ran to completion, every existing fallback in that branch was attempted in its original order, and the function returned `Vector2i.ZERO`. For far pursuit this means `_hc_far_approach_waypoint` returned non-finite, `_hc_contact_flank` returned non-finite, and the final return at `:10220-10228` was zero. For the near branch it means the batched/local candidate loop completed with `best == Vector2i.ZERO`, the ordinary-melee `_hc_contact_flank` fallback (when applicable) returned non-finite, and the final return at `:10280-10290` was zero. A `ZERO` from the entry wait, retry deadline, decision budget, missing context, investigation/path pending, or a non-chooser return is not a complete local-plan failure.

Do not infer this from `_hc_last_reason`. `FRONTLINE_BLOCKED` is assigned at `:10222` before a possible contact fallback and at `:10265` even when `best != Vector2i.ZERO`; it is a classification string, not proof that no candidate was returned. Do not infer it from an empty route, zero blocker id, or a stale wait record either.

## Permitted hook points and values

1. **Entry classification after existing early wait, before any new query** (`:9935-9956`). Record only whether the existing wait guard returned, whether context was available, and the existing target/self/known-position state. If the guard returns, emit the branch outcome and stop. Do not call target projection or any provider beyond the projection already performed by the guard.

2. **Common local context after `_hc_sync_navigation` and `_hc_refresh_observation`** (`:9957-9970`). If the current invocation reaches this point, record the already computed `anchor`, `victim_anchor`, `far_approach`, `cell`, and `preferred` values, plus the existing world/map generation identifiers. These are scalar geometry inputs useful for later comparison. They must be copied as scalars; do not retain the live target or an array reference.

3. **Direct candidate branch** (`:10000-10052`). A passive sink may receive the existing `intended`, `next`, `neighbor`, `_hc_step_override`, and the booleans/results already evaluated for motion, polygon, edge, point-walkability, and (where reached) frontline. The hook must not invoke `_hc_motion_clear`, `_hc_frontline_at`, polygon, edge, point, or target-radius helpers again. The existing direct success return remains unchanged. If the branch falls through, retain the reason for fall-through as a field, not as a synthesized failure claim.

4. **Blocked chooser entry and far branch** (`:10202-10228`). Record `far_approach` and the two existing result booleans: `_hc_far_approach_waypoint` finite and `_hc_contact_flank` finite. For a returned waypoint, record the already assigned `_hc_step_override`/waypoint geometry and mark `completed_plan=false`; for two non-finite results followed by zero, mark `completed_plan=true`, `fallback_exhausted=true`, `result_zero=true`. The hook must not inspect or rerun each internal candidate check in either helper.

5. **Blocked chooser near branch** (`:10230-10290`, with helpers `:10390-10425`). Record only values already present after the batch: whether `_hc_prepare_flank_batch` completed, the batch’s option-offset/scratch cardinalities, the final `best`, and whether the ordinary-melee contact fallback returned a finite point. The sink may receive scalar candidate geometry and reject flags from the worker’s already-consumed batch record, provided the sink copies them synchronously. It must not call `spatial_index` or re-read `spatial_index_position`, `can_receive_damage`, radii, world-collision metadata, or any target/provider method. If every tested option is rejected and contact fallback is non-finite, then and only then is the near chooser a completed zero result.

6. **Post-return envelope**. Record the actual returned `Vector2i`, whether `_hc_step_override` is finite, and whether `_hc_blocked_wait_target_id` was written. This is an observation of the original result, not a second eligibility decision. In particular, a successful contact or best option followed by a `FRONTLINE_BLOCKED` reason must remain a success in the audit.

## Values that are unsafe to read early

- Target position, target radius, self position, peer position, `can_receive_damage`, `worldCollision`, environment/provider revisions, and polygon/edge state can affect current geometry or eligibility. Reading any of them before the original call changes the query count/order and can create the very diagnostic perturbation under audit.
- `victim_anchor` is the already observed anchor used for branch geometry. It is not interchangeable with a later live target projection. The far wait record also stores a victim anchor (`:10223-10226`), while the entry guard compares a live target projection (`:9941-9949`); the audit must retain both values and classify mismatch without claiming target-only invalidation.
- `_hc_flank_outputs`, `_hc_motion_scratch`, and `_hc_contact_flank_scratch` are mutable working arrays. Never enqueue them or their Node references for later use. Copy only bounded scalar counts, candidate option indices, endpoint vectors, reject bits, and IDs synchronously at the hook boundary. A hook must not clear or refill these arrays.
- Do not use `_hc_last_reason == "FRONTLINE_BLOCKED"` as a failure filter. It is written on both failed and successful chooser outcomes. Do not treat budget waits, path-pending, investigation waits, or static direct-path rejection as completed no-plan failures.

## Required result fields and stop condition

Each emitted observation should include branch (`entry_wait`, `context`, `direct`, `far`, `near`, `route`), actual return, `completed_plan`, `fallback_exhausted`, `far_approach_found`, `contact_fallback_found`, batch completion/cardinality, the scalar current/anchor/victim geometry already used, target identity, self identity, map/generation, and the existing deadline/budget flags. Use `NOT_MEASURED` for certificate/replay cost; do not report a projected optimization or zero-cost cache.

The audit can close the hypothesis if complete zero-result chooser calls are rare, target-only wait invalidation is rare, or the copied candidate geometry/rejection facts differ. If repeated facts exist, report only the parent call-time envelope; that envelope still includes mandatory observation, budget, and fallback work. Any future cache proposal requires a separate proof of its retained candidate set and hard rejection predicates.

## Review of the current passive-hook diff

Reviewed the research-tree `scripts/enemy.gd` hook diff and `tests/support/no_plan_failure_audit_20261009.gd` sink. The production diff retains the original wait-guard `Time.get_ticks_msec()` call as one read (`:9954-9961`), adds no provider/spatial query, and leaves the original chooser returns, decision-budget operations, wait writes, and performance counter calls in place. `RuntimeDiagnostics.end_timed_segment` returns the elapsed integer, so assigning that existing return for the sink does not add a second timing operation.

The source-side complete-failure events are emitted only after the far approach and contact fallback both return non-finite (`:10250-10260`), or after the near candidate loop and ordinary-melee contact fallback return no result (`:10304-10326`). That is the correct bounded placement. The sink’s `complete_failure` flag is therefore acceptable for this frozen source, but a future sink should also require the completed chooser branch and actual zero result itself rather than trusting an event label alone.

Two diagnostic coverage defects must remain visible before the run. The source emits `chooser_enter` at `:10233`, while the sink summary asks for `chooser_entered`; its `chooser_entered` count will consequently remain zero. The sink also asks for an `envelope` event, but the source emits no event with that name, so that count is likewise always zero. These do not alter production behavior, but they make those summary fields unusable until the names/contract are aligned.

The `motion_hard_reject` payload (`:10376-10377`) contains only segment endpoints, the current peer point, and the summed radius. It omits peer identity, individual peer radius, eligibility/world-collision family, and which exact helper/query produced the rejection. That is adequate as an observation, not as a repeat certificate. The audit must keep repeated geometry/rejection evidence `UNPROVEN`; matching `a,b,c,sum_radius` cannot establish the same blocker or the same hard-rejection predicate.

Coverage is also intentionally incomplete: `_hc_motion_clear` failures in the far approach/contact/direct paths, pre-filtered static failures in `_hc_prepare_flank_batch`, destination failures, and frontline failures are not all represented by a hard-reject event with their full predicate inputs. The emitted `far_candidate`, `near_candidate`, `near_motion_reject`, and `near_destination_reject` events can show branch progress, but they cannot turn a repeated candidate shape into a safe reusable failure proof. This is acceptable for the diagnostic run only if the report explicitly labels those families `UNPROVEN` and does not claim a certificate.
