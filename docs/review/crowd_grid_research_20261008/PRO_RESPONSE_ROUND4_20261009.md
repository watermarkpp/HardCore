## 二、最小值得调查的生产entry：完整普通近战执行，但不是“把整个actor搬走”

我认可你选的**target维护之后进入ordinary melee quantum**，作为当前最小的候选边界。它避免同时改目标搜索、状态更新、伤害时钟和整个actor生命周期。

但这个entry必须覆盖下面四块，才有资格讨论大幅收益：

| 执行块 | 对应源码范围 | 真正需要进入融合/原生核心的内容 |
|---|---|---|
| 近战主分支 | `_hc_tick_melee()` | 就绪/保持/追击分支、已知目标与真实目标的使用区别、当前步是否继续 |
| 新步选择 | `_begin_autonomous_step_without_cadence()`及`_hc_neighbor_internal()`相关路径 | canonical leg、候选顺序、静态/动态合法性组合、waypoint与route选择 |
| 已提交步推进 | `_advance_autonomous_step_internal()` | 移动前后判断、距离预算、到达/阻塞分类、剩余时间与后续subleg |
| 实际数值循环 | `_hc_motion_candidates()`及前排、终点、flank计算 | **整个候选遍历与精确几何体**，不是只迁移`core_crossed()`这个末端调用 |

源码里，近战循环只有在没有活动步时才选择新步；每次推进后用真实位移消耗剩余时间，最多检查16个subleg，并可能提前结束。**这些构成一个连续的执行域，而不是16个都必然执行的任务。**

### 为什么不能只做stepSelection/neighbor原生化

你的调用量里，推进7350次，neighbor约970次。新步选择虽然单次重，但大量tick是在推进既有步。只迁移选择器，会留下大部分高频推进链；只迁移身体末端公式，又会留下候选准备、对象读取、分支和跨层调用。

身体循环现在确实包含对象筛选、地图检查、计数、其他actor正式位置读取、包络剔除、资格检查，最后才调用精确几何。**仅迁移最后一步，覆盖不到前面的执行成本。**

### 也不能用“扩大到retarget”补足纸面比例

先测这个entry的边界成本。若它不够，应该得到一个明确结论：

> **当前entry范围不足以独立承担50%目标。**

这时再依据未迁移部分的成本决定是否扩展，而不是现在为了凑到60%或80%，预先把目标维护和预算器一起重写。

## 三、最容易把native收益吃掉的问题：把“保留effects”误写成“保留整个旧helper”

这里是我认为当前设计最需要主控核对的地方。

### `_move_with_spatial_rules()`不能整体视为“引擎原生移动”

它实际依次包含：

```text
接触恢复
→ 实际原生扫掠/slide
→ 方向保护及可能回退
→ 空间索引发布
→ 实际位移与计数
→ 困魔边界检查
→ 安全区检查
→ 环境保护定时与查询
→ 可能再次回退和发布
```

这些都在源码中，不是推测。

**若native每次都yield给原封不动的`_move_with_spatial_rules()`，那么它里面的脚本guard、投影/identity读取和保护控制流仍然留在VM中。** 这样实现可以安全，但其收益范围比“完整移动quantum port”小得多。

反过来，也不能为了扩大native范围，把一次原有移动拆成十几个细碎的语言往返。

正确原则是：

> **保留外部效果及其发生顺序；纯计算可以融合。不是每个旧函数都必须成为一个effect，也不是每个纯函数都必须成为一个native调用。**

### 必须保留的effects与建议粒度

| 边界 | 必须真实发生、保持原顺序的内容 | 不应额外拆出的细碎往返 |
|---|---|---|
| 原生移动与位置提交 | 零位移恢复、实际扫掠/slide、原参数、必要回退、原位置setter和索引发布点 | 单独求方向、距离、预测终点、范围判断 |
| 观察与预算 | 原观察到期判断、scope失效、FIFO服务、`begin/end/cancel`时序 | 每读一个scope标量就yield |
| 攻击提交与结算 | 原owner的就绪提交、动作预留、release/RNG、动画/音频/伤害回调及生命周期验证 | 将kernel的一个布尔结果直接当作不可撤销的攻击授权 |
| 可能重入的provider/回调 | 未证明纯性的Callable、信号、测试hook、场景/生命周期变化 | 已验证无重入片段内反复重新取同一身份 |
| 观察与共享状态发布 | 必要计数、窗口语义、共享缓存/索引的可见状态 | 把每次纯算术中间值发布给owner |

预算器有同epoch内的owner服务额度、kind区分、scope变化和已消耗服务不退还等语义，不能只保留“最多5”这个汇总条件。

攻击路径则明确存在同步回调，并先预留动作再进入表现和结算。**continuation必须在回调前写回原逻辑此刻已经可见的状态，回调后重新读取；不能把旧状态覆盖回来。**

此外，失效后不能从quantum开头重跑已经执行过的effects。`invocation_id＋continuation位置＋effect序号`至少要能区分“尚未执行”和“已经执行”，防止重复移动、重复预留动作或重复伤害。它是调用身份，不是第二套战斗时钟。

## 四、可以合并的pure链：合并输入到结果的整段，不合并观察时机

我建议把可迁移区域分成三类，而不是不断增加getter快路。

### 1. 已验证输入上的分支与步进计算

在一个没有相关写入、没有重入的片段内，可以一次取得分类、正式self/target输入、必要scope字段，随后连续完成：

```text
范围形状判断
→ 当前步/目标方向判断
→ canonical leg与接触长度计算
→ 本次速度和位移预算
→ 预测终点
→ 原生移动返回后的推进/到达/阻塞计算
```

但中间发生真实移动，便是新的输入片段。不能让“同一个quantum”成为继续使用旧位置的理由。

还要保留两个不同位置：**推进开始位置**与**接触恢复后的`position_before_move`**。原移动保护使用后者；两者不能统一成一个`start_ground`。

### 2. 同一读片段内的候选数值循环

候选身份仍从当前完整索引查询取得，数据仍按需要读取。随后将包络剔除、精确身体判定、终点占用和相关评分计算在一段内处理，才可能避免逐候选跨VM往返。

这里有两个限制：

**不要每次打包全部34怪。** 这会把局部候选查询重新变成全体扫描。

**不要为了构建完整typed行，提前读取原本会被早期条件排除的所有昂贵字段。** 现有循环先做部分筛选、再读位置、再做包络剔除，最后才做资格与精确判定。过度预打包可能抵消循环原生化的收益。

如果候选位置/资格必须每个字段都call回GDScript才能获得，那么这一批工作的主要成本只是从旧loop搬进packing，并没有消失。

### 3. 已取得空间权威后的纯几何

可融合的是：在已验证的空间上下文中，连续消费精确坐标与半径进行计算。

不能直接宣称以下整个函数是pure：

- `_hc_world_between()`会维护缓存并在未命中时发起真实查询。
- `_hc_point_walkable()`包含上下文与缓存处理。
- `_hc_refresh_observation()`会改观察状态、已知位置、路径和预算状态。

这些包装层的必要副作用要保留，能够抽取的是其中的纯计算体。当前源码对环境revision、两个投影Callable、安全区owner/revision和导航上下文都有明确区分，不能用单个map generation替代。

**尤其不能把取得真实target ground，变成更新`_hc_known_ground`的理由。** 观察时机和追击信息权限必须继续由原owner决定。

## 五、typed packing与continuation会不会吃掉收益？会，而且现在就应测，不应凭经验忽略

两种方案共用同一语义边界时，可以写成：

\[
T_{\text{fused}}=R+P
\]

\[
T_{\text{native}}=R+B+K
\]

其中：

- \(R\)：边界外工作，以及仍由宿主执行的effects、必要读取和观察成本；
- \(P\)：融合后仍由GDScript执行的计算；
- \(B\)：原生方案新增的packing、边界调用、continuation管理与writeback；
- \(K\)：真正的native计算。

**native比融合方案快的条件只有一个：**

\[
P-K>B
\]

这与Godot官方的性能说明一致：更换语言不会自动加速已经在引擎内部执行的函数；有价值的是迁移项目自身的计算。:chatgpt-content-reference{index="10"}

### continuation不应按helper数量增长

沿用你上一轮调用量，仅“每次tick进入＋每次实际移动后继续”就已经是约一万六千次入口/恢复的量级，实际还要看观察、预算、provider和其他分支。**这只是规模估算，不是已测出的ABI调用数。**

如果每次往返总新增5微秒，两万次就是100ms；10微秒、三万次就是300ms。这些是假设算例，但说明不能只测一个空C++函数的调用耗时。

真正应记录的是：

```text
begin/resume总数
按effect种类分组的次数
输入/输出字段数与字节量
候选行打包数
重入/失效后的重建次数
```

**不能为了控制次数而给continuation加一个会拖到下一tick的预算。** 正确做法是减少不必要的边界，而不是少执行原有工作。

### packing采用什么形态

建议使用固定布局、可复用的输入/输出缓冲和少量状态标量；只写回原语义要求变化的字段。不要逐字段调用native setter，不要每个subleg都新建Dictionary，不要把整棵actor状态打包。

Packed数组有合适的紧凑存储形式，但“使用Packed数组”不等于整个ABI零拷贝；官方也区分了普通传递与从内建属性/方法取得数组的情况。因此仍要测实际接口路径，而不是仅凭类型判断。:chatgpt-content-reference{index="11"}

数值方面，GDScript的标量`float`是64位，默认`Vector2`分量却是32位；原生实现不能统一成一种精度后只要求“看起来差不多”。保留原运算顺序、精度边界、EPS和比较关系，不开会改变这些关系的数学优化。身份和版本使用整数通道，不塞进浮点数组。:chatgpt-content-reference{index="12"}

### 计数保留不意味着必须每个计数都跨一次语言

但本轮**不建议同时重构计数实现**。先保留其真实成本，把它列入\(R\)或\(B\)。

以后仅对已证明在片段内没有读取、切窗、开关变化或其他可见副作用的纯加法计数，才可能讨论等价合并；计时、慢事件阈值和窗口语义不能按同样方式处理。不能靠延迟发布到outer之外改变成绩。

## 六、我建议的单个因果实验：生产接口空桥对照，而不是预录答案或完整重写

**实验名可用`QUANTUM_ABI_SHAM`。目的只回答：这个拟采用的原生边界，是否还留得下足够的计算预算？**

它利用你正在验证的ABI，不需要先实现完整native AI，也不需要回放碰撞、伤害或预算结果。

### 两个模式，算法和effects都真实执行

| 模式 | 执行方式 |
|---|---|
| **LOCAL** | 在选定的同一entry与effect切分下，现有GDScript计算照常执行，直接使用局部输入/结果 |
| **ABI_SHAM** | 相同GDScript计算仍只执行一次；在拟采用的begin/resume处，额外经过真实布局的packing、native空桥、输出读取与writeback通路 |

空桥只转交当前这次真实计算产生的数据，不代替任何决策，不读取预录答案。两模式都真实执行原观察、FIFO、原生碰撞、索引、攻击和伤害。

**writeback必须替代对应原写入，而不是额外再写一次相同位置。** 同值setter也可能有索引或其他副作用，不能用“值没变”证明双写安全。

空桥中为了验证接口而额外进行的参考结果拷贝、校验等，要单独标记；否则`SHAM－LOCAL`测到的会包含并非正式接口必需的实验成本。这个差额首先是桥接成本估计，不天然是严格上下界。

### 同一次实验只补一张非重叠账本

不再给20个helper加高频包装。只在已选定的**大计算片段与effect边界**累计：

- \(R\)：不迁移部分及宿主effects；
- \(P\)：拟迁移的计算片段；
- \(B\)：空桥带来的额外成本估计。

同一段时间只能归入一项。保留完整outer clock、原full计数和10200 callbacks。额外边界计时本身仍属诊断开销，不能转成正式收益，也不能把它按比例均摊回函数。

若已有typed融合原型覆盖了同一范围，LOCAL应使用它，才直接回答“native相对融合还有多少空间”；否则先用原算法做LOCAL，但必须明确：**这时只测边界可行性，尚未完成native与融合方案的直接比较。**

### 这个实验为什么比再做一次getter ORACLE更有价值

它同时避免了两种误判：

**没有删掉计算来制造快窗口。** 即使空桥变慢，也是有效结果，告诉我们边界有多贵。

**没有假设所有tick inclusive都能迁移。** 实际保留在宿主的查询、预算、计数和移动保护，会落在\(R\)里。

因果对照还必须检查工作轨迹，不只是攻击16/HP167/queue0：至少包括移动/回退与索引事务、攻击提交和结算tick、观察服务与FIFO事件。若额外ABI成本通过墙钟改变了`180＋相位`的到期分支，就标记为**工作轨迹不一致，不能直接用差额解释桥接成本**；不冻结时间、不回放grant来掩盖。原观察逻辑确实使用墙钟到期时间。

### 如何据此决策

定义：

\[
K_{\max}=T_{\text{目标}}-R-B
\]

在计时口径一致、误差受控的前提下：

**若仅\(R\)就达到或超过1028.63925ms：**
当前entry与宿主保留范围无法独立达标，即使native计算趋近于零也不够。这里否定的是**当前切分和保留实现**，不是宣称游戏在现有玩法合同下永远不能优化50%。

**若\(R+B\)接近目标：**
虽然数学上可能，但留给整个native核心的时间极小。比如二者合计900ms，只剩约128.64ms；此时应计算实际需要的核心加速倍数：

\[
s_{\text{需要}}=\frac{P}{1028.63925-R-B}
\]

不能拿`core_crossed`的smoke速度替代整个核心的这个要求。

**若\(R+B\)明显低于目标，且\(P\)足够大：**
完整native quantum才获得优先施工依据。先实现上述同一边界，不顺带扩大到retarget或改观察/FIFO。

若测量误差不足以区分这三种情况，结论应是`UNKNOWN`，而不是默认继续扩大port。

## 给主控的最终执行判断

**继续完成ABI验证，但暂不以“更可能达到50%”为理由直接展开完整quantum迁移。先用同一生产entry做`QUANTUM_ABI_SHAM`，测出宿主保留成本、实际可迁移计算和真实接口成本。**

同步typed context与纯链融合应作为这个边界的共享实现基础，不再拆成一串1%级小候选；完整native则是通过边界预算门槛后，用来加速剩余整段计算的后端。

**当前没有证据支持“这份post-retarget quantum在保留所列effects后一定能达到50%”。最需要防止的不是C++算得不够快，而是把大量VM查询继续藏在owner effects和packing里，最后只有一个很快、但覆盖很小的native核心。**

最终移植仍只带执行与数据通路改动，攻击/受击合同以保护中的最新主树为准；固定研究源码里的旧source-decision攻击等待不能随port重新带回。
