## 二、最小切口：合法性检查之后，动作预留之前

当前可核对的`_hc_try_start()`顺序是：

```text
冷却、重复发动、动作占用等前置条件
→ _hc_access(hit_target) 判定当前是否允许攻击
→ _try_reserve_source_body_action(false)
→ 分配动作和release
→ 随机伤害、冷却、动画、即时或延迟结算
```

**把实验门放在`_hc_access == CLEAR`之后、`_try_reserve_source_body_action(false)`之前。** 这里尚未承诺攻击，也未抽伤害、消耗冷却或启动动画。

这样选有一个明确限制：**本轮不节省排队前的完整攻击资格检查。** 它只测试“把新攻击提交及其后续活动分散”是否值得，而不是同时测试减少资格检查频率。

### 等名额不是已经发动

待发动记录只保存请求身份和等待信息，不保存已经承诺的命中、伤害或攻击动作。

轮到时，仍在该怪物**自己的原physics调用位置**重新通过原提交条件。玩家在等待期间离开合法范围，可以导致尚未发动的请求取消；**一旦真正提交，之后的伤害和动画就继续按已保护的现行合同完成，不再受这个队列控制。**

队列不能从`_process()`主动调用怪物发动攻击，也不能跨过原actor执行顺序代它结算。

### 必须区分三种返回结果

实验接入需要区分：

```text
STARTED：原攻击已经提交
DEFERRED：当前合法，但等待调度
REJECTED：原资格检查不通过
```

**不能把`DEFERRED`直接当成普通`false`。** 原调用方可能把`false`解释为“攻击失败，继续追击或找路”，反而增加工作、改变等待行为。

`DEFERRED`只结束本次“发动攻击”的分支：合法接触位置可以等待，但不能因此跳过整个Enemy更新、停住战斗时钟、停止受伤或取消已提交移动。目标变得不合法后，退出等待，原追击逻辑继续。

## 三、避免physics补步重发预算：名额只认process epoch

新名额的唯一周期键：

```text
epoch = Engine.get_process_frames()
```

**不使用`Engine.get_physics_frames()`重置名额，也不根据`delta`累计补发“欠下的名额”。**

Godot 4.7的主循环会先执行若干physics步骤，再执行process；`_physics_frames`在每个物理步骤增加，而`_process_frames`在整个主循环后才增加。因而同一次主循环的多个physics补步，可以共享同一个名额计数。:chatgpt-content-reference{index="2"}

例如：

```text
process epoch = 100
    physics 600：已发放1次攻击名额
    physics 601：剩余名额仍为0
    physics 602：剩余名额仍为0

process epoch = 101
    才恢复为1次
```

实现时再守住三条规则：

**名额在进入原动作预留/提交之前先消耗。** 后续即使因为状态变化提交失败，也不在同epoch退还并反复重试，防止回调重入或失败循环突破限额。

**队列不持有跨帧的FrameBudget token。** 排队记录与实际执行中的计时token分开；获准后同步begin/end，不能把预算作用域挂到下一帧。

**只在观察到epoch改变时重置一次。** 不要physics入口重置一遍、`_process()`又重置一遍。无physics的process回合不积攒信用；headless下也不使用`get_frames_drawn()`，它可能一直为0。:chatgpt-content-reference{index="3"}

队列按首次请求顺序保留等待年龄，每个actor至多一个有效请求。死亡、换图、换目标或不再具备发动资格时撤销，不让失效队首堵住所有怪物；同一请求重复到达不刷新年龄。

## 四、现有两套预算怎样处理：同一时间账本，但不假装已经硬限制全部AI

你指出的冲突确实存在：

| 现有机制 | 实际含义 |
|---|---|
| `FrameBudget` | 按process epoch记时间；默认1200微秒，optional可以被拒绝 |
| `HCDecisionBudget` | 按physics epoch服务最多5个owner，内部以`necessary=true`进入FrameBudget，因此允许超过时间额度 |

**“5个owner”不是时间上限，“necessary”也不会受optional额度硬拦截。**

本轮这样闭合边界：

**新攻击不进入`HCDecisionBudget`，不继承它的5-owner名额，也不另开一份1200微秒资金。**

A、B都在同一攻击提交范围记入现有FrameBudget：

- **A**允许新攻击按原时点继续，以necessary方式记账。
- **B**必须同时满足“本process还有攻击名额”和“FrameBudget的optional准入成功”；拒绝后等待，**不得偷偷改成necessary再试一次**。

两臂共同增加的攻击记账，应明确写入probe配置，因此A是本次对照底稿，**不是未经修改的fixed107性能复测**。比较结论是“预算化攻击策略的整体效果”，不是某一个限流判断的纯执行成本。

本轮**不同时修改HCDecisionBudget的epoch或necessary语义**。否则A/B之间就不只剩“攻击是否分帧”这一项变化。

这意味着一个可能的真实结果：旧必要决策已经耗尽1200微秒，B中的新攻击持续拿不到optional预算。**这应报告为预算竞争和服务不足，不是攻击分帧成功，也不能靠补发额度掩盖。**

### 不能承诺整帧绝不超限

新攻击提交包含不可中断的同步效果。即使进入前还有预算，一次提交本身仍可能超过剩余额度。原FrameBudget是在工作结束后记入实际elapsed，并非可抢占执行器。

因此，首轮能保证的是：

> **同一process不会因physics补步重复获得攻击名额；预算拒绝后不启动新的可延后攻击。**

不能保证的是：

> **所有AI、物理、已承诺伤害和绘制加起来一定小于16.67毫秒。**

超过预算时，已提交动作继续完成，记录真实超额，停止进一步准入；不能中途取消伤害来保住时间表。

## 五、对照必须看五类结果，不能只看CPU

同一地图、怪物身份与布局、血量、掉落和输入政策，两臂都运行原300physics窗口。允许新策略导致真实轨迹、攻击量和HP不同——**这是现在要测的产品代价，不再要求它们逐帧相等，也不能把差异隐去。**

两臂使用相同60帧上限、physics频率和补步配置，记录实际process数量；不使用固定时间仿真或减少physics补步来制造稳帧。60帧上限本身只是限制，不保证实际达到60。:chatgpt-content-reference{index="7"}

| 维度 | 必须输出 |
|---|---|
| **计算成本** | 原Enemy总CPU；同process内所有physics回调的Enemy耗时之和；攻击检查、调度维护和提交耗时分别记账 |
| **帧稳定性** | process间隔p50/p95/p99/max、超过16.67/33.33ms次数；每个process实际包含几个physics步骤 |
| **攻击产出** | 提交尝试、实际发动、伤害结算、动作完成量；每process的新攻击峰值；窗口末尾尚未结算/尚未完成的动作 |
| **战斗影响** | 实际伤害总量、治疗量、玩家HP变化、药品使用时点、怪物与玩家移动；不能只看净HP |
| **服务质量** | 首次合法请求到实际提交的真实毫秒等待、process等待、预算拒绝、取消原因、未服务请求年龄及队列峰值 |

**每帧峰值必须按process聚合，不能拿单个physics步骤的最大值代替。** Godot主循环自身对部分physics指标保留的是单步骤最大值；一次画面刷新前的多个步骤总耗时，仍需在本次probe里按epoch合计。:chatgpt-content-reference{index="8"}

不能在窗口末尾强行排空攻击队列，再报告“queue0”。尚未服务的请求是结果；只统计已成功服务者的平均等待，会遗漏等待最久的那批怪物。

最低限度还需一个新契约检查：**同一process epoch连续进入多个physics回调，B最多消耗一次名额；已提交攻击的后续处理不经过限流门。** 这属于新调度规则验证，不重跑旧native实验。

## 六、如何作出决策

本次是首个有限政策对照，不是稳定60fps验收。电脑headless结果可以验证调度与CPU走势，不能代替手机渲染和帧时间结论。
