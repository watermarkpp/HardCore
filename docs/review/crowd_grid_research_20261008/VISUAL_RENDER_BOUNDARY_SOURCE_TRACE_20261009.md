# Fixed107 visual/render boundary source trace

Review scope: fixed107 source at Git `edae6fdef6a6551a951fab1ea8c6ade43359d603` (research worktree `C:/Users/Administrator/.codex/worktrees/crowd-v107-comparison/HardCore`), plus the renderer section of `project.godot`. This is a source trace only; no profiler, GUI, native, device, or test run was performed.

## Production call ownership

- `scripts/monster_visual.gd:388-400` runs `_advance_action_timers(delta)` and, when a visual has resident resources and is visible, calls `_update_animation_frame(delta)` once per process callback. This is visual-node CPU work outside the Enemy physics clock. The same method performs the fallback visual residency timer only when there is no coordinator (`:393-397`); production with a coordinator reaches residency through the coordinator poll instead.
- `scripts/monster_visual.gd:505-553` chooses `death`, `attack`, `hit`, `walk`, or `idle`, derives direction and frame, and computes a `region_rect`. It switches among `active_resources[current_state]` and applies the region only when the texture or region differs (`:550-553`). Movement is presentation state: `_hc_m30_is_walking()` reads the owner locomotion intent/melee tick or legacy ground velocity (`:1550-1561`). Entering combat changes the action state and therefore may change the selected atlas texture; moving changes the walk state/region. Neither path constructs an atlas or calls a loader per frame.
- `scripts/monster_visual.gd:620-660` is the cold activation boundary. `_activate_resources()` builds the formal mapping, calls `SourceFrames.request_profile`, then `_resources_for`; on a cache miss it leaves `active_resources` empty. On success it installs the complete five-action profile and applies the first idle render state (`:638-645`), then sends the coordinator the applied notification after the profile fields are complete (`:650-660`). Release clears the sprite texture and active profile and relinquishes its lease (`:670-689`).
- `scripts/monster_visual.gd:1060-1080` assigns `sprite.texture` only on a texture identity change and updates `region_rect` independently. The source records render-state changes, but does not expose GPU upload/completion timing. The synchronous `_load_client_texture` fallback at `:1107-1124` is explicitly a deterministic test path; it is not evidence of the production live-combat path.

## Streaming, decode, and residency boundary

- `scripts/monster_visual_streaming_coordinator.gd:948-1070` owns the visual lifecycle: registration is `R` only, `request_visual_resources` is the `R -> W` demand transition, and a cached profile is returned immediately. A cold runtime request is placed in the `runtime_demand` lane and otherwise leaves the visual on its fallback until completion.
- `scripts/monster_visual_streaming_coordinator.gd:237-279` starts at most two profile jobs. Each of the five action paths goes through `ResourceLoader.load_threaded_request`; live runtime demand has `use_sub_threads=false` (`:253-278`, `_job_use_sub_threads` at `:306-309`). This makes asynchronous resource loading/decompression work a possible source-side event during cold activation, but the source does not establish whether a particular platform performs that work on the render thread or when any GPU upload completes.
- `scripts/monster_visual_streaming_coordinator.gd:445-540` polls status and calls `ResourceLoader.load_threaded_get` for all five action atlases, validating dimensions before admission. The coordinator accounts decoded RGBA8 bytes (`:709-728`), not compressed on-disk or GPU VRAM bytes. The resulting `Texture2D` objects are admitted as one profile; the visual then assigns one selected texture through `_apply_render_state`.
- `scripts/monster_visual_streaming_coordinator.gd:696-707` evicts only unprotected LRU profiles once either the 12-profile or decoded 64 MiB bound is exceeded. Waiters, leases, bootstrap holds, and map pins are protection (`_resource_is_protected` call at `:704`). A visual release can therefore make a later cold activation reload/decode the five atlases; a live lease prevents eviction.
- `scripts/monster_visual_streaming_coordinator.gd:1404-1432` visits at most 12 visual subscriptions per coordinator poll, round-robin, and calls `streaming_residency_poll`; it does not iterate every visual each frame. The central polling path is `_poll_admitted` (`:382-430`) and is frame-budget gated. This bounds coordinator bookkeeping but does not prove an Android frame-time or GPU cost.

## Renderer and attribution boundary

`project.godot:66-72` uses `gl_compatibility` for desktop and mobile, nearest default canvas filtering, and enables ETC2/ASTC VRAM compression imports. The source contract intentionally accounts decoded RGBA8 residency; import compression and any runtime texture upload behavior remain engine/platform work outside the Enemy CPU clock.

The fixed source therefore supports this bounded conclusion: normal combat/movement animation is per-process CPU state/region selection over already resident `Texture2D` objects; cold activation, reactivation after unprotected eviction, or a profile generation change can cause five-atlas threaded load/get and subsequent texture assignment. It does not support attributing the reported phone frame rate to GPU upload, decompression, or rendering without a platform run that records those boundaries.

## One falsifiable next measurement

On one fixed107 run with identical actor count and camera path, record (a) `_update_animation_frame` calls, (b) `_apply_render_state` texture-identity changes versus region-only changes, (c) coordinator threaded request/get counts and residency evictions, and (d) platform frame-time/GPU counters. A combat/movement interval with no texture-identity changes and no request/get/eviction increments would falsify a claim that its frame cost is caused by atlas reload/upload; a cold interval with those increments would establish the source event while still requiring platform counters to classify CPU versus GPU time.
