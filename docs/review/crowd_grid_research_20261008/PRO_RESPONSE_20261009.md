## 一、先校正收益账：局部失效实际只省了约2.49ms身体检查

应当用**未加细分插桩的107数据**对比局部方案，不能用插桩后的身体检查耗时作基线。`growth_GROWTH.json` 中，107的30参战身体清空两轮均值为 **244.8965ms**。

结合你给出的局部方案两轮数据，计算如下：

| 300tick窗口 | 封装107 | 局部失效方案 | 变化 |
|---|---:|---:|---:|
| 总CPU，两轮中位数 | 2057.2785ms | 2096.7840ms | **增加39.5055ms，约1.92%** |
| 身体清空，两轮均值 | 244.8965ms | 242.4030ms | **减少2.4935ms** |
| 总CPU减去身体清空 | 1812.3820ms | 1854.3810ms | 增加41.9990ms |

**身体清空的实际节省仅相当于总CPU的约0.12%。** 因此，目前不是“身体检查大幅改善，却被神秘开销完全抵消”，而是“被优化子项本身没有产生足够大的净收益”。

两轮还不足以证明稳定的1.92%退步，但足以支持当前决策：**没有证明整体收益，不晋升。**

另外，107的30参战记录里，平均8851次身体清空查询、40280个候选检查、27656次身体检查，分别约为每次查询 **4.55个候选、3.12次身体检查**。这不符合“每次仍然遍历全部30只怪”的情况。10→30增长很快值得研究，但不能直接推导为“再换一种网格即可砍掉大半CPU”。

## 二、真正值得动的成本在哪里

细分证据中有一组扣除了**已插桩嵌套子段**的耗时。它比直接相加“移动38%＋身体12%＋原生移动”等包含关系更适合安排调查优先级。这里的数字仍然只是**插桩诊断值，不是生产性能验收值**；未单独插桩的工作仍留在最近的父段里。

| 诊断段 | 自身／未细分剩余耗时 | 下一步关注点 |
|---|---:|---|
| `ground_projection` | 347.665ms | 投影入口调用、缓存验证、实际转换分别占多少 |
| `native_move_and_guards` | 324.057ms | **不能全部当成引擎原生移动**，还含未拆开的保护工作 |
| `combat_loop` | 320.995ms | `_hc_tick_melee()` 中的重复取值、条件与状态维护 |
| `motion_body_clearance` | 270.485ms | 候选对象访问与精确几何分别占多少 |
| `advance_step` | 233.918ms | 推进过程中的重复状态读取与保护检查 |
| `target_maintenance` | 170.355ms | 当前目标维护，不等于重新搜索目标 |
| `target_observation` | 127.609ms | 等待期维护、scope构造、预算调用与真正观察分开 |
| `step_attack_readiness` | 96.222ms | 大量快速拒绝，不是大量完整攻击几何 |

**修正我前面一条过程判断：`_hc_step_can_end()` 主要通过目标、站位和攻击范围等条件快速拒绝，不是主要通过冷却状态拒绝。** 源码里先做范围判断，只有通过后才调用完整 `_hc_access(target)`。因此14651次就绪检查不能当成14651次完整的WORLD和前排阻挡查询。

同时，当前投影入口已经有自身空间索引快照复用、目标同帧精确位置缓存，以及不创建Dictionary的Vector2返回路径。**“给坐标加缓存”“去掉投影结果Dictionary”都不是这里的新方案。**

### 对50%目标的实际判断

身体清空即使完全消失，也只解决约12%。目标维护、观察和攻击资格也不能只看调用次数就当作可以全部删除。

要接近50%，应当争取的是：

> **同时压低投影入口、战斗循环、移动推进和几何循环中的重复对象访问与管理工作，同时保持真正需要的状态判断和精确碰撞。**

这是值得验证的方向，不是已经证明有50%空间。其收益必须最终回到 **≤1028.63925ms** 的完整窗口判定。

## 三、第一优先级：把同一次移动中的“重复取值”改成“直接传递结果”

### 涉及入口

`_hc_tick_melee()`、`_advance_autonomous_step()`、`_screen_position_px_to_ground_position_gu()`。

这里最直接的证据在 `_hc_tick_melee()`：每个子步读取 `leg_start`，推进后读取 `leg_end`；循环结束又分别为 `actual_ground_motion_gu` 和 `after` 连续取得当前位置投影。中间没有新的位移时，这些调用虽然可能命中缓存，仍然重复执行缓存匹配和函数入口逻辑。

**最小改法不是再造一个缓存层，而是在当前同步执行范围内复用局部变量。**

先做最小的一刀：循环末尾只取得一次真实终点，用同一个值计算 `actual_ground_motion_gu` 和后续视觉接收条件。再研究把推进后已经取得的真实 `leg_end` 传给调用方，避免调用方重新取得相同坐标。

继续扩大时，应遵守以下边界：

- **只复用实际执行后的真实终点，不把计划终点当实际终点。** 原生移动、碰撞修正、回退或对齐发生后，必须以修正后的真实位置为准。
- 重用范围先限制在无`await`、无位置写入、无可能重入的同步片段。不能简单做成“这一physics tick的位置永远不变”。
- 继续保留现有地图、代际和投影Callable的权威约束；不改成绕开正式投影的通用菱形公式。当前缓存明确包含这些条件。

这类修改不需要新增每帧Dictionary或RefCounted对象。**先用已有局部变量和必要的标量输出，避免为了减少调用又制造分配。**

### 最小证伪测量

把73274次投影入口调用拆成四个计数：自身快照命中、目标缓存命中、真正Callable转换、其他／拒绝路径。再记录“同一同步片段、相同实参连续请求”的次数。

验收看两件事：**入口调用确实减少；关闭细分计时后总CPU也下降。** 只看到实际转换数不变并不能否定这项，因为它主要针对缓存命中仍需支付的入口成本；反过来，入口次数下降但总CPU不降，也不应继续扩大改造。

## 四、第二优先级：邻居选择可以做严格的评分下界剪枝

这是当前代码里一项**具体、可证明、无需改变寻路结果**的算法机会。

### 精确位置：`_hc_choose_blocked_neighbor()`

普通近距离分支按固定邻居顺序，执行静态合法性、移动身体检查、终点占用检查，然后计算：

```text
基础成本 = endpoint到anchor的距离 + 方向惩罚（0或0.05）
最终成本 = 基础成本 + 前排阻挡惩罚（0或2）
```

只在 `cost < best_cost` 时更新最优结果，因此同分保持原有先后顺序。

由此存在严格下界：

\[
最终成本 \ge 基础成本
\]

**某个候选的基础成本已经大于等于当前最优成本，它不可能胜出。** 可以在执行该候选的身体、终点和前排精确查询前跳过它。

概念上的调整如下，保留原邻居遍历顺序：

```text
计算 base_cost

若 base_cost 和 best_cost 都是有限值，
并且 base_cost >= best_cost：
    跳过该候选

否则：
    执行原有合法性检查
    计算原有前排惩罚
    按原有严格“小于”规则更新结果
```

### 为什么这不是偷减碰撞

这里不是让一个可能被选中的移动不检查碰撞，而是证明**这个候选无论检查结果是什么，都不可能成为最终选择**。最终选中的候选依然执行原来的完整检查。

但必须限定适用范围：

**只先改这个使用“距离＋非负惩罚”评分的分支。** 不把它套到 `_hc_far_approach_waypoint()` 的“第一个合法方向”规则，也不套到 `_hc_contact_flank()` 中优先最大脱困距离的`rear_relief`规则。后两者的排序目标不同。

当前 `_hc_prepare_flank_batch()` 已经提前构造并查询候选包络，所以第一版剪枝主要减少后续精确检查，**不会自动消除已经支付的批量查询成本**。先证明这一小步有收益，再考虑是否有必要改变预备批次的时机。

### 最小证伪测量

记录可剪枝候选数、被省去的身体／终点／前排调用数，以及原版和候选版的**最终邻居、实际step override、flank waypoint**差分。

这项适合较早执行：改动小，正确性证明明确，失败也容易撤回。**收益不能预报成几十个百分点**，因为788次邻居选择不是整个怪物循环。

## 五、第三优先级：减少同批几何中的重复对象访问，而非重复建设网格

当前已有十六包络批量查询，但后续三个消费者仍分别遍历候选：

`_hc_motion_candidates()`、`_hc_flank_destination_candidates_clear()`、`_hc_frontline_candidates()`。

它们会重复进行对象有效性、类型、地图、存活／可受伤状态、`worldCollision`、半径和`spatial_index_position()`等读取。具体判定不同，不能复用一个“是否碰撞”的布尔结果，但**相同同步查询中的输入数据有机会只取得一次**。

### 建议分两步，避免一上来建立长期快照

**第一步：同一候选池内合并移动清空与终点占用的读取。**

原来的两个精确判定都保留，只让候选的当前位置、半径和资格在这一小段同步遍历内取得一次。不能把`core_crossed()`替换成更粗的中心距离判断，也不能省掉原来的重叠退出规则。

**第二步：有充分收益证据后，才扩展到一次邻居决策内的数值输入批次。**

这个批次只为一次无重入查询服务，使用可复用容量的数组或标量记录，结束后失效。它不跨真实移动，不跨其他actor更新，更不跨地图切换、死亡、复活或身体尺寸变化。

这里有两个现实限制。

其一，目前单次查询平均只有约4.55个候选，构造批次的成本可能反而更高，必须同时测准备与消费总和。其二，现有代码已经先做保守包络剔除，再检查部分资格与精确几何；不能为了“统一准备数据”，把大量本可便宜剔除的候选提前做完整资格读取。

**这条路线的目标是减少重复访问，不是把活体位置冻结成帧快照。**

## 六、目标维护和预算器：有重复，但必须区分维护、观察和攻击权

### 1. 观察函数的重复主要发生在入口维护

`_retarget_internal()` 会调用 `_hc_refresh_observation()`，追击路径也会调用。观察函数已经有等待时间，不会每个入口都做完整LOS观察；但它在判断是否需要观察前，会构造六项Array scope：

```text
map、zone generation、自身life、目标instance ID、目标life、环境revision
```

等待期存在pending请求时，又重新构造scope调用预算器的`poll`。预算器 `_valid()` 随后通过`owner.call("_hc_decision_scope")`再次构造并比较。

**第一刀可以非常小：等待期poll直接传入本函数已经取得的`observation_scope`，不再现场构造第二份。** 再计数`_hc_decision_scope()`总调用、scope复制、预算验证调用，判断是否值得扩大。

下一步才考虑把身份scope变为稳定票据或字段化比较，减少`has_method→call→构造Array→比较Array`。票据仍必须在地图、life、目标或环境变化时立即失效；特别是环境变化导致的“旧可见性立即无效”，不能等下一次预算轮次。

### 2. 预算器里确实还有线性队列操作，但不是50%的主突破口

实际代码使用Array队列，存在`pop_front()`、`remove_at()`和`erase(id)`；`cancel()`即使没有对应请求，也继续修剪队首并发布pending状态。当前每个epoch最多服务 **5个owner**，不能为性能改动这个额度或公平性。

可测的改法是：先记录无效取消比例、队列移动元素量、重复scope复制量、pending状态未变化却重复发布的次数。只有这些确实占时，才换成带head的队列或带代际的惰性删除。

**不能简单给`cancel()`加“自己不在队列就return”。** 它现在还承担队首清理和共享pending同步；修改后必须证明不会留下失效队首、改变当帧服务对象或影响其他预算消费者。

### 3. 不能用“每帧只观察一次”作为无条件去重键

这一版 `_hc_refresh_observation()` 使用 `Time.get_ticks_msec()`，并以`180 + instance_id % 5 × 7`毫秒安排后续观察。它还会处理同帧发生的伤害脏标记、scope变化和pending轮次。**只用physics frame作去重键，会漏掉其中一些状态变化。**

因此，第一阶段建议只做**同一同步片段内**的输入复用，不提高观察间隔，不推迟失效处理，不让预算器拥有攻击权限。

## 七、局部桶失效：当前先撤出晋升路线，不再追加“已有的快路”

实际 `enemy_bucket_pool_unchanged()` 已有地图级修订快路：地图成员没有变化时直接返回；只有地图发生变化，才扫描covered Rect内的桶戳。**“先做全局／地图版本快判断，再做局部判断”已经存在，不能再作为新建议。**

当前仍可能支付的成本是：密集怪群不断跨桶，而很多怪物查询的covered Rect相互重叠，导致它们频繁进入逐桶Dictionary查询；即便最后允许复用，也已经支付了扫描成本。与此同时，窄相位实时位置与身体检查并没有减少。**这是源码支持的成本机制，但还不是已被细分计时证明的全部归因。**

继续研究这条线前，只补四组数就够了：

| 需要补的量 | 用来回答什么 |
|---|---|
| 地图级快路通过次数 | 是否大部分调用已经很便宜 |
| 实际扫描桶数总量、分布 | 验证成本究竟有多大 |
| 扫描后通过／拒绝次数 | 花了多少成本得到有效复用 |
| 候选重建与验证各自总耗时 | 省下的重建是否大于新增验证 |

只有验证扫描显著占时，才值得试整数索引／稠密桶戳数组等结构替换；同时保留空桶历史、clear代际和最大半径增长失效。**不建议现在建设反向依赖订阅系统，让每个桶维护所有候选池消费者——那可能只是把查询成本搬到大量更新通知上。**

当前决定应是：**保留研究分支和完整证据；下一项实验从明确基线起步，不把这个未获益方案作为前置依赖。**

## 八、交给主控的执行排序与验收门槛

以下按“有望覆盖的成本＋改动可控性”排序，不给没有证据的收益百分比。

| 顺序 | 最小实验 | 主要证伪条件 |
|---|---|---|
| **P1** | `_hc_tick_melee()`相同终点投影复用；再分步传递真实推进终点 | 入口调用下降，但完整CPU不降；或出现位置／移动差分 |
| **P2** | `_hc_choose_blocked_neighbor()`基础成本下界剪枝 | 最终邻居、step override或waypoint变化；或可剪枝比例过低 |
| **P3** | 同池移动与终点检查复用候选输入 | 准备成本抵消收益；精确清空结果有差异 |
| **P4** | 观察poll复用现有scope，再拆预算构造／验证成本 | 队列顺序、失效时机、实际服务延迟改变 |
| **P5** | 只在证据支持时替换桶戳存储结构 | 验证成本不是主要项，或整体CPU仍无净收益 |

### 还需要补一个不宜忽视的证据缺口

**相同seed、身份顺序和布局，不等于所有内部决策轨迹必然相同。** 这版源码用真实毫秒时间安排观察，用instance ID模数决定观察相位和绕行偏好。因此，16／17次攻击、190／185点HP损失不能单靠汇总数字解释为行为完全等价，也不能直接认定为优化改变了攻击规则。应额外记录观察到期／服务tick，以及每只怪的相位与方向偏好。

性能试验建议先用少量交错A/B排除明显失败，再对保留候选增加成对重复。正式分数关闭细分计时；诊断实验保留调用计数与少量分段计时。320.995ms的`combat_loop`剩余项和`native_move_and_guards`仍需进一步分清，必要时使用采样型原生分析补充，而不是继续给每个小函数加高频计时。Godot官方也区分了采样与插桩：未插桩代码不会自动在trace里得到细分归因。:chatgpt-content-reference{index="24"}

### 移植主树时需要两套对照，不能只跑旧研究树

**性能目标仍对封装107：≤1028.63925ms；行为正确性则对包含最新玩法修复的主树。**

建议同时保留“主树未优化→主树优化”的配对结果，用来隔离优化本身的收益。不能因为新主树工作量增加就重设50%目标，也不能为了对齐旧107的少量攻击而恢复旧攻击等待。

固定研究源码 `_hc_tick_melee()` 仍保留`SOURCE_DECISION_WAIT`和到达后的source decision gate。这与本次明确的“合法范围内就绪即攻击”不能直接混同，**移植时只带算法改动，不带旧控制流覆盖最新修复。**

行为回归至少应覆盖攻击合法／提交／结算tick、真实位移与清空判定、已提交攻击不被后续离开错误取消、受击等待攻击完成、受击动画等值暂停剩余冷却，以及不同伤害类型各自的判定时机。HP总量和攻击总数只是汇总结果，不能代替这些时序证据。

**最终建议：先执行P1和P2，各自独立测量；随后再决定是否扩大同批几何和预算器改造。局部失效停止晋升。50%目标保持不变，但必须由完整CPU与最新主树行为共同证明，不能由缓存命中率、身体检查次数或局部PASS替代。**
