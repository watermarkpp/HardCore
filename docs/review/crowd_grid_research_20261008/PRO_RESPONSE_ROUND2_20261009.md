## 一、这次应消除的是重复验证链，而不只是重复函数调用

源码能确认三条有共同依赖的重复读取链。

**第一条是分类链。** `_source176_ordinary_melee()`再次进入`_hc_standard_melee()`，后者读取delivery kind、区域攻击开关、召唤开关、远程判定及特殊投递条件。因此，`kind == ""`不能独立代替完整分类；但在这些输入没有变化的同步片段内，完整分类结果可以直接向下传递，不必每层重新读取配置。

**第二条是自身坐标证明链。**

```text
spatial_index_position()
  → _spatial_index_projection_cache_matches()
      → Callable有效性、当前位置、map、generation、
        environment revision、Callable身份比较
  → 未命中时进入_screen_position_px_to_ground_position_gu()
      → 又进入自身缓存匹配路径
```

这里的缓存已经存在。真正应该减少的是：**调用方刚证明过这些条件，下层又重新证明一次。**

**第三条是环境与scope链。** 自身投影guard、`_hc_static_query_scope()`、`_hc_decision_scope()`、`_hc_sync_navigation()`都读取环境revision。实际`WorldBackground.environment_collision_revision()`本体只是返回一个整数，前面的对象检查、动态调用以及各层scope处理才构成整条读取成本。环境revision又独立于地图generation，不能直接删掉它。

因此，你的新增计数支持调查这个结构问题，但**不能把122942次分类、114983次投影guard、133098次revision读取当作三块独立耗时相加**：它们存在嵌套。

这次重构与前面小实践的区别应当是：

> 前面是让每次验证便宜一点；这次是让一个已验证的内部调用片段，不再逐层重新验证同一批输入。

## 二、最小上下文：只装输入，不装行动许可

建议暂称 **`HCMeleeReadContext`**。这是拟新增的数据载体，不是仓库已有类型。

只为当前actor的一次外层调用服务，分成四组按需填充的数据：

| 数据组 | 建议保存 | 不应夹带的结论 |
|---|---|---|
| 分类 | 完整`standard_melee`结果、`ordinary_melee`结果、此次分类对应的delivery kind | 不保存“本帧可以攻击／可以移动” |
| 身份 | 自身map、generation、life；当前目标身份与life；按原消费者需要取得的目标generation、parent等 | 不代替攻击release的生命周期验证 |
| 空间权威 | environment对象身份、revision、原有投影Callable；需要时取得的导航、安全区上下文身份与revision | 不把地图generation当作全部空间版本 |
| 几何输入 | 精确self screen／ground、精确target screen／ground，以及各自是否已取得 | 不保存跨位移有效的LOS、身体清空或攻击资格 |

### 三项必须明确的限制

**不保存冷却、受击进度和攻击承诺。** `_attack_timer`、动作占用、pending attack、控制／魅惑／休眠等状态，仍在原位置按现行主树逻辑判断。上下文不能再形成一套影子行动状态。

**真实target ground不能代替`_hc_known_ground`。** 现有观察系统只有在观察通过或相关事件发生时才更新已知位置；追击使用的`desired_target`也明确来自surround goal或`_hc_known_ground`。上下文取得真实坐标，只能服务原本就允许读取真实位置的消费者，不能顺手让失去视线的怪物持续跟踪玩家。

**不强迫每个片段都投影self和target。** 有些分支通过早期条件就返回，有些范围判断原本使用screen差值转GU。应按需取得正式绝对坐标；否则可能把“guard很多、转换较少”优化成“guard少了、真正转换反而多了”。

还要保留原数值路径：**原本的“screen差值转GU”和“两个正式ground相减”，不要在本次重构中当作完全可交换的表达式统一掉。** 即便数学上等价，浮点运算顺序和边界判定也可能不同。这是额外行为变更，不属于本候选。

## 三、施工范围：三个owner入口，加它们内部的读值消费者

### 1. 不从整个`_physics_process_internal()`起手

这段顶部依次推进动作时钟、处理死亡、状态效果、pending伤害、目标维护及其他行为。它不是一个可以整体借用旧读值的范围。当前源码也明确在状态处理后再次检查死亡，并在后续目标维护中可能撤销或更换目标。

**首版从`_hc_tick_melee()`进入普通近战处理的局部范围开始。** 不移动它之前的状态更新，不改`_retarget_internal()`的节拍与执行顺序，也不顺带重构预算器。

三个owner是：

```text
_hc_tick_melee()
  → _advance_autonomous_step_internal()
      → _move_with_spatial_rules()
```

通过它们向内部消费者传递读上下文。**“入口检查”和“已取得输入后的核心处理”应共用实现，不要复制两份完整移动算法。**

### 2. 内部消费者怎么改

下面的“读上下文入口”均是建议新增的私有路径：

| 现有消费者 | 上下文路径应做的改变 |
|---|---|
| `_hc_standard_melee()`／`_source176_ordinary_melee()`调用点 | 在已分类的片段内直接用分类标量，不再次访问配置 |
| `_hc_step_can_end()`／`_movement_step_engagement_ready()` | 复用本片段分类与坐标；仍在原来的移动前、移动后位置执行判断 |
| `_hc_access()`的内部读值核心 | 使用本片段self／target坐标和空间scope；保留原有资格、WORLD、前排检查及顺序 |
| `_hc_static_query_scope()` | 增加从已取得标量构造／复用原scope的内部路径，不再次读取environment revision |
| 自身投影与索引同步内部路径 | 用已取得的精确位置与权威字段匹配现有快照，避免重新进入完整guard链 |

**公共`spatial_index_position()`、通用投影入口以及其他actor调用的接口先保持现状。** 不能让公共getter隐式读取一个“当前活跃上下文”，否则重入调用和其他怪物查询会误用调用者的读值。

`_hc_static_query_scope()`当前已经复用不可变Array key。这次不是再造scope缓存，也不能原地修改已经作为Dictionary key使用的Array；只是把**取得key所需字段**的重复工作移到片段入口。

### 3. GameRoot投影链先不动

本候选**不摘出GameRoot内部mapper Callable，不跨片段保存profile成功结果，也不取消live runtime identity验证**。

真正需要一次新投影时，仍走当前正式投影入口。上下文只在随后没有相关写入、没有重入的片段内，直接消费已经取得的结果。

原因很具体：`GameRoot._resolve_projection_profile_for_map()`不仅看外层Callable，还通过`MapEditorRuntimeBridge.load_map()`取得runtime identity并比较。只保存同一个外层Callable，不能证明其背后的正式地图profile始终没变。

### 4. 数据载体不能制造另一种热路径

建议每actor预分配一个typed载体，或者使用等效的局部标量传递；**不要每次helper调用新建Dictionary／Array／RefCounted，不要每个字段getter再执行一次`ensure_context()`全量验证。**

关键约束是：

> 验证发生在进入读片段时；内部消费者直接读字段。
> 一旦退出片段，旧字段便不再代表“当前值”。

用片段序号辅助诊断即可，不能把它当作世界版本。外层调用尚未结束时，重入调用不得复用同一个载体；首版可让重入路径使用原来的实时查询实现。**回退到原实现不等于暂停或等下一tick。**

## 四、刷新边界：同一tick里必须允许多次结束、重建上下文

“没有`await`”不代表不能重入。Godot普通信号连接可以立即执行回调；`CONNECT_DEFERRED`才把连接延后。你们的`_hc_try_start()`也明确标注动画／音频可能发信号，并存在admission hook同步删除目标的处理。:chatgpt-content-reference{index="12"}

### 建议首版采用的边界表

| 边界 | 首版处理 | 必须保留的语义 |
|---|---|---|
| 原生碰撞恢复、`move_and_collide()`、`move_and_slide()` | 进入前结束旧读片段；返回后按实际位置建立后续片段。未证明只写自身位置前，保守重取权威字段 | 原生碰撞调用、参数、移动预算不变 |
| `set_combat_position()`对齐、到达、回退 | 旧位置读值失效；保留setter及原索引同步事务，后续取得最终实际位置 | 不新增位置写入口，不把计划终点当实际终点 |
| `_hc_try_start()`、攻击动画、即时伤害结算、admission hook | 首版整体作为边界；调用前关闭上下文，返回后确实还需要继续读取才重建 | 冻结release record继续独立生效，不因关闭上下文取消已提交攻击 |
| 受击／伤害信号及可能反向调用攻击者的逻辑 | 进入可重入调用前关闭；返回后重新取得需要的值 | HP、受击排队、冷却暂停均按最新主树处理 |
| 目标撤销、更换、召唤物拦截接管 | 旧目标几何与身份全部失效；在原控制流允许继续的位置重建 | 不拿旧目标坐标给新目标做攻击或追击 |
| 死亡、复活、换图、generation或parent变化 | 结束旧借用；执行原生命周期失效路径 | 不能把旧调用刷新为新life后继续完成旧计划 |
| 环境revision或空间上下文变化 | 旧WORLD／导航scope失效；重新取得相应权威，触发现有导航失效处理 | 同map、同generation也不能继续相信旧revision |
| 未审计Callable、覆写方法、测试hook或其他可能改状态的外部入口 | 作为边界，或该次直接使用原实时路径 | 不能因为方法名像getter就认为它纯读 |

**关闭必须发生在回调之前，而不只是回调返回后。** 否则回调内部重入时，已经有机会读取旧上下文。

另外，`Time.get_ticks_msec()`及“某个deadline是否到期”不纳入此上下文。即使没有代码写入这些字段，时间也会继续流逝；不能为减少读取而把整段墙钟时间冻结。

### 移动里有两个不同的起点，不能合并

`_move_with_spatial_rules()`的真实顺序是：

```text
move_and_collide(Vector2.ZERO, false, safe_margin, true)
position_before_move = global_position
实际定向move_and_collide()，或move_and_slide()
方向保护与可能回退
_spatial_index_update()
困魔、安全区、环境保护与可能再次回退
```

所以至少要区分：

**推进函数的`frame_start`**：恢复前，用来描述整个推进过程。

**移动保护的`position_before_move`**：前置碰撞恢复后取得，是现有保护和部分回退逻辑的起点。

二者不能因为“都叫移动前坐标”就共用一个ctx字段。这里应保留命名明确的历史局部值；它们可以跨位移保存，但不能再冒充位移后的当前坐标。

### 索引更新不能延迟到整次actor执行结束

当前移动后会发布索引，后续回退又通过`set_combat_position()`同步索引；`RuntimeCombatSpatialIndex.update_actor()`负责更新位置及跨桶成员关系。上下文重构可以减少取得这些输入的重复工作，**不能为了只发布一次而改变当前发布点**。

## 五、这项候选的真正施工边界

我建议把首版约束为：

> **仅对已进入普通近战的owner调用链，增加显式读上下文；公共查询、伤害结算、决策预算、原生移动算法、精确碰撞算法均不改。**

`_hc_refresh_observation()`、新步规划和其他尚未完成纯性核对的调用，首版允许在它们前后断开片段。不要为了追求“一次actor执行只构建一次ctx”，把它们强行包进去。

这会留下部分开销，但好处是重构的行为证明可以收敛。以后只有在确认某个函数**不会修改上下文依赖、不会重入**后，才扩大一个读片段，而不是先扩大再找失效漏洞。

特别注意两个容易让这项候选失真的情况。

**不能把114983次guard全部记为可消除。** 身体和前排检查会读取其他怪物的`spatial_index_position()`。自身／当前目标上下文不覆盖所有邻居；首版必须保留这些公共读取，不能拿本actor的life、Callable或空间证明替邻居担保。现有候选消费者确实逐个读取其他actor的实时位置与资格。

**不能把重构后的入口判断当成攻击授权。** 例如，当前`_target_candidate_is_live()`还检查玩家死亡、HP、切图状态，以及目标地图。身份字段的复用不意味着这些行动资格判断可以不再执行；最多是让其内部不重复构造已经取得的输入。

你正在做的P1最终真实终点接口，可以作为这里的输入来源；**不再另外设计一套终点缓存，也不把P1收益重复计入上下文候选。**

## 六、收益判断，以及下一块必须调查的具体成本

### 不能据调用数给它预算50%

目前不能从这些数据算出可靠的“上下文可削减成本占总CPU多少”。96%插桩开销尤其不能按统一比例平摊回各个函数。Godot官方也明确提醒，计时型profiler本身可能显著拖慢运行，应当以重复的实际测量确认优化效果。:chatgpt-content-reference{index="21"}

这项的数学门槛可以明确：

\[
\text{总CPU下降比例}
=
\text{所覆盖的真实耗时占比}
\times
\text{该部分削减比例}
-
\text{新增上下文成本占比}
\]

即使覆盖部分能减少 **80%**，要单项实现总CPU减少 **50%**，它也必须覆盖原总耗时至少 **62.5%**，还没计算构建与刷新成本。

**现有证据没有证明这些可重复读取工作占到这个比例。** 首版又明确不覆盖全部邻居读取、精确几何和原生碰撞，因此我不把它作为单项达成50%的方案。另一方面，也不能凭前面两个1%左右的小实践，就断言整条验证链下沉没有较大空间——那两个候选并没有实施这次的边界传值结构。

### 下一块只指定一个：`_move_with_spatial_rules()`的原生移动与索引发布段

这里有一个已经从源码确认、会影响成本判断的问题：

**`move_and_slide_usec`不是完整原生碰撞成本。**

它的计时开始于前置零位移`move_and_collide()`之后，所以**漏计碰撞恢复**；结束于`_spatial_index_update()`之后，所以又**包含索引同步及其相关读取**。有些路径执行的还不是`move_and_slide()`，而是定向`move_and_collide()`。

因此，上下文候选之后，下一块应明确区分：

```text
前置碰撞恢复
实际定向扫掠／slide
方向保护与位置回退
索引同步及正式投影
```

**先确认这四部分的真实成本，不先删前置恢复，也不先改碰撞模式。** 前置恢复目前承担接触分离职责，不能把少做它直接作为算法优化。上下文下降后若这一段成为主要剩余成本，才能讨论如何在保持现有恢复、扫掠和碰撞结果的前提下减少重复处理。

### 随现有运行保留少数计数即可

不需要再开20段高频计时。主控可在已有300tick运行里，保留以下几类整数计数用于证伪：

| 计数 | 要回答的问题 |
|---|---|
| 读片段构建数、按原因分类的结束／刷新数 | 是否被大量边界打碎，构建成本失控 |
| 受覆盖路径中的实际分类、revision读取、self／target投影次数 | 是否真正消除了完整验证链，而非换了函数名 |
| 自身读取与邻居读取的分开计数 | 到底覆盖了多少原有guard |
| 重入／未知provider回退、上下文一致性异常 | 安全边界是否确实生效 |

正式总CPU仍在相同统计边界内测量：**构建、刷新、回退全部计入怪物系统成本，不能挪到GameRoot外层后宣称节省。**

**给主控的最终判断：这项可以作为P1/P2之后的独立结构性候选施工，但应以“分段取得输入、内部直接消费”为核心，拒绝整帧快照和隐式全局快路。它是否有明显收益尚待实测；50%没有单项依据。下一块锁定`_move_with_spatial_rules()`中目前计时混合且漏项的碰撞恢复—实际移动—索引同步段。**
