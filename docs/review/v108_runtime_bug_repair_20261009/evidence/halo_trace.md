# v108 passive halo / dense wake trace (read-only)

**Scope and binding.** This is a source-only review of release-v108 baseline `92c6eeb93af9546b891ea0a1a15dd4f8c600502b9` in the current MAIN checkout. No engine or test was run and no production file was edited. The observed user symptom is “a dense halo wakes only 1–2 monsters” and “firewall damage leaves a packed group inert.” The conclusions below separate a proven source limit from hypotheses that require a dense native receipt.

## Actual wake chain

1. `GameRoot._on_player_moved()` (`scripts/game_root.gd:6540-6543`) calls `_mark_passive_monster_wakeup_dirty()`. Player and SummonActor emitters are registered at `:1639` and `:11689/:12128`; `_passive_wake_emitter_current()` (`:6546-6568`) rejects dead, wrong-map, teleported, expired or hidden emitters.
2. `_mark_passive_monster_wakeup_dirty()` (`:6634-6678`) puts a dirty emitter id in FIFO and marks `FrameBudget` category `monster_passive_wakeup`. It does not do a group scan. If an emitter becomes invalid while it is active, it explicitly clears the current candidate array/cursor (`:6657-6664`); this is a real loss of that in-flight page, followed by a fresh query. Ordinary player movement alone does not make a live player invalid, so movement by itself is not evidence of a reset.
3. `_begin_passive_monster_wakeup_batch()` (`:6693-6786`) chooses one emitter per batch (queue inspection itself is capped at eight and stops on `FrameBudget.remaining_usec() <= 0`), projects that emitter, and performs one spatial AABB query. A missing/invalid extent produces an empty batch (`:6742-6752`); a failed service query requeues the emitter (`:6757-6783`).
4. `_pump_passive_monster_wakeup()` (`:6789-6880`, called from `GameRoot._process()` at `:1919`) runs at most once per `Engine.get_process_frames()` epoch (`:6797-6802`). It charges one optional `FrameBudget.begin()` for the query and another for each candidate. It advances only while there is remaining budget and at most **8 candidate attempts per process epoch** (`:6833-6844`); a denied token leaves the cursor in place. Completion clears the page and proceeds to the next emitter (`:6866-6880`). Thus a dense page is paginated across process frames; it is not guaranteed to wake all candidates in the same frame.
5. Each candidate is filtered for live EnemyActor/map/generation/HP/death state (`:6681-6690`, `:6845-6858`) and then calls `Enemy.request_passive_target_wakeup()` (`:6860-6864`). The Enemy entry (`scripts/enemy.gd:1729-1778`) performs identity/life/map/generation, live/safe/hidden, halo extent and formal static LOS checks before recording a witness and leaving deep sleep. It does not assign a target, attack, or HP.

## What is and is not being occluded

The wake broadphase is the runtime combat spatial index, not a physics raycast. `CombatTargetQueryService.query_envelope_into()` (`scripts/layers/runtime/combat_target_query_service.gd:118-145`) delegates to `RuntimeCombatSpatialIndex.query_enemy_nodes_aabb_into()` (`scripts/runtime_combat_spatial_index.gd:238-273`). The index performs query-stamp dedup and live/map/death filtering; it does not reject a candidate because another enemy or dynamic body is between it and the player. Static terrain visibility is a later, intentional gate: `_initial_acquisition_static_los_clear()` (Enemy, current source around `:6295`) calls the terrain policy segment test. Therefore “one monster physically blocks the other” is not supported by this source path. A terrain polygon or shoulder can reject a candidate, as required by the straight-line halo contract.

## Most likely dense-halo failure mechanism

The source proves a throughput and fairness boundary, not a permanent-drop branch:

- one `process` pump per engine process frame;
- one optional query admission plus one optional admission per candidate;
- eight candidate attempts per process frame;
- shared `frame_optional_budget_usec`/`FrameBudget` can deny the query or a candidate because budget/fairness/resource completion wins;
- the cursor is retained on denial, but an emitter invalidation or a failed/changed map-generation query clears the active page and restarts it.

For a 30-enemy halo, a clean page needs at least four process epochs even before static LOS and shared-budget denials. In an AOE-heavy frame, each static LOS call is in the candidate’s charged scope; a packed frame can therefore show only 1–2 wakes during the observed window, while the rest are still queued or are fail-closed on LOS. If the player/summon emitter changes map/generation/visibility or is destroyed during the page, the code intentionally discards the unconsumed page (`:6657-6664`) and re-queries, which can repeatedly expose only the prefix. There is no source evidence that merely stopping the player drops the remaining cursor: a live player remains current and the page should drain. The receipt must distinguish `cursor_retained_due_budget`, `page_restarted_due_emitter_invalid`, `static_los_rejected`, and `request_accepted` rather than infer from active count.

The shared `FrameBudget` contract explains why a dense AOE can interfere without a dynamic-collision bug. `scripts/layers/runtime/execution/frame_budget.gd:40-145` resets by process epoch, admits only when remaining time and oldest-first fairness allow it, and returns token `0` for budget/fairness/unrunnable denial. Passive wake is marked as a non-physics process owner (`GameRoot`), so a disabled/paused owner or another pending category can defer it. A denial does not advance the cursor, but it can extend activation latency across many frames.

## Firewall path: why “all remain inert” cannot be attributed to halo alone

`FireWallFieldController._apply_field_tick()` (`scripts/fire_wall_field_controller.gd:250-340`) performs its own caller-owned AABB query and canonical footprint test. It has no passive-halo dependency. For each accepted EnemyActor it invokes the runtime damage callback (`:334-340`). The Enemy damage receiver routes positive damage through `_apply_damage_core()` (`scripts/enemy.gd:7530-7574`), which calls `_leave_background_deep_sleep()` before HP mutation (`:7568-7574`) and then threat/wake handling. `take_ground_tick_damage()` (`:7471-7472`) uses the same HP authority without struck animation. Thus a positive firewall/DOT hit should wake a dormant enemy even when the enemy never received a halo request. If the packed group takes no reaction, the missing evidence is upstream of the wake coordinator: controller query/projection/footprint/claim, zero/non-positive damage, feature-batch rejection, or a receipt showing the callback never reached `_apply_damage_core`. Dynamic enemy bodies do not explain it in this chain.

## Why the earlier evidence did not expose this

The release receipt identifies direct73 as the GameRoot player/summon/hidden/budget/FIFO/cap-8/lifecycle check (`outputs/release_v108_20261009/close_integration.py:36`) and the 602 check as the final acquisition fixture (`outputs/release_v108_20261009/ACQUISITION_FINAL_REVIEW.json:3,50,333`). Those contracts prove the gates and one/few-candidate behavior, but they do not prove dense-cohort completion under a single halo, repeated `FrameBudget` denial, page restart during emitter invalidation, or firewall callback-to-HP delivery for every packed enemy. The current status explicitly records direct73 and direct82 as focused contracts and direct90 as geometry acquisition, not a dense halo/firewall cohort (`docs/WORKSPACE_CURRENT_STATUS.md:1`). Therefore their PASS cannot be used to explain this phone symptom.

## New bounded native test needed

Add a new, separately bound dense test rather than changing direct73/602:

- Spawn 30 live ordinary enemies at unique stable index positions inside one player halo, with at least two terrain-blocked lines and no dynamic bodies between otherwise identical pairs. Keep player stationary for one arm and move it continuously for a second arm; include one map/generation/visibility invalidation during pagination.
- Run a third arm with the same cohort and a real active FireWall field whose canonical footprint covers all 30. Record per process epoch: query admissions, candidate cursor start/end, `FrameBudget.last_denial_record("monster_passive_wakeup")`, candidate request calls, static-LOS rejects (reason and actor id), accepted wake witnesses, page restart count, emitter queue depth, and each enemy `background_deep_sleep` transition.
- For FireWall, record controller `candidate_count`, `controller_exact_test_count`, `damage_application_count`, claim successes, each enemy positive HP delta, `_leave_background_deep_sleep` transition, and final target/wake state. Assert the receiver path independently of halo; do not convert a halo failure into a PASS by manually assigning targets or calling wake methods.
- The test must let the cursor drain with the player stopped and must report bounded completion latency. It must separately fail if candidates remain after the queue is empty, if a page restarts without an emitter invalidation/map-generation change, if the broadphase candidate count is below the expected live cohort, or if controller callback count exceeds exact accepted targets.

Expected result categories are `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`, and `MISSING`; no performance or Android claim follows from this source review. The first receipt should make the distinction between “not yet serviced due to shared budget” and “not eligible because terrain/static LOS or damage delivery rejected” mechanically visible.

## Additional scheduler and stealth findings

`GameRoot._process()` orders `_pump_enemy_death_work_queue()` before `_pump_passive_monster_wakeup()` (`scripts/game_root.gd:1871-1920`). Both are non-physics `FrameBudget` categories owned by the same GameRoot process owner. The death queue marks its category in `_refresh_death_budget_owner()` (`:13838-13847`); passive wake marks `monster_passive_wakeup` at `:6811-6818`. `FrameBudget.begin()` (`scripts/layers/runtime/execution/frame_budget.gd:53-145`) does not require a missing callback identity: the pending entry stores a weak GameRoot owner, and the calling owner is explicitly eligible. After a death optional scope is serviced in an epoch, fairness skips that already-serviced category; if death is older and still eligible before service, it can win the wake category's optional admission. A wake denial leaves its cursor and pending mark intact, so there is a future retry on the next process epoch. There is no source path that permanently disables the category merely because it was denied once. This is a latency/fairness interaction, not proof of candidate loss. The receipt needs the two category `last_denial_record()` values and cursor/queue state at each epoch to establish whether the dense symptom is death-budget starvation.

The more direct hidden-player interaction is in `_process()`'s first line: `_recover_equipment_stealth_if_out_of_combat()` (`:1871-1872`) calls `player.recover_equipment_stealth_after_combat_exit()` (`:8367-8374`) whenever `_stealth_break_override` is set, `_player_combat_enemy_ids` is empty, and there is no pending action/attack timer. The player `break_stealth()` path (`scripts/player.gd:1862-1870`) emits `passive_wakeup_changed`; recovery (`:1873-1889`) re-arms equipment stealth and emits the signal again if visibility changes. GameRoot's emitter predicate rejects a stealthed player (`:6553-6555`), and `_mark_passive_monster_wakeup_dirty()` removes that emitter from the queue; if it is the active emitter it clears the current page (`:6657-6664`). Therefore, when an equipment-stealthed player casts a firewall, the sequence can be: cast breaks stealth -> no enemy has yet become a formal target -> next process restores ring stealth before the wake pump -> emitter is no longer current and an in-flight halo page is cleared. This can explain a very small number of halo activations if the first one or two enemies acquire target state before recovery, but it requires the actual player to have the equipment stealth effect. It cannot explain a non-stealthed player.

The same stealth predicate is also intentional: `Enemy.request_passive_target_wakeup()` rejects hidden Player/SummonActor (`scripts/enemy.gd:1753-1758`), and retarget retains the hidden-target gate (`:3318-3321` and other attack/aim gates). The missing test axis is therefore explicit: dense cohort with no stealth; dense cohort with equipment stealth and a firewall cast; and a direct-damage-only cohort. For the latter, positive damage enters `_apply_damage_core()` and calls `_leave_background_deep_sleep()` before HP mutation, so it should wake independently of the player's hidden emitter.

### Required scheduler evidence

The natural-frame reproduction should capture, per process frame, before and after each pump:

- `monster_passive_wakeup`: pending, cursor, candidate-array size, active emitter, emitter FIFO, `FrameBudget.last_denial_record()`;
- death-work category: pending/state, `last_denial_record()`, and whether its optional scope actually consumed the epoch;
- player `is_stealthed()`, `_stealth_break_override`, `_player_combat_enemy_ids.size()`, and emitter-current result;
- candidate request/accepted/static-LOS-rejected counts and every page restart reason;
- firewall controller candidate/exact/damage callback counters plus per-enemy HP delta and deep-sleep transition.

A stopped-player interval must show whether a retained cursor drains. If it does, the bug is service latency/visibility policy; if it does not, the receipt must show a concrete page reset, invalid emitter, map-generation change, or firewall upstream rejection. Do not classify a dynamic monster collision as an occlusion without a terrain/static-LOS rejection record.

## Focused conclusion for the reported no-stealth case

With no player stealth, the emitter-current gate is not the explanation. The wake owner is the live GameRoot `_process()` callback: both `_pump_enemy_death_work_queue()` and `_pump_passive_monster_wakeup()` run in that callback (`scripts/game_root.gd:1871-1920`). `FrameBudget.mark_pending()` stores a weak GameRoot process owner for both categories; `FrameBudget._eligible()` only rejects an owner that is invalid, outside the tree, paused without permission, or not processing (`scripts/layers/runtime/execution/frame_budget.gd:53-95`). The passive category is explicitly marked `runnable=true`, `physics_owner=false` (`game_root.gd:6811-6818`). There is no missing identity argument in this production path.

There is real cross-category delay: death work is pumped first, then passive wake; each category uses optional `begin()`. `FrameBudget._fair_blocker()` can make the wake category wait behind another pending category whose service epoch is older (`frame_budget.gd:86-112`), and `begin()` records fairness/budget denial without advancing the wake cursor (`:118-145`). Once a category is serviced, same-epoch fairness skips it, so this mechanism explains delayed service but not permanent loss. A natural receipt must show whether wake `begin()` is denied mostly for `fairness`, `budget`, or `unrunnable`; otherwise “only one wakes” is not attributable to the queue.

The damage order is also concrete. FireWall calls `GameRoot._apply_canonical_ground_tick()` (`scripts/game_root.gd:11373-11388`), which calls `CombatRuntimeService.apply_enemy_direct_spell_damage(..., MAGSTRUCK_MINE)`. The service invokes `Enemy.take_ground_tick_damage(final_damage, source_actor, damage_context)` when `final_damage > 0` (`scripts/layers/runtime/combat_runtime_service.gd:156-166`). Enemy `_apply_damage_core()` rejects only lifecycle/body-policy/non-positive/batch failures before `_leave_background_deep_sleep()` (`scripts/enemy.gd:7537-7569`), then applies HP; a live attacker also enters `_add_threat()`. For ordinary melee, `_hc_received_damage()` records the source and sets `_hc_damage_dirty=true`, resets retarget cadence, and leaves sleep (`enemy.gd:10865-10879`). `_retarget_internal()` treats this dirty bit as a non-passive wake and clears it only after a completed observation (`enemy.gd:8387-8400`). Therefore a non-lethal positive FireWall tick should create an independent damage-driven wake/retarget opportunity even if halo paging is delayed. If the tick kills the enemy, no target acquisition is required; “did not attack” is then expected for that dead instance.

The remaining source-supported explanations for the report are consequently narrow: (a) the dense halo page is still queued or static-LOS rejected under shared optional budget; (b) the firewall controller's own candidate/footprint/claim path did not invoke the Enemy callback for those actors; (c) positive damage was resolved but each actor died before its next physics/retarget callback; or (d) a body-policy, feature-batch, zero-damage, map/generation, or life rejection occurred. Dynamic enemy bodies are not a blocker in either the wake AABB index or firewall AABB index.

The reproduction must keep at least half the pack non-lethal for several ticks and capture `Enemy._hc_damage_dirty`, `_retarget_internal` entry/exit, target-change events, and `current_hp` deltas. A lethal-only wall test cannot distinguish “damage woke then died” from “damage callback never arrived.”
