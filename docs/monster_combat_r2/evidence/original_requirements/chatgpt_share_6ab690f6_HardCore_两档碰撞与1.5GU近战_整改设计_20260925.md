# HardCore：两档脚底碰撞与统一 1.5 GU 近战整改设计

**方案编号：HC-BODY-2TIER-1P5-V1**  
**性质：推荐设计、施工边界与验收规范，不是已经实施并实测通过的补丁。**  
**核对基线：watermarkpp/HardCore，codex/integration，78a797973409c0ce47590b928f3d26ff067fe567。**

## 1. 决策

采用用户提出的第二条路线：怪物脚底碰撞收敛为小型、大型两档；大型 Boss、大型精英和神兽使用大型档；普通接触近战保留统一的中心到中心 1.5 GU 起手。

不采用逐怪物动态射程，不读取贴图宽高计算战斗体积，不按动画帧、朝向或剩余血量改变物理形状。本设计不改变正式分类、伤害、防御、攻速、仇恨规则、特殊技能射程、地图数据和碰撞层权限。

用户要的是稳定、接近现有手感且不引入持续性能负担。两档路线的优势是能够证明尺寸上界，并最大限度保留当前固定射程调用链；不是声称“可变射程必然更慢”。逐身份预计算的可变射程同样可以做到常数级读取，但需要协调起手、站位、延迟命中、寻路目标和诊断中的每一个范围入口，维护风险更高。

## 2. 已核对的现状

以下是远端源码事实，不是手机运行态读回：

- `scripts/art_spec.gd`：玩家横向碰撞半径 18 px，默认怪物 16 px，Boss 28 px。
- `scripts/enemy.gd::_ready()`：Boss 固定走 28 px；非 Boss 读取行为配置，缺省 16 px；创建公共脚底形状。
- `scripts/monster_unit_adapter.gd`：碰撞半径换算为 `r_px / (32 * sqrt(2))`，不能使用普通旧标量的 `r_px / 32`。
- `scripts/world_spatial_rules.gd`：公共脚底轮廓横纵比例 2:1，16 个顶点。
- `scripts/monster_ai_package/policy.gd`：START_GU=1.5，PREFERRED_GU=1.5，DELAY_TOLERANCE_GU=0.25。
- `scripts/enemy.gd::_contact_distance_gu_to_target()`：攻击者半径 + 目标半径 + 0.4375 GU。
- `scripts/enemy.gd::_hc_tick_melee()`：接触站位超过起手上限时，进入 BODY_REQUIRES_EXPLICIT_EXCEPTION 并停止该追击处理。已经进入范围的目标可能在此前起手，不能把这个分支解释为永久禁止攻击。
- `scripts/summon_actor.gd::_ready()`：召唤物仍创建屏幕圆形 CircleShape2D，骷髅 15 px、神兽 21 px，但其 combat_radius_gu 用公共等距脚底换算；两者几何约定不一致。
- 当前怪物身体半径还参与前排阻挡、运动避让、地形检查和空间索引，不能只改 CollisionShape2D。

## 3. 推荐冻结数值

### 3.1 半径表

| 对象 | 地面半径 GU | 对应横向半径 px | 投影轮廓宽×高 px | 处理 |
|---|---:|---:|---:|---|
| 小型怪物 | 16/(32√2)，约 0.3535533906 | 16 | 32×16 | 保留当前默认小怪尺寸 |
| 大型 Boss / 大型精英 | 0.5 | 22.627416998 | 45.254833996×22.627416998 | 所有大型共用此档 |
| 骷髅宠物 | 同小型档 | 16 | 32×16 | 纳入小型档，修复原圆形；不保留旧 15 px 的独立档 |
| 神兽 | 同大型档，0.5 | 22.627416998 | 45.254833996×22.627416998 | 纳入大型档，修复原圆形 |
| 玩家 | 18/(32√2)，约 0.3977475644 | 18 | 36×18 | 完全保留现有玩家身体尺寸 |

这里的 GU 是半径，不是直径或攻击距离。投影尺寸是场景坐标，不是手机最终显示像素。小型档使用公式或足够精度的浮点值，不要把显示用的 0.354 当作独立的新权威数值。

大型档的半径约为小型档的 √2 倍；相同顶点模板下占地面积为小型档的 2 倍。它表达“更大的脚底占地”，不表达整个怪物贴图必须装进碰撞轮廓。

### 3.2 保留的近战参数

- 新起手上限：1.5 GU，仍为地面中心到中心的欧氏距离。
- 基础理想站位：1.5 GU，维持现有行为。
- 现有接触站位附加间隙：0.4375 GU，本包不调整。
- 已提交延迟近战的现有容差：0.25 GU，不推广到即时攻击，不作为新起手距离。
- 普通延迟近战对应的最大中心距离仍为 1.75 GU，不再额外加双方身体半径。
- 不改神兽喷火、投射物、远程法术、范围攻击、固定炮台和召唤行为的专属范围或伤害通道。

特别禁止把 1.5 GU 改为“从身体边缘再伸出 1.5 GU”。这会把射程额外扩大，不是本方案。

## 4. 数学依据与证明边界

定义 `ra`、`rt` 为双方声明的地面脚底半径，`G=0.4375` 为现有接触站位间隙。

```
C = ra + rt + G
P = max(1.5, C)
```

本方案所有常规战斗身体均不超过 0.5 GU，所以：

```
C_max = 0.5 + 0.5 + 0.4375 = 1.4375 GU
1.5 - C_max = 0.0625 GU
```

这使所有已纳入两档的尺寸组合在配置层不会把 P 推到 1.5 以上。另设离线配置验收余量 0.05 GU：

```
ra + rt + 0.4375 + 0.05 <= 1.5
```

大型半径由此需要满足 `r <= 0.50625 GU`；取整洁且可精确表示的 `0.5 GU`。0.05 是本设计选择的配置预留量，不是 Godot 官方规定，也不是对任意帧长、墙角或拥挤场景的物理证明。

| 组合 | C，接触站位需求 GU | 距离起手上限的余量 GU |
|---|---:|---:|
| 小型 → 玩家 | 1.1888009550 | 0.3111990450 |
| 大型 → 玩家 | 1.3352475644 | 0.1647524356 |
| 大型 → 骷髅宠物 | 1.2910533906 | 0.2089466094 |
| 大型 → 神兽 | 1.4375 | 0.0625 |
| 大型 → 大型怪物 | 1.4375 | 0.0625 |

最后一行是尺寸上界测试，不代表开放新的友军伤害、魅惑对象或 Boss 互殴机制。

不能直接照搬 24 px 或 28 px 作为统一大型半径：

- 两个 24 px 等距身体：`C≈1.49816017`，只剩约 0.00184 GU，不满足本方案预留量。
- 两个 28 px 等距身体：`C≈1.67493687`，已超过 1.5。
- 旧 Boss 28 px + 神兽声明值 21 px：`C≈1.52025726`，已超过 1.5；这还没有计入神兽物理圆形与声明半径的不一致。

**实际验证状态：**本次以独立 Python 算术检查覆盖五类对象尺寸的 25 个有序组合，并核算 16 个投影顶点的半径往返一致性，均满足上述数学条件。25 组不是 25 个 Godot 实战测试，也不代表所有组合在游戏里都是合法敌对关系。Godot 物理测试、全目录实例化和手机性能测试尚未执行。

## 5. 身体分类：独立字段，不能复用 is_boss

大型身体与 Boss 身份必须解耦。不能为了把尸王或骷髅精灵变大而设置 `is_boss=true`，也不能改动正式 `classification`。否则可能改变 Boss 能力、生命周期分支或其他玩法。

建议建立版本化的身体策略输入 `assets/data/actor_body_policy_v1.json`。它包含两档的权威半径、每个怪物整数 ID 的身体档位、骷髅/神兽的档位以及用户玩法覆盖来源。最终可运行目录里的每个受管理怪物必须有一个明确档位，不允许新 ID 静默落到小型。

分类规则：

1. 当前正式 Boss 默认分配大型档；这只决定身体，不改技能或射程。
2. 已确认的大型精英分配大型档，例如普通骷髅精灵、尸王、沃玛卫士；精英不是一律大型。
3. 其他小型、普通接触怪物分配小型档。
4. 先离线读取完整正式目录、现有碰撞配置和已批准的足底表现，逐 ID 输出映射后再落库。大型标记可以辅助首次审计，贴图画布尺寸不能成为运行时体积公式。
5. 飞行、固定、无实体阻挡等现有行为独立保留。两档不授权把飞行怪变成实体墙，也不授权让固定怪移动。
6. 宝箱、NPC、场景障碍等非本次怪物/召唤物身体系统的对象保留原规则，不为了“全项目两档”擅自改造。

**本交付没有伪造一份已经逐项审核完的完整 ID 映射。**全目录映射及新增/放大/缩小影响报告是施工的第一项必交证据。已知的两档几何上界可以证明；每个怪物应该归哪一档仍必须以实际目录和足底形态完成离线确认。

## 6. 单一数据来源与初始化顺序

推荐将身体策略作为现有规范目录的构建输入，生成明确的 `combat.body_profile`（档位、半径、策略版本/来源摘要）；怪物运行时继续从现有正式身份入口读取，不另加名字匹配或后缀回退。召唤物从同一策略解析自己的档位，不再分别硬编码 15/21。

只允许“一个手工权威输入 → 生成/缓存的运行数据”。禁止把生成目录和旧行为配置当成两个都能独立覆盖身体半径的来源。旧 `collisionRadius` 可以保留作历史来源，但正式两档对象不得再从它覆盖新身体。

建议新增 `scripts/actor_body_policy.gd`，只负责校验、一次性解析和统一脚底形状入口。不得新增 `_process()` 或 `_physics_process()`，不得成为每帧轮询服务。

初始化顺序必须是：

```
确认正式 monster_id / summon_id
→ 解析并验证最终身体档位
→ 保存最终 combat_radius_gu / collision_radius_px
→ 出生落点、地图可走和安全区检查
→ 创建一个物理脚底形状
→ 注册空间索引
→ 开始 AI 与战斗
```

禁止出生检查先用默认小半径，入树后再把身体变大；禁止出生快照与实际物理体积不同。对于对象复用或读档，重新确认本次档位并清除旧空间登记/路径缓存；不要在一次正在进行的攻击或碰撞计算中途更换身体尺寸。

## 7. 物理形状与所有消费者同步

### 7.1 形状

玩家保持现有形状。怪物保持当前单个、16 顶点的等距脚底凸多边形。骷髅和神兽改用同一形状生成入口，替换旧屏幕圆形。

CollisionShape2D 保持局部 position=(0,0)、rotation=0、scale=(1,1)。通过最终半径生成点，不把圆形缩放成扁椭圆，不追踪动画每帧改变形状，不根据当前朝向旋转身体形状。沿用当前 16 点模板；本包不顺便降为 8 点或提高到 32 点。

同一个半径对应一个保守地面圆约定及其 16 点物理近似，不声称有限多边形与理想圆每处严格重合。物理、导航采样和战斗足底应统一中心与投影约定，禁止再次出现神兽当前那种纵向翻倍的不一致。

### 7.2 必须排查的消费者

施工时执行全文符号审计，而不是只改两处常量。至少覆盖：

- `combat_radius_gu`、`collision_radius_px`、`collisionRadius`、`MONSTER_COLLISION_RADIUS_PX`、`BOSS_COLLISION_RADIUS_PX` 的全部运行态读写。
- EnemyActor 与 SummonActor 初始化、物理形状、出生重叠修正、生成落点预检。
- summon spawn footprint、召回/传送落点、存档恢复。
- 空间索引登记半径、范围/线段候选查询的覆盖性、前排阻挡与运动交叉检测。
- 寻路终点、静态可走缓存键、墙角和安全区边界。
- 玩家物理攻击、AOE、投射物与召唤物攻击消费的目标脚底快照。
- 编辑器/校准工具预览和运行时诊断（读取同一规则，不重建第二套尺寸）。

只同步“目标身体”数据，不扩大技能自身的释放形状，不改攻击属性。改变目标身体必然可能改变边缘擦中或群怪摆位；这必须回归，不能在报告里写“技能命中完全没变化”。

黄圈、阴影、血条和贴图仍是显示对象，不能反向修改物理体积。沿用既有独立显示规则；若冻结的黄圈外观必须维持原尺寸，使用显示数据保留，不借用旧战斗半径伪造。

## 8. 近战代码整改边界

保留现有 1.5 GU 起手、1.5 GU 理想站位和 0.25 GU 延迟容差。保留 WORLD、目标有效性、前排阻挡、控制、地图代际和攻击 release 生命周期校验。

`BODY_REQUIRES_EXPLICIT_EXCEPTION` 不直接删除，不改成无条件放行。用两档数据和构建校验保证正式对象不触发该几何冲突。将异常前移到目录构建/实例初始化：缺失档位、非有限半径、负数、超上限、策略版本不一致应给出明确错误并禁止该无效配置发布；生产不能悄悄夹取半径后继续游戏。

本包不做新的自适应身体间隙，不改成边缘到边缘射程，也不新增每怪每帧测距射线。离线校验的配置预留量不加入攻击范围，更不加在每次命中伤害判断上。

范围外必须在可达且已有 AI 条件满足时继续接近；冷却完成、范围内且访问条件为 CLEAR 时，应在现有调度窗口起手。不能要求隔墙、前排遮挡、固定炮台或控制中的怪物也攻击。

## 9. 性能要求与诚实边界

设计约束：

- 每个怪物仍为一个物理身体、一个脚底形状、16 个顶点；不新增 Area2D、RayCast2D、独立攻击探针或碰撞子身体。
- 分类与半径只在目录加载/实例初始化解析，运行时直接读取现有浮点字段。
- 不新增逐帧 JSON、字典克隆、贴图像素扫描、全场 group 查询或逐目标形状构建。
- 不提高寻路、重选目标、环境保护或碰撞查询频率。
- 可以缓存两档的点数据；共享 Shape2D 资源仅在确认无运行时修改者后采用，不得因为共享被某一个实例改尺寸而影响整群怪。共享资源优化不是必需前置条件。
- 不为了“补偿成本”减少 AI 更新率、降低伤害频率、禁用身体阻挡或改动地图几何。

**不能预先声称绝对零增加。** Godot 官方明确说明凸多边形通常比 CircleShape2D 这样的基本形状有更高单次碰撞开销；召唤物从圆形变为 16 点凸多边形存在这一差别。尺寸调整也可能改变实际接触对数、导航可达性和同屏交战密度。两档减少配置复杂度，不等于已经证明引擎耗时必然下降。

因此本设计的发布要求是：不新增逐帧 AI 工作，并在受控同机 A/B 中没有可重复的整体性能退化。若有退化，先根据物理/脚本采样定位，不得靠关闭正常战斗机制获得虚假通过。

## 10. 实施分包与验证

本包只处理身体/统一近战几何。此前发现的隐式 Boss 技能、基础攻速覆盖、动画队列问题应分别修复并回归；仅本包完成不能宣称“无动作扣血全部修复”。

### A. 固定基线与离线目录

1. 使用隔离工作树；执行前重新读取 `origin/codex/integration`。若 SHA 已改变，对本报告对应函数重查差异，不把旧行号当绝对位置。
2. 记录原目录和所有地图工作区文件的哈希、原有未提交修改，禁止丢弃用户工作。
3. 导出所有受管理正式怪物的旧半径、档位来源、是否实体阻挡、是否普通近战、是否地图实际刷新。
4. 生成逐整数 ID 的新档位表，以及半径放大/缩小的影响表。大型精英不能靠更改正式 Boss 分类实现。
5. 先建立会拒绝旧 Boss/神兽组合与形状不一致的针对性测试，再做生产改动。

### B. 数据/初始化/物理接入

核心修改范围：

- 新增身体策略输入与其严格校验；接入 `tools/build_canonical_monster_catalog.py` 或仓库已存在的等价规范构建入口。
- `scripts/monster_identity.gd`：在现有正式身份入口暴露已校验身体数据，不增加名字回退。
- `scripts/enemy.gd`：设置与 ready 的身体初始化，移除旧 Boss/行为配置竞争覆盖；关联出生/索引字段一致。
- `scripts/summon_actor.gd`：两种召唤物的初始化、spawn footprint 与实际形状一致。
- `scripts/world_spatial_rules.gd`：复用现有 16 点模板；不扩展到动态逐帧形状。
- `scripts/art_spec.gd` 和 `scripts/monster_unit_adapter.gd`：逐项清理残留的旧体积权威使用，不改玩家尺寸或其他单位转换。
- 所有实际读到旧半径的生成落点/空间索引/快照调用者：在本次符号审计输出中逐一登记，不能凭文件名猜测已覆盖。

本报告不提供未经仓库完整构建验证的可直接覆盖补丁，执行者必须按真实接口修改，不得直接复制示意名称替代现有 API。

### C. 必须新增的自动测试

建议新增并注册以下测试场景；以下是新文件名建议，不是声称它们已经存在：

- `tests/actor_body_policy_contract_test.tscn`：完整 ID 覆盖、未知/重复 ID、半径类型与边界、两档数据唯一来源、最大组合预留量。
- `tests/actor_body_projection_test.tscn`：实际点集逆投影半径、16 点数量、零局部偏移/旋转、单位缩放、身体与索引/快照一致。
- `tests/monster_melee_body_pair_test.tscn`：小/大怪对玩家、骷髅、神兽；最大尺寸组合；1.49/1.5/1.51 GU 的八方向新起手。

### D. 物理/玩法验收

- 八方向接近与绕圈；1.49/1.5/1.51 GU；范围外不能新起普通攻击；已起手延迟攻击按原容差验证。
- Boss 对玩家、骷髅、神兽，尤其画面上下方向的接近，不再因身体与射程规则矛盾停住。
- 不同体型混合、两只大型前后排列、墙角/窄门、前排遮挡、受控单位，不能用穿人或穿墙换取攻击成功。
- 刷新、传送、换图、召回、死亡重生、存档恢复的尺寸和空间登记一致。
- AOE 与投射物边缘命中使用新目标身体，但伤害/防御/法术抗性/攻速/攻击通道不变。
- 贴图大小、脚点和动画帧不由新碰撞档位驱动；选中圈与玩法几何不串写。
- 现有小怪从 10/12/15 等旧半径归为 16，或大型精英从 16 归为 22.627，可能改变窄道行为；必须由影响表驱动回归，不宣称所有地图手感天然不变。

### E. 手机性能门禁

同一设备、同一引擎与导出方式、同一地图、温控条件尽量一致，做交错顺序 A/B，多次重复。建议每个持续场景至少 120 秒、至少 5 轮；这是验收设计，不是执行耗时承诺。

覆盖：1、10、20、30 怪；全小型、混合大型；当前允许的宠物上限；追击聚怪、火墙/AOE、攻击后死亡掉落、无战斗静置。另做固定实体状态的 CPU/物理微基准，用于区分“算法更贵”和“正常参战怪更多”。不能拿卡住不动的旧 Boss 当作公平性能基线。

记录：帧时间 p50/p95/p99、超过 16.67/33.33 ms 的比例、怪物脚本耗时、move_and_slide/物理耗时、空间查询/路径请求数量、内存与分配趋势。计数器用于测试构建且限量采集，不新增正式版逐怪每帧写盘。

发布条件：功能回归通过；新增逐帧探针/全场扫描/形状重建为零；微基准与实战对照没有超出测量波动的可重复退化。60 FPS 对应 16.67 ms 是整帧预算，不能被解释为本包已经保证 30 怪达到 60 FPS。

## 11. 发布与回滚

身体尺寸、出生检查和空间索引必须作为同一个几何版本发布，不允许只更新部分 JSON 或只热替换一份脚本。首次验收采用完整构建并彻底重启应用；不在现有存活实体仍用旧形状时注入新半径。

不得强推、删除分支或清理别的工作树。本任务不改地图布局/文件来“修复”变大的单位走不通。记录地图文件变更为零、全目录身体映射摘要、构建源码 SHA、策略摘要及测试记录。

若发生新增卡位、出生重叠、脚底/索引不一致或可重复性能退化，整包回滚至前一几何版本；保留失败证据。不要混用新形状与旧导航、旧形状与新半径。

## 12. 交付结论

推荐小型保持当前默认 16 px（约 0.353553 GU 半径），大型与神兽统一为 0.5 GU 半径，骷髅纳入小型，玩家不改；普通接触近战继续统一 1.5 GU。

这一组数字满足最大身体组合加现有间隙仍小于射程的约束，并保留明确配置预留量。它不是唯一数学可行解，也不是官方原版体积值；它是针对当前固定射程代码、用户可靠性目标与最小持续开销要求的一组可论证基线。

完成碰撞/站位整改不等于完成整个怪物系统所有 Bug 的维修。最终需要独立关闭 Boss 隐式技能、攻速覆盖和动作/音效/伤害一致性的既有问题，再做联合发布验收。
