这已经足以造成你说的“动作还没看见，血已经掉了”。

## 为什么你还能听到攻击音效？

这里还有第二个非常明确的 BUG。

`EnemyActor` 当前这样执行：

```gdscript
func _play_attack_animation(duration: float) -> void:
    if visual != null:
        visual.play_attack(duration)

    _audio_attack_started()
```

但是 `visual.play_attack()` **并不保证攻击动作马上播放**。

`monster_visual.gd` 现在有一个严格 FIFO 动作队列：

```gdscript
if _hit_remaining > 0.0 \
or _attack_remaining > 0.0 \
or _presentation_count > 0:

    _enqueue_presentation(PresentationAction.ATTACK, duration)
    return
```

特别是你正在打 Boss 的时候，Boss 会不断收到：

```text
STRUCK
STRUCK
STRUCK
ATTACK
STRUCK
...
```

也就是说攻击动画可能还在队列里。

可是与此同时：

```text
攻击音效：已经播放
伤害：已经结算
攻击动作：还在队列里
```

这和你实际观察到的：

> “没有攻击动作我就掉血了，但是我能听到攻击音效”

**完全吻合。**

而且还有一个更坏的情况。

这个视觉队列容量只有：

```gdscript
PRESENTATION_QUEUE_CAPACITY := 16
```

队列满了以后：

```gdscript
if _presentation_count >= PRESENTATION_QUEUE_CAPACITY:
    ...
    return
```

新的动作会直接被丢弃。

但 `EnemyActor` 根本不知道动画被丢了，所以依然：

```text
播放 attack_start 音效
→ 结算伤害
→ 攻击动作因为 FIFO 满了根本没有播放
```

所以你说的**“完全没有攻击动作，只听见声音然后掉血”在当前代码里不但可能，而且存在一条非常明确的生产路径。**

# 为什么感觉“有时候远、有时候近”

这里有三个因素叠加。

第一，当前 1.5 GU 是**地面二维空间里的欧氏圆**，不是屏幕上 1.5 个固定长度。

项目正式投影：

```gdscript
screen_x = (ground_x - ground_y) * 32
screen_y = (ground_x + ground_y) * 16
```

所以同样是 1.5 GU，投影到屏幕不同方向后，中心视觉距离大约可以从：

```text
约 34 px
到
约 54 px
```

差异很明显。

这本身并不是攻击范围随机，而是等距投影的正常结果。

第二，两个 Boss 都使用：

```text
BOSS_COLLISION_RADIUS_PX = 28
PLAYER_COLLISION_RADIUS_PX = 18
PLAYER_MELEE_CONTACT_GAP_GU = 0.4375
```

换算下来 Boss 和玩家的物理接触中心距离大概已经是：

**1.454 GU。**

而攻击起手距离只有：

**1.500 GU。**

两者只差：

**约 0.046 GU。**

也就是说，对于大型 Boss 来说，现在的 1.5 GU 基本就是**快贴脸才攻击**。

第三，也是现在最影响感受的：

> 实际伤害发生的位置和你看到攻击动画的位置可能根本不是同一时刻的位置。

你肉眼自然会认为：

>
> 或者

> “怎么这次贴这么近才攻击？”

其实你看到的动作已经不是伤害判定发生时的空间状态了。

# 所以我认为这次不能简单把 1.5 改回 2

**1.5 GU 本身可以保留。**

真正有问题的是上次施工把三件本来应该独立的东西绑到了一起：

```text
追击停止距离
攻击准入距离
伤害结算时点 / 特殊攻击通道
```

尤其这句设计：

```gdscript
kind != "" → hit_delay = 0
```

我认为必须撤掉。

### 我建议的修复方向

第一优先级是让 **攻击动作、声音、伤害重新成为一个统一事务**。怪物攻击成立后，必须先真正进入 Attack presentation，再在攻击动作规定的 impact 时点结算伤害；`attack_start` 音效也必须跟真正开始播放攻击动作同步，而不是“动画请求已经入队”就播放。

第二优先级是保留你要求的 **1.5 GU 近战规则**，但建立唯一的 `effective_melee_reach_gu = 1.5`。不要再出现“239 的 runtime attack_range_gu = 1.0，但 HC 又说 = 1.5”这种双权威。239 的物理+魔法混合伤害方式可以继续保留，攻击距离则明确服从你的 1.5 规则。

第三优先级是给 238/239 补正式攻击时序。它们都有完整 6 帧攻击动画，但目前这两只暗之 Boss 没有完整的 `boss_rule` 时序。至少要给它们正式的：

```text
attack_animation_duration
impact_time / hit_delay
attack_interval
```

而不是让 238 继续使用默认 `0 ms hit delay`。

## 一、这次确认了哪些问题

### 1. 怪物攻击表现、音效和伤害没有可靠绑定到同一次动作

这是与你反馈最直接对应的问题。

当前 `visual.play_attack()` 可能只是把攻击放进队列，甚至因为队列满而丢弃；但调用者随后仍提交攻击音效，攻击逻辑也按自己的时间结算伤害。因此，持续受击时可以出现：

> **身体仍在播放旧受击 → 新攻击已经发声、结算 → 新攻击身体动作迟到，或根本没有播放。**

这不是仅仅调整攻击距离能解决的。当前队列还没有保存完整的攻击身份和朝向信息，迟到的动作可能使用后来的目标或朝向，进一步放大“攻击距离忽远忽近”的观感。fileciteturn33file0L2-L2fileciteturn54file0L2-L2fileciteturn58file0L2-L2

**整改重点：关键攻击不能继续被普通受击队列长期阻挡或静默丢弃。** 但合并的是受击表现，不是伤害次数、受击造成的攻击延期或状态判定次数。

### 2. 部分 Boss 的实际攻击周期会绕过已加载配置

这里发现了一处比上一轮更明确的问题：

```gdscript
return (0.78 if _boss_phase_two else 1.15) if is_boss else _attack_interval
```

当怪物属于 Boss、但 `boss_rule` 为空时，实际周期会使用隐藏的 **1.15 秒**，而不是已经加载的 `_attack_interval`。真正起手时，代码又确实用 `_current_attack_interval()` 写入冷却。fileciteturn32file0L2-L2fileciteturn58file0L2-L2

这也解释了为什么仅看以前的“有效攻击政策表”仍可能漏掉问题：表里六暗相关记录显示的是 `attack_interval_seconds=1.5`，但记录中的起手次数、结算次数都是零，**它不是连续攻击间隔的实测证据**。fileciteturn31file0L2-L2

方案要求 Sol 对所有身份分别列出：

**来源配置 → 初始化后的有效值 → 实际连续起手间隔。**

不能只修 238/239，也不能反过来把所有 Boss 都统一改成 1.5 秒。

### 3. 怪物的直击法术受击延期，可能被连续追击绕过

目前，符合条件的法术受击会推迟 `walk_tick_ms`。但是，进入连续追击后，下一段运动可以直接调用：

```gdscript
_begin_autonomous_step_without_cadence(...)
```

这条入口没有消费前述移动许可检查。因此可能出现：**延期数值确实写了，怪物下一步却没有按预期等待。**fileciteturn46file0L2-L2fileciteturn47file0L2-L2fileciteturn59file0L2-L2

已有对应专项主要验证 WalkTick 增量、伤害和受击队列，没有在那个场景继续验证下一次真实位移。fileciteturn51file0L2-L2

方案要求补的是**实际运动轨迹测试**：当前已经提交的一步可以完成，下一段必须服从有效延期；同时不能让火墙误加这种移动锁，也不能把连续追击改成每走一格都停顿。

### 4. 人物新动作会继承历史上较长的动画时长

人物表现代码对新的普通动作使用：

```gdscript
_action_duration = maxf(_action_duration, duration)
```

但帧进度又按 `_elapsed / _action_duration` 计算。这会留下历史时长污染。fileciteturn34file0L2-L2fileciteturn35file0L2-L2

例如一个已经结束的 **0.8 秒死亡动作**留下时长，下一次请求 **0.51 秒攻击**：动作只存活 0.51 秒，却仍按 0.8 秒计算播放进度，末段帧就可能缺失。

因此，这次不能只审怪物。施工已经加入：

**施法后短攻击、受击后攻击、攻击中受击、死亡复活后攻击**等完整链路，要求动画时长、实际帧和人物可行动时刻一起验证。

### 5. 人物旧中毒通道存在“强毒过期后污染新弱毒”的边界问题

旧通道把 `poison_time` 减到零，却没有在普通过期路径同步清掉 `poison_damage`；再次施加时又始终取历史最大值：

```gdscript
poison_damage = maxi(poison_damage, maxi(1, tick_damage))
```

所以，强毒自然结束后，新弱毒仍可能继承旧强度。fileciteturn60file0L2-L2fileciteturn61file0L2-L2

**这不等于所有中毒系统都有同样的问题。** 怪物自身的毒过期路径会清理强度、间隔和累计值；人物新的怪物来源中毒入口也有死亡、零血量和转换期检查。方案明确保留这些保护，不把不同毒伤通道粗暴合并。fileciteturn44file0L2-L2fileciteturn61file0L2-L2

## 二、另外几类风险，要求先复现再改

这些已经放进整改包，但没有冒充“你的手机必然发生过”。

**命中后的吸血、控制和上毒缺少完整接收回执。** 普通攻击调用目标 `take_damage()` 后，还会继续处理吸血和附带状态。需要确认目标拒绝伤害、护身效果支付、目标致死或攻击者被同步回调杀死时，这些副作用是否仍会错误执行。不能未经来源核查就把所有吸血统一改成“按最终 HP 差计算”。fileciteturn40file0L2-L2

**人物致死通知存在需要验证的同步重入窗口。** 当前流程先把 HP 写到零，再广播部分属性、资源等通知，之后才设置 `_dead`。方案要求注入“零血量通知里再次伤害、治疗、换图”的反例，并验证死亡、复活和延迟通知是否只执行一次。fileciteturn62file0L2-L2

这类修复不能随手重构整个伤害系统。尤其人物当前死亡分支含 `await`，**不能简单把返回类型改成 Dictionary，就假定调用者能同步拿到完整伤害结果**。施工方案已经专门要求把同步结算与延迟表现职责分开。

## 三、上一轮有两处判断必须纠正，避免 Sol 修偏

**第一，`presentationDelaySeconds=0.2` 不能直接解释成“应该等 0.2 秒才扣血”。** 当前代码明确区分来源表现通知和实际投递；部分特殊近战的即时结算有其原有语义。不能看到零延迟就统一补前摇。fileciteturn58file0L2-L2

**第二，保留源攻击距离，同时应用用户的 1.5 GU 覆盖，并不自动构成“双重权威 BUG”。** 当前特殊近战条件在进入公共近战时，会明确转用 `HCPolicy.START_GU`；要判断是否混乱，应检查同一次攻击的不同阶段是否真的用了冲突边界，而不是只看两个字段数值不同。fileciteturn43file0L2-L2

所以，这份方案**不采用“全部攻击改成动画播到某一帧才扣血”的修法**。Godot 的绘制更新与物理更新不是同一个时钟，让渲染反过来决定伤害，会把帧率和资源加载差异带进战斗结果。整改设计是让逻辑动作、身体表现和声音共享身份与时间依据，伤害仍由战斗层拥有。citeturn949821view0

## 四、受击系统不能全部推倒重做

有些你可能观察到的“不硬直”，本来就不是错误。

怪物受击政策明确区分普通受击、直击法术、火墙和毒 DOT：普通受击不制造全局移动锁；直击法术的移动延期有条件；火墙不进入同一 WalkTick 延期分支；毒 DOT 不触发普通受击。不能为了统一效果，把这些全部改成同一种硬直。fileciteturn41file0L2-L2

人物也已经有“当前攻击/施法先完成，再补受击表现”的处理，并按最终伤害与项目受击政策判断。**保留已提交动作，不等于漏播受击；必须结合队列、锁和实际帧一起判断。**fileciteturn62file0L2-L2

方案要求保留这些正常职责，只修明确缺陷。它还把全身份的 HP、攻击上下限、物防、魔防、命中、敏捷和抗性加入来源—运行时对照，防止整改时重复扣防御、把魔法攻击改成物理攻击，或者无授权改变数值。
