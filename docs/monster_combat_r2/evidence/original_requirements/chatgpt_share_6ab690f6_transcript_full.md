## 三、公共动画队列存在缺陷：它确实能产生“有声音、掉血、却不出招”

这部分不是两个 Boss 的专属问题，而是公共 `MonsterVisual` 和 `EnemyActor` 之间的协调问题。

### 1. 攻击动作会排在受击动作后面，队满还可能被丢掉

`MonsterVisual.play_attack()` 的当前行为是：

- 正在播放受击、正在攻击，或者表现队列不为空时，把攻击事件放进队列；
- 队列满了，记录 overflow，然后丢弃新事件；
- **攻击事件也会经过这条可丢弃路径。**

这意味着“调用了攻击动画函数”，不代表“攻击动作已经播放”，甚至不代表“之后一定会播放”。fileciteturn22file0L2-L2

### 2. 音效和伤害并不知道动画被排队或丢弃

EnemyActor 的调用是：

```gdscript
if visual != null:
    visual.play_attack(duration)
_audio_attack_started()
```

`play_attack()` 没有把“已开始／正在排队／被丢弃”的状态返回给这里，随后攻击开始音效仍然执行。近战逻辑也已经建立攻击记录和冷却，并按自己的即时或延迟规则结算伤害。fileciteturn64file0L2-L2 fileciteturn23file0L2-L2

于是会出现这样的执行顺序：

```text
你击中怪物，怪物正在显示受击
          ↓
怪物的攻击被战斗逻辑接受
          ↓
攻击画面排队，甚至被丢弃
          ↓
攻击音效发出，伤害正常结算
          ↓
你看到怪物仍在受击或没有出招，却掉血了
```

**这与你描述的现象直接吻合。** 不过，要判定手机上的每一次异常到底是这条路径，还是前面的隐式范围技能，需要用同一次攻击的 ID 和时间记录区分，不能把所有情况混成一个原因。

### 3. 还会牵连朝向和移动表现

当前表现状态使用怪物当下的朝向；而战斗层的攻击姿态计时和视觉层排队后的动画计时不是同一个东西。目标离开 1.5 格后，部分恢复阶段可以转回追击，视觉攻击却可能尚未结束，甚至刚从队列里开始。这是“滑着攻击、动作方向改变、看起来距离不稳定”的结构性风险。fileciteturn56file0L2-L2 fileciteturn59file0L2-L2

## 五、整个怪物系统的伤害、防御链还查到了什么？

### 已阅读的防御入口，没有发现“物防和魔防统一混扣”的证据

玩家普通受伤入口扣物防，直接法术入口按魔防结算；混合伤害分别处理两种防御后，再进入后续护盾和死亡流程。至少在本次读到的公共入口里，**没有证据支持“所有法术又额外扣了一次物防”这样的全局错误。**fileciteturn47file0L2-L2 fileciteturn46file0L2-L2

怪物自身的 `take_damage()` 是接收已经算好应扣血量的入口，不能为了“补防御”就在这里统一再减一次 `defense`，否则可能引入真正的重复减防。怪物的直接法术防御快照、物理防御和红毒修正也有分开的入口。fileciteturn64file0L2-L2 fileciteturn93file0L2-L2

### 另有两个公共边界问题，应该分级修复

**负伤害输入没有保护。** `_apply_damage_core()` 直接执行：

```gdscript
current_hp = maxi(0, current_hp - amount)
```

没有先拒绝负数。负伤害会变成回血，甚至超过最大血量。这是已经确认的接口防御缺口，**但本次没有证据证明你的实战异常是由负数输入造成的**。应把它列为 P2，不与本次主因混淆。fileciteturn93file0L2-L2

**物理与魔法吸血的伤害口径不一致。** 公共物理攻击路径把减伤前的伤害传给吸血；已阅读的魔法路径使用结算返回的实际伤害。这可能在护盾、减伤或实际扣血较少时造成不一致，需要按明确规则统一。**尚未证明这两只 Boss 启用了相关吸血能力，因此不能拿它解释这次主要症状。**fileciteturn42file0L2-L2 fileciteturn38file0L2-L2 fileciteturn73file0L2-L2

另外，DOT／中毒不播放普通受击动作是代码明确区分的机制，不应在维修中把所有持续掉血都强制补成一次普通攻击动画。fileciteturn93file0L2-L2

## 六、详细维修顺序

### 第一包：关闭隐式 Boss 能力，恢复正确基础攻速

主要修改 `scripts/enemy.gd`。

将技能与阶段能力改为默认关闭，只有**确切 ID 的合法显式配置**才能开启。初始化时重置旧 Boss 状态，避免旧阶段、预警、技能范围记录残留；技能函数入口也必须校验能力，不能只靠调用者。

`_current_attack_interval()` 必须以身份对应的规范间隔为基础，不再因 `is_boss` 返回 1.15／0.78。**不能把所有怪物都改成 1.5 秒**，也不能删除其他 Boss 真正配置过的狂暴机制。显式机制应作为明确的覆盖，保留来源。

同时核查 `_apply_boss_rule()` 是否又用旧规则覆盖了新的属性间隔，输出“目录值—规则值—运行基础值—当前实际值”的逐 Boss 对照。

### 第二包：修公共动作与伤害的一致性

主要修改 `scripts/enemy.gd`、`scripts/monster_visual.gd`，在现有攻击释放记录上扩展，而不是另建一套伤害中心。

**推荐方向是：已接受的攻击不能被当成普通可丢弃表现。** 可以压缩、合并过期的纯受击画面，但必须保留真正的控制、受击期限惩罚和已确认的战斗规则。

每次攻击用同一个身份关联动作、音效、伤害、朝向策略和取消状态。死亡、换图、重生、禁战和重新初始化时失效旧事件，不能在恢复后补播、补伤害。

这里特别禁止四种“看起来能修、实际会引入新问题”的做法：**只扩大队列、每帧重播攻击、把所有伤害统一延迟一个固定时长、等待渲染动画结束才决定伤害。**

### 第三包：做全目录属性与能力运行态核验

不能只修 238、239 两个 ID。影响范围应按条件扫描：

```text
所有允许运行的怪物
    → 所有 classification == boss 的身份
    → boss_rule 是否为空
    → 是否获得了未配置能力
    → 基础间隔是否被覆盖
    → 攻击类型、伤害通道、范围和表现是否对应
```

再覆盖普通近战、特殊近战、远程、范围攻击、宠物目标、受击、DOT 和死亡取消。物理接触距离是否导致 1.5 GU 无合法攻击位置，也要作为条件检查；**本次没有证实两个目标 Boss 触发了这个体积问题，不能据此直接缩碰撞体。**

### 第四包：以实战与性能结果作为发布门禁

完整矩阵在文档中。最重要的验收点是：

| 验收场景 | 必须达到的结果 |
|---|---|
| 两只暗之 Boss，满血和半血 | 无未配置范围技能，无自动切到 0.78 秒 |
| 1.49／1.5／1.51 GU 边界 | 起手判定稳定，考虑现有浮点容差，不在范围外新起普通近战 |
| 玩家与宠物持续攻击 Boss | 已接受攻击的表现不丢，动作、声音、伤害可按攻击 ID 对应 |
| 强制表现队列满载 | 不丢攻击，不无限排队，不重播过期攻击 |
| 绕圈、离开近战圈、快速进出 | 无错误旧朝向，无未定义的滑动攻击 |
| 死亡、重生、传送、换图、暂停 | 旧攻击不跨生命周期扣血 |
| 物理、魔法、混合、AOE、DOT | 防御和护盾按各自规则处理，不重复扣减 |
| 同机 1／10／20／30 怪对照 | 不因新日志、额外分配或全场扫描造成性能回退 |

诊断记录应使用限量内存缓冲或指定目标追踪，**不要每怪每帧写 JSON、同步写盘或增加组扫描**。没有真机结果，不能宣称“30 怪已经稳定丝滑”。

## 一、现在的近战怪物，攻击距离是不是一样？

**被当前公共近战系统接管的攻击，起手距离是一样的：1.5 GU。不是按照普通怪、精英、Boss 分别设置。**

在 `scripts/monster_ai_package/policy.gd` 中，当前关键参数为：

| 参数 | 当前值 | 含义 |
|---|---:|---|
| `START_GU` | **1.5** | 允许新发起一次近战攻击的最大距离 |
| `PREFERRED_GU` | **1.5** | 基础理想近战站位距离 |
| `DELAY_TOLERANCE_GU` | **0.25** | 某些已经起手的延迟近战，在结算时允许的额外距离容差 |

配置明确标记为 `user_gameplay_override`，即**项目玩法覆盖**，不是从原版怪物属性表直接读出的统一射程。fileciteturn39file0L2-L2 fileciteturn42file0L2-L2

这里有两个容易误解的地方。

**第一，“近战”不等于“物理伤害”。** 当前公共近战分类包含普通接触攻击，以及部分 `special_melee`、`gas_adjacent`、`mixed_target_tile` 攻击。也就是说，有些造成魔法伤害的贴身攻击，同样使用 1.5 GU；远程法术、投射物、独立范围攻击和召唤行为则保留自己的规则。fileciteturn44file0L2-L2

**第二，“怪物只有一个攻击距离”这个说法不够准确。** 同一个怪物可以有普通攻击、喷吐、投射物、范围技能等不同攻击行为。当前代码甚至专门同时提供 `source_range_gu` 和实际 `start_gu`，说明**资料中的来源距离，未必就是公共近战覆盖后真正使用的起手距离**。fileciteturn44file0L2-L2

所以，准确的表述应当是：

> **普通接触近战共用 1.5 GU 起手规则；特殊攻击按自己的规则判断。不能把所有怪物造成伤害的位置，都拿 1.5 GU 来解释。**

## 二、原游戏的普通近战，是否也是统一距离？

### 查到的核心规则：统一判断“周围八个相邻格”

我检查了公开的 GameOfMir 旧式服务端参考源码。普通怪物的 `TMonster.AttackTarget()` 会调用 `GetAttackDir()`；通过相邻位置判断、且攻击间隔允许时，才调用攻击，否则继续接近目标。citeturn936509view0

`ObjBase.pas` 中 `TBaseObject.GetAttackDir()` 的位置条件，可以等价整理成：

\[
|\Delta x|\leq 1,\quad |\Delta y|\leq 1,\quad \text{双方不在同一格}
\]

这里使用的是整数地图坐标，因此含义就是：**目标位于怪物周围的八个相邻格之一。** 判定本身没有根据怪物贴图大小、等级或 Boss 标记，自动放大攻击距离。继承这条普通攻击规则的怪物，使用同一种邻接范围。fileciteturn47file0L2-L2

我又交叉检查了 Crystal。它的公共怪物攻击范围同样调用 `Functions.InRange(..., 1)`，而这个函数检查的正是横、纵坐标差分别不超过 1。**两套参考实现都支持“普通近战以八邻格为基础”的结论。**citeturn704177view0turn741613view0

### 但特殊攻击，确实不是统一“一格”

旧式源码中另有 `TargetInSpitRange()`：先允许横纵坐标差进入两格范围，再按朝向对应的喷吐格子模板判断。它不是普通八邻格攻击，也不是简单的任意方向圆形两格攻击。fileciteturn47file0L2-L2

还有 `TElectronicScolpionMon`：它有横纵坐标差不超过两格的魔法攻击判断，执行完自己的行为后又调用父类逻辑。你的项目来源表把牛魔王、牛魔法师、牛魔祭司对应到这类“特殊法术＋普通贴身攻击”的来源规则。**这是“同一只怪物存在不同攻击范围”的实际例子，不能全部归为普通近战距离。**fileciteturn49file0L2-L2 fileciteturn46file0L2-L2

**资料边界也需要说明：**公开 GameOfMir 仓库说明其客户端资料面向 1.5／1.76；Crystal 则明确是社区维护的现代重实现。它们是可核验的代码证据，但不是“运营商当年某一版 1.76 线上程序逐字证明”。本次没有找到官方完整的逐怪物射程表，因此不能据此宣称“所有历史版本、所有 Boss 的所有攻击都一样”。citeturn741613view1turn704177view1

## 三、最关键的换算：为什么原版“一格”，不应该直接改成“1 GU”？

你项目的单位契约已经把两种概念分开：

**GU 是地面直线距离；GS 是离散格子邻接步数。** 当前代码还明确规定，沿一个地面坐标轴到相邻格是 **1 GU**，到斜相邻格则是 **√2 GU，约 1.414 GU**。fileciteturn48file0L2-L2 fileciteturn40file0L2-L2

这意味着：

> **格子规则中的“相邻一格”，可以是直邻，也可以是斜邻；但在直线距离里，两者并不一样远。**

下面是按已核对的两套判定进行的数学核算。假定双方位于非重叠的整数格中心，只比较几何范围，不考虑墙、冷却和其他单位阻挡：

| 目标相对位置 | 地面直线距离 | 旧式八邻格近战 | 圆形 1 GU | 圆形 1.5 GU | 圆形 2 GU |
|---|---:|---:|---:|---:|---:|
| `(1, 0)`：直相邻 | 1 | 能攻击 | 能 | 能 | 能 |
| `(1, 1)`：斜相邻 | 约 1.414 | 能攻击 | **不能** | 能 | 能 |
| `(2, 0)`：沿一个轴隔着一格 | 2 | 不能攻击 | 不能 | 不能 | **能** |
| `(2, 2)` | 约 2.828 | 不能攻击 | 不能 | 不能 | 不能 |

**这直接回答了你对 1.5 的疑问：**

把圆形近战距离设为 **1 GU**，并不是简单“恢复原版一格”，而是会漏掉四个斜相邻格。设为 **1.5 GU**，在整数格中心上恰好可以覆盖原来的八个邻居，又不覆盖沿坐标轴隔一格的目标。设为 **2 GU**，则会额外覆盖四个这样的第二圈位置。

因此，**1.5 有明确的几何合理性，不是一个明显乱设的值。**

但它也不是唯一正确值：在理想数学条件下，任何满足

\[
\sqrt{2}\leq R<2
\]

的圆形半径，都能在整数格中心上选中同一圈八个邻居。**所以不能进一步说“证明了 1.5 就是原版真实射程”，更不能说它一定是手感最好的数值。**

### 为什么仍然不能说已经完整还原？

因为你的游戏并不只在整数格中心判断攻击。当前近战逻辑在移动后，会使用实际位置再次尝试起手；距离判断也直接使用浮点地面坐标。fileciteturn41file0L2-L2 fileciteturn44file0L2-L2

例如双方地面偏移为 `(1.4, 0)`，1.5 GU 圆形判定允许攻击。假如把原先“横纵差各不超过 1”的方形条件直接延伸到连续坐标，这个位置就不允许攻击。

**这只是两种连续几何的比较，不是说原版会处理这个小数格状态。** 它说明：整数格上的结果相同，不代表连续移动时的起手时机、站位和绕圈体验相同。

## 四、那么，1.5 GU 在你的项目里，真正需要担心什么？

### 1. 不是“统一距离”本身，而是距离是否与碰撞兼容

当前公共近战用双方投影后的地面位置判断距离，**不会把怪物体积直接加到 1.5 GU 射程上**。理想站位则取“基础 1.5 GU”与“现有身体接触距离”中的较大者。fileciteturn44file0L2-L2

代码中还有一个明确分支：

```gdscript
if preferred > HCPolicy.START_GU + GroundUnitSpace.EPSILON_GU:
    _hc_last_reason = "BODY_REQUIRES_EXPLICIT_EXCEPTION"
    velocity = Vector2.ZERO
    return
```

也就是说，**如果某个怪物与目标的身体接触约束要求它们保持超过 1.5 GU 的距离，而起手仍要求不超过 1.5 GU，就会发生规则冲突。** 当前代码会报告需要显式例外，并停止这条追击处理。fileciteturn41file0L2-L2

这是缩短距离后必须检查的具体风险。

但要区分证据等级：**代码中存在这个条件，不等于已经证明暗之骷髅精灵、暗之沃玛教主触发了它。** 需要读出这两只 Boss 对玩家、宠物的实际接触距离才能确定，不能直接据此给全部 Boss 加射程。

### 2. 起手距离、站位距离、命中容差是三个不同概念

当前两个基础常量恰好都是 1.5，但“可以开始攻击的位置”和“追击后停在哪里”，在设计上不是同一件事；已经开始的一次延迟攻击，之后又有自己的结算容差。你的代码也确实分开处理这些阶段。fileciteturn39file0L2-L2 fileciteturn41file0L2-L2

因此，检查时应该分别问：

**怪物在哪个距离起手？它实际停在哪里？玩家移动后，这一击在多远的位置结算？**

不能看到离开 1.5 后扣了一次血，就立即判定“起手距离没有改成功”；也不能把现有的 0.25 容差解释成“所有近战怪真正的射程都是 1.75”。该容差只应解释相应的已提交延迟攻击。fileciteturn44file0L2-L2

### 3. 菱形视角会放大视觉上的距离差异

你现在的标准投影为：

\[
screen_x=(ground_x-ground_y)\times32
\]

\[
screen_y=(ground_x+ground_y)\times16
\]

所以，**地面上的等距离圆投影到画面上，并不是屏幕上的正圆，而是横向更宽、纵向更窄的形状。** 这是根据当前投影公式得到的几何结果，不是攻击范围在不同方向随机变化。fileciteturn40file0L2-L2

再加上攻击判定使用的是角色地面位置，而不是手、武器尖端或贴图边缘，单看 Boss 身体之间的屏幕空隙，并不能准确判断它是否超过 1.5 GU。fileciteturn44file0L2-L2

**因此，距离校准应该显示脚底判定点和投影后的攻击范围，而不是在截图上量两个身体之间的像素。**

### 4. 玩家与怪物的射程差，会改变战斗体验

你项目正式距离契约中的玩家普攻是 **2 GU**，公共怪物近战覆盖是 **1.5 GU**。名义上存在 **0.5 GU** 的射程差。fileciteturn48file0L2-L2 fileciteturn42file0L2-L2

由此可以推导：在其他条件允许时，玩家可能先打到怪物，而怪物还需要继续靠近。这个差值能否稳定用于走位，取决于双方移动、攻击节奏、受击与碰撞规则，**不能只凭半径就断言能无限无伤风筝**。

这不是天然的 Bug，但它是应该明确接受的玩法差异。若怪物原先也是 2 GU，现在改为 1.5 GU，改变的不只是“少半格”，还可能改变双方第一次交手和追击中的先后关系。

## 五、我的建议：保留 1.5 作为基线，但不要把它当作已经验证的最终答案

## 一、现在的碰撞到底有多大？

### 1. Boss、普通怪、精英并不是同一套尺寸

当前 `EnemyActor._ready()` 的选择规则是：

```text
正式分类为 boss：
    固定使用 Boss 碰撞半径 28 px

不是 boss：
    优先使用配置中的 combat_radius_gu
    否则使用配置中的 collisionRadius
    都没有时，使用默认 16 px
```

**这里没有“精英统一放大”的分支，也没有根据贴图宽高自动生成碰撞的逻辑。** Boss 分支目前还会直接使用统一的 28 px，而不是继续读取该怪物行为配置中的个体碰撞尺寸。fileciteturn58file0L2-L2 fileciteturn46file0L2-L2

下面是当前规则下的代表性尺寸：

| 对象 | 配置的横向半径 | 脚底碰撞范围：宽 × 高 | 对应地面半径 |
|---|---:|---:|---:|
| 无独立碰撞配置的普通怪 | 16 px | **32 × 16 px** | **0.354 GU** |
| 稻草人 | 15 px | **30 × 15 px** | **0.331 GU** |
| 半兽勇士 | 21 px | **42 × 21 px** | **0.464 GU** |
| 沃玛卫士 | 24 px | **48 × 24 px** | **0.530 GU** |
| 普通骷髅精灵（56）、尸王（89） | 默认 16 px | **32 × 16 px** | **0.354 GU** |
| 暗之骷髅精灵（238）、暗之沃玛教主（239） | Boss 统一 28 px | **56 × 28 px** | **0.619 GU** |
| 玩家，作为对照 | 18 px | **36 × 18 px** | **0.398 GU** |

表中的配置值来自美术规格常量、怪物行为配置、正式身份分类及创建碰撞的代码；GU 数字是按项目转换公式计算并四舍五入的。这里的像素是**场景坐标中的尺寸，不是经过相机缩放后在手机截图上量到的尺寸**。fileciteturn48file0L2-L2 fileciteturn77file0L2-L2 fileciteturn64file0L2-L2 fileciteturn67file0 fileciteturn74file0L2-L2

### 2. 一个容易误判的地方：普通骷髅精灵、尸王虽然看起来大，碰撞却不大

当前正式目录将 **骷髅精灵 56、尸王 89 分类为 `elite`，不是 `boss`**。它们对应的 `large_client_boss` 配置只有大型客户端表现标记，没有独立碰撞半径，因此走非 Boss 分支，落到默认 **16 px**。fileciteturn67file0 fileciteturn64file0L2-L2 fileciteturn77file0L2-L2 fileciteturn58file0L2-L2

所以实际情况是：

> **部分大型精英的身体碰撞，确实和默认小怪一样；另一些精英，例如沃玛卫士，则有更大的独立配置。不能只看外观，也不能只看名称里有没有“王”“教主”。**

角色脚下的黄圈也不能直接当作碰撞边缘。当前普通脚底圈先在碰撞范围上乘 **1.25**，部分爬行怪还会应用额外的纯显示调整，这些调整不改变碰撞或攻击距离。fileciteturn50file0L2-L2 fileciteturn44file0L2-L2

## 二、默认 Boss 的体积，会不会让它进不了 1.5 GU？

**对玩家而言，按当前默认尺寸，不会仅仅因为 Boss 体积大而进不去。**

这里必须用正确的转换：玩家和怪物的碰撞是**近似椭圆的 16 边形**，横纵半径比例为 2∶1。其对应地面半径为：

\[
r_{\mathrm{GU}}=\frac{r_{\mathrm{px}}}{32\sqrt2}
\]

不是简单除以 32。项目的转换函数明确区分了这两种换算。fileciteturn69file0L2-L2 fileciteturn46file0L2-L2

### Boss 与玩家的实际核算

Boss 地面半径约 **0.6187 GU**，玩家约 **0.3977 GU**。

因此，按标称脚底形状计算，双方身体刚好接触时，中心间距约为：

\[
0.6187+0.3977=\mathbf{1.0165\ GU}
\]

在 **1.5 GU** 起手时，两者之间还留着约：

\[
1.5-1.0165=\mathbf{0.4835\ GU}
\]

的身体边缘间隙。这是根据当前尺寸得到的几何结果，未计入物理引擎的接触容差。

代码还额外保留了一段 **0.4375 GU 的站位间隙**：

```text
接触站位距离
= 怪物半径 + 目标半径 + 0.4375
```

对 Boss 打玩家：

\[
0.6187+0.3977+0.4375=\mathbf{1.4540\ GU}
\]

仍小于 1.5。随后公共策略取两者最大值：

```text
理想站位 = max(1.5, 接触站位距离)
```

因此这一组合的理想站位仍是 **1.5 GU**，不是 1.454 GU。fileciteturn56file0 fileciteturn60file0L2-L2 fileciteturn51file0L2-L2

**所以，不能把你那两只暗之 Boss 的“无动作扣血”，直接归因于“Boss 太大，1.5 格容不下”。至少 Boss 对玩家这组尺寸不支持这个解释。**

不过，统一中心距离不代表相同的视觉间隙：同样在 1.5 GU 起手，默认小怪离玩家的身体边缘更远，大 Boss 的身体边缘更近。这是不同半径在同一中心距离下必然产生的差别。

## 三、但我查到了真正冲突的组合：Boss 对神兽

这部分不是假设，而是当前配置和代码能够直接推导出的两项问题。

### 问题一：保留的站位间隙，把目标站位推到了攻击范围之外

神兽当前声明的地面战斗半径，来自 **21 px**，约为 **0.4640 GU**。怪物读取召唤物目标半径时，使用召唤物的 `combat_radius_gu`。fileciteturn71file0L2-L2 fileciteturn56file0

于是 Boss 对神兽：

\[
0.6187+0.4640+0.4375=\mathbf{1.5203\ GU}
\]

**这已经超过 1.5 GU。**

对比几组就很清楚：

| 攻击组合 | 代码计算的“半径之和＋站位间隙” | 是否超过 1.5 GU |
|---|---:|---|
| 默认普通怪 → 玩家 | 1.1888 | 否 |
| 沃玛卫士 → 玩家 | 1.3656 | 否 |
| Boss → 玩家 | 1.4540 | 否 |
| Boss → 骷髅宠物 | 1.3877 | 否 |
| **Boss → 神兽** | **1.5203** | **是** |

这张表是按已读取的尺寸与公共公式计算的，**不是物理接触距离实测表**；尤其召唤物还有下一节的形状问题。fileciteturn48file0L2-L2 fileciteturn77file0L2-L2 fileciteturn71file0L2-L2 fileciteturn56file0

而当前近战追击逻辑遇到这种情况，会执行：

```gdscript
if preferred > HCPolicy.START_GU + GroundUnitSpace.EPSILON_GU:
    _hc_last_reason = "BODY_REQUIRES_EXPLICIT_EXCEPTION"
    velocity = Vector2.ZERO
    return
```

**也就是：站位要求超过起手距离，就停止这条追击处理。**fileciteturn51file0L2-L2

需要准确限定：这不等于“Boss 永远打不了神兽”。代码在这个检查之前，会先尝试对已进入 1.5 GU 的目标起手；神兽自己走近、双方原本已在范围内，仍可能攻击。问题在于，**Boss 从范围外主动接近神兽时，存在被这条规则卡住的明确路径**。fileciteturn51file0L2-L2

### 问题二：召唤物的物理碰撞形状，与它声明的 GU 半径不一致

玩家和怪物使用公共函数创建等距椭圆碰撞，但召唤物的 `_ready()` 仍然是：

```gdscript
var shape := CircleShape2D.new()
collision_radius_px = 15.0 if summon_id == "skeleton" else 21.0
shape.radius = collision_radius_px
collision.shape = shape
```

与此同时，它又用**椭圆对应的换算函数**生成 `combat_radius_gu`。也就是说，同一个召唤物，实际创建的物理形状和提供给战斗系统的半径，不在同一套几何约定下。`CircleShape2D` 本身就是物理圆形，并不会因为游戏采用菱形视角就自动变成椭圆。fileciteturn71file0L2-L2 fileciteturn69file0L2-L2 citeturn668947search3

对神兽来说，区别是：

| 项目 | 尺寸 |
|---|---|
| 按其声明 GU 半径应对应的等距碰撞 | **42 × 21 px** |
| 当前创建的圆形物理碰撞 | **42 × 42 px** |

**纵向实际多占了一倍。**

按默认未额外缩放的形状、不计物理接触容差进行几何计算：

- **沿画面左右方向**，Boss 与神兽接触需要约 **1.0828 GU** 的中心间距。
- **沿画面上下方向**，Boss 的纵向半径 14 px，加上神兽圆形半径 21 px，共 35 px，对应约 **1.5468 GU**。

这里的“上下、左右”指画面方向，不是地面坐标轴。数值来自当前碰撞形状及等距投影公式。fileciteturn58file0L2-L2 fileciteturn69file0L2-L2 fileciteturn71file0L2-L2

**这意味着，在这组默认几何下，从画面上下方向贴近神兽，物理碰撞可能先把 Boss 挡在 1.5 GU 之外。** 即便修掉前面的站位间隙问题，这个形状不一致仍然需要处理。

这是源码支持的方向性风险，但我没有在你的手机上复现，也没有证据证明你原先那次战斗涉及神兽，因此不能把它直接当作那次异常的唯一原因。

## 四、统一攻击距离到底该不该保留？

**可以保留普通接触近战的统一距离，但不能让它与身体碰撞、站位要求互相矛盾。** 这次查到的问题，不需要靠“所有 Boss 加射程”或“所有怪物缩碰撞”来处理。

我建议按下面的顺序修正。

**首先，统一召唤物的碰撞几何。** 骷髅和神兽的物理碰撞、战斗半径、出生占地检查，应使用一致的地面单位约定。当前玩家和怪物已有公共碰撞构建函数，召唤物却另建圆形，是应该优先核对并修复的差异。修改时要保留玩家与宠物之间现有的穿行规则，不要顺带改碰撞层。

**其次，把“身体不能重叠”与“希望留一点站位空隙”分开。** 当前额外的 0.4375 GU 不是身体本身，但它与身体半径一起参与了“超过攻击距离就停止”的判断。对于真实身体能放进攻击距离的组合，应允许调整这段软性站位间隙；对于真实身体已经放不进去的组合，再要求明确的体型或攻击范围配置。不能直接删掉保护分支，也不能只把目标距离强行截成 1.5，让怪物往碰撞体内部走。

**最后，真正的大体型怪物应按个体配置，而不是按“大贴图＝大射程”推断。** 当前 Boss 全部用 28 px，部分大型精英却用默认 16 px，这是一种现有项目规则，不代表每只怪物都已做过独立的脚底体积校准。后续调整应检查具体 ID，并同时验证八方向接近、打玩家、打骷髅、打神兽，以及狭窄地形中的行为。

## 二、为什么大型半径选 0.5 GU，而不是随便选 24 或 28 px？

这是本方案最重要的依据。

### 1. 当前需要满足的不只是“两个身体放得下”

当前代码的接触站位需求是：

\[
C = 攻击者半径 + 目标半径 + 0.4375
\]

随后理想站位取：

\[
P = \max(1.5,\ C)
\]

如果这个结果超过 1.5 GU，公共近战追击就会进入 `BODY_REQUIRES_EXPLICIT_EXCEPTION` 分支，停止该追击处理。这正是身体与固定射程必须一起校准的原因。fileciteturn80file0L2-L2 fileciteturn85file0L2-L2 fileciteturn73file0L2-L2 fileciteturn81file0L2-L2

### 2. 采用 0.5 GU，最大的组合也能兼容

本方案最大的常规身体就是 0.5 GU，因此即使双方都是大型：

\[
C_{\max}=0.5+0.5+0.4375=\mathbf{1.4375\ GU}
\]

距离 1.5 GU 上限还剩：

\[
1.5-1.4375=\mathbf{0.0625\ GU}
\]

由此得到以下数值：

| 组合 | 身体半径之和＋现有站位间隙 | 距离 1.5 GU 上限的余量 |
|---|---:|---:|
| 小型怪物 → 玩家 | 1.1888 GU | 0.3112 GU |
| 大型怪物 → 玩家 | 1.3352 GU | 0.1648 GU |
| 大型怪物 → 骷髅宠物 | 1.2911 GU | 0.2089 GU |
| **大型怪物 → 神兽** | **1.4375 GU** | **0.0625 GU** |
| 大型身体 → 大型身体 | 1.4375 GU | 0.0625 GU |

最后一行只是验证尺寸上界，**不是建议开放新的 Boss 互殴或友军伤害机制**。

我还建议在离线配置检查中保留 **0.05 GU 的预留量**：

\[
r_a+r_t+0.4375+0.05 \leq 1.5
\]

最大半径因此应满足：

\[
r_{\max}\leq0.50625
\]

取 **0.5**，既满足约束，也便于统一管理。

**这 0.05 是本方案选择的配置预留量，不是 Godot 官方规定的安全距离，也不能代替墙角、拥挤和移动中的物理测试。** Godot 的 `safe_margin` 是碰撞恢复参数，会影响接近身体时的实际处理，不能与这里的站位预留量混为一谈。citeturn361436view1

### 3. 为什么不直接把大型统一成 24 px？

按项目现有换算计算：

| 统一大型横向半径 | 两个大型身体＋0.4375 GU 间隙 | 判断 |
|---|---:|---|
| 28 px | 约 **1.6749 GU** | 超过 1.5 |
| 24 px | 约 **1.4982 GU** | 数学上勉强放得下，但只剩约 0.0018 GU |
| **0.5 GU，约 22.63 px** | **1.4375 GU** | 满足本方案预留量 |

因此，我不建议把旧 Boss 的 28 px 原样保留，也不建议选一个恰好顶在边界上的 24 px。

**0.5 GU 不是唯一可行答案，但它是根据当前代码约束推导出来、可以解释清楚的一组数值，而不是凭感觉调出来的。**

## 三、为什么不优先选择“体型不同，射程也不同”？

第一种方案可以做对，甚至也能做到每个实例只读取一个预先算好的射程值，**并不天然比第二种慢**。

但对你的现有代码，它需要同时保证以下入口使用同一套“本怪物射程”：起手判定、追击停步、移动结束、延迟命中、寻路目标和诊断显示。当前源码中，这些位置已经围绕固定 `START_GU` 和 `PREFERRED_GU` 建立关联。fileciteturn73file0L2-L2 fileciteturn75file0L2-L2 fileciteturn81file0L2-L2

另外，你提出“最大要小于 2”。可变射程还需要明确：限制的是**起手距离**，还是**延迟命中的最终距离**。例如起手 1.9，再保留当前 0.25 容差，延迟结算边界就会到 2.15。当前确实存在这项延迟容差。fileciteturn73file0L2-L2

相比之下，第二种方案可以直接保留：

**普通近战新起手 1.5 GU；原本有延迟容差的攻击，仍按最多 1.75 GU 的相应结算边界处理；不再追加身体半径。**

因此，我选择第二种主要是为了**减少需要同时改对的地方**，而不是把它包装成已经测出更高帧率的方案。

## 四、真正可靠的施工，必须同时做好这五件事

### 1. “大型身体”与“Boss 身份”彻底分开

新增或使用独立的身体档位，例如 `small`、`large`，**不能为了把某只精英的碰撞变大，就把它设置为 Boss**。

当前 `is_boss` 来自正式身份分类，且会影响身体初始化等行为；身体分类不应反过来改变正式怪物身份。fileciteturn68file0L2-L2 fileciteturn72file0L2-L2

建议正式 Boss 默认大型；真正的大体型精英进入大型；其他小型怪物进入小型。**精英并不自动等于大型。**

所有归类在离线阶段按**整数怪物 ID**写清楚。运行时不读图片尺寸，不裁剪透明区域，不按当前动画帧重新估算体积。

这里有一个必须交付的前置结果：**完整的逐 ID 身体档位表，以及“哪些怪变大、哪些变小”的影响表。** 本次已经证明两档尺寸的兼容上界，但没有假装已经逐个审核完所有怪物的身体归类。

### 2. 神兽和骷髅必须改成正确的等距脚底形状

不能只把神兽的数字从 21 改成 22.63。

当前召唤物实际创建的是 `CircleShape2D`，但声明的 GU 半径使用了等距脚底转换。只改数字，仍会保留“物理圆形与战斗半径约定不同”的问题。fileciteturn77file0L2-L2

推荐玩家、怪物、召唤物都使用一致的脚底约定：**地面圆形半径，投影为等距椭圆，再使用现有 16 点凸多边形近似。** 怪物目前已经有这套公共模板，可以复用。fileciteturn78file0L2-L2

不要用缩放碰撞节点的方式把圆压扁；直接根据半径生成形状，碰撞节点保持单位缩放。Godot 官方也提醒，缩放碰撞形状可能带来非预期行为。citeturn605277search11

### 3. 所有地方只能认同一个最终半径

以下数据必须一致：

**物理碰撞、空间索引、寻路占地、前排阻挡、出生检查、传送落点、技能消费的目标脚底范围。**

当前半径已经参与前排阻挡、运动检测和群体间距等计算，所以仅修改物理形状并不能完成整改。fileciteturn75file0L2-L2 fileciteturn80file0L2-L2

尤其要避免这个顺序错误：

> 出生前按小身体检查落点 → 出生后变成大身体 → 卡进墙里或其他单位里面。

正确顺序应该是：**先确定最终档位和半径，再检查出生位置，再创建身体和登记索引。**

数据上采用一个权威策略输入，编译或缓存到现有规范目录；旧 `collisionRadius` 可以保留作审计来源，但不能在运行时又覆盖回来。

### 4. 保持 1.5 的含义不变，不添加新的“补偿射程”

本包建议保留现有基础停步距离与延迟规则，**不要再增加自适应射程、动态身体补偿或每次攻击的新探针**。

特别禁止把公式改成：

```text
允许攻击距离 = 1.5 + 怪物半径 + 目标半径
```

那会把 1.5 从“中心距离”偷换成“身体边缘之外的距离”，不是你现在要保留的玩法。

现有 `BODY_REQUIRES_EXPLICIT_EXCEPTION` 保护也不直接删除。应该用两档数据和加载校验，让正式对象不再触发尺寸矛盾，而不是把无效配置无条件放行。

### 5. 不把身体整改混成一次怪物系统大改

这次可以同步身体数据，但**不顺带修改伤害、防御、攻速、仇恨、技能伤害通道或特殊攻击射程**。

远程法术、范围攻击、投射物和召唤行为仍保留自己的范围规则；当前公共近战本来就与这些行为分开。fileciteturn82file0L2-L2

同样，碰撞整改不能替代之前讨论的动作、音效与伤害同步维修。**只把身体尺寸改对，不能据此宣布“有声音、掉血、没动作”全部解决。**

## 五、怎样做到不增加游戏的持续性能负担？

我建议把要求写成可验收的工程约束，而不是口头承诺“零成本”。

**运行时不新增逐帧工作。** 身体档位和半径只在加载、创建实例时解析，战斗中直接使用现有字段。不新增逐帧字典复制、图片扫描、全场怪物遍历和动态形状重建。

**怪物的碰撞复杂度不增加。** 每怪仍然一个身体、一个脚底形状、16 个顶点，不增加攻击 `Area2D`、额外射线或多个身体部件。Godot 官方建议尽量减少动态物体的碰撞形状数量。citeturn361436view2

**不动现有调度频率。** 不提高寻路、目标重选和环境检测频率，也不靠降低它们来掩盖新问题。

但必须明确一个边界：**神兽和骷髅从圆形改为凸多边形，不能预先保证引擎内部每一次碰撞的成本绝对不增加。** Godot 官方明确说明，凸多边形通常比圆形等基础形状有更高的单次碰撞开销。citeturn361436view0

另外，改变身体大小还可能改变实际拥挤程度和接触数量。因此，可靠的承诺应该是：

> **不新增逐帧 AI 算法、不增加每只怪物的形状和顶点数量，并以真机 A/B 测试“没有可重复的整体性能退化”作为发布条件。**

这比直接说“改完绝对一丁点性能都不消耗”更严谨。

## 六、这套方案怎样才算真正通过？

建议把下面这些作为发布门槛，不是可选测试：

| 验收项目 | 必须达到的结果 |
|---|---|
| **全目录身体配置** | 每个受管理正式 ID 有明确档位，无缺失、无非法值、无旧配置反向覆盖 |
| **八方向近战接近** | 大小怪对玩家、骷髅、神兽都不因身体与射程矛盾停止追击；范围外不新起普通攻击 |
| **物理与战斗一致性** | 实际形状、索引半径、目标脚底快照、出生检查使用同一套数据 |
| **窄道、墙角、前排阻挡** | 不穿墙、不穿身体，不靠关闭阻挡让攻击“恢复正常” |
| **生命周期** | 出生、召回、传送、换图、读档、死亡重生后，不残留旧形状或旧索引 |
| **技能回归** | 伤害和防御公式不变；AOE、投射物对新目标身体的边缘命中经过验证 |
| **性能** | 同机重复对比 10／20／30 怪、混合大型怪与宠物场景，无可重复性能退化 |

这里还有一个容易忽略的问题：**不能拿“旧版本 Boss 卡住不动”的场景，与“新版本 Boss 正常追击和攻击”的场景直接比较，然后把正常增加的战斗工作全算成优化失败。** 建议同时做固定实体状态的物理/脚本微基准，以及实际完整战斗对照，区分原因。

本次已经完成 **25 组尺寸组合的算术检查，以及 16 点投影的半径一致性核算**；这些证明的是配置几何，不是 Godot 实战或手机帧率。完整文件里已经列出对应的自动测试、正式测试套件、真机门禁和整包回滚要求。

## 最终建议

**就采用这组方案：**

> **小型怪物和骷髅：16 px 横向半径，约 0.353553 GU。**  
> **Boss、大型精英和神兽：统一 0.5 GU 半径。**  
> **玩家碰撞不变。**  
> **普通接触近战继续统一 1.5 GU，不额外加身体补偿。**

它保留了大小怪的占地差异，又让最大的正常身体组合也能满足当前站位规则；同时避免引入逐怪物射程以及新的逐帧计算。

**施工重点不是“改两个数字”，而是“两档身份映射、召唤物形状修正、全部半径消费者同步、初始化顺序正确”这四项一起完成。** 在你给定的目标下，这是我最推荐的整改路线。
